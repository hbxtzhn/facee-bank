## 一句话
索引里存的是列的原始值，而不是函数算出来的值。在列上套函数，MySQL 没法直接在索引里定位，只能对每一行先算再比，也就是全表扫描。

## 要点
- [kp1|3] 索引按列的原始值排序存放，不包含函数计算后的结果
- [kp2|3] `WHERE 函数(列) = 值` 要对每行先算函数再比较，无法利用索引定位
- [kp3|2] 改写法：把函数移到等号另一边，让列保持原样
- [kp4] MySQL 8.0.13 起可以建函数索引，直接对表达式建索引

## 详解
### 先搞懂：目录按名字排，却问「名字的长度是 3 的人」
学生名册按姓名拼音排好序，找「张三」可以直接翻到 Z 那一页。但如果问「名字长度为 3 的人」，名册的排序帮不上忙，只能一页页看每个人的名字再数字数。

索引也是这样：它按列的原始值排序。后文用到的术语：

- **索引**：按某列排好序的目录，能快速定位。
- **全表扫描**：不用索引，从头到尾逐行检查。
- **函数**：对一个值做计算得到另一个值，比如取年份、转大写。

### 机制：为什么套了函数就没法定位
设 `create_time` 上有索引，看这两条查询：

```sql
-- 写法 A：列保持原样，可以用索引
WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01'

-- 写法 B：列上套了函数，无法用索引
WHERE YEAR(create_time) = 2026
```

写法 A 里，索引按 `create_time` 排序，MySQL 可以直接定位到 2026 年的起点，顺着往后读到终点。

写法 B 里，索引中存的是完整的时间，不是年份。MySQL 无法判断索引里哪一段的 `YEAR()` 等于 2026，只能把每一行的 `create_time` 取出来，先算 `YEAR()`，再比较。这就是全表扫描。

### 怎么改写
核心思路：不要让列被函数包住，而是把计算挪到常量那一边。

- `WHERE YEAR(create_time) = 2026` 改成时间范围条件；
- `WHERE DATE(create_time) = '2026-11-08'` 改成 `create_time >= '2026-11-08' AND create_time < '2026-11-09'`；
- `WHERE price + 1 = 100` 改成 `WHERE price = 99`。

### 另一条路：函数索引
MySQL 8.0.13 起支持函数索引，也就是直接对表达式建索引，查询里使用同样的表达式就能走这个索引：

```sql
CREATE INDEX idx_year ON orders ((YEAR(create_time)));
```

这条语句里的双层括号是语法要求。不过建索引会占额外空间，通常先尝试改写查询。

### 怎么确认
用 `EXPLAIN` 对比改写前后：看 `key` 是否出现索引名，`type` 是否从 `ALL` 变成 `range` 等。

## 示例
```sql
-- 不推荐：create_time 上有索引也用不上
SELECT id FROM orders WHERE YEAR(create_time) = 2026;

-- 推荐：改写成范围条件，可以走索引
SELECT id FROM orders
WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';
```

## 易错点
- 以为只有自定义函数才会失效；`YEAR()`、`DATE()`、`LOWER()` 等内置函数同样会
- 把范围条件的右边界写成 `<= '2026-12-31'`；时间列带时分秒时会漏掉最后一天的数据
- 以为 8.0 以后函数一律能用索引；必须专门建函数索引，查询表达式也要一致

## 追问
### [f1] 隐式类型转换为什么也会让索引失效？
比如字符串列和数字比较，MySQL 会对列做类型转换，等于在列上套了函数，索引就用不上。所以比较时要让常量的类型和列一致。
