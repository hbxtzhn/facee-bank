## 一句话
Redis 集群把数据分成 16384 个槽，用 `CLUSTER ADDSLOTS` 把槽分给各个节点；key 落在哪个槽，就由持有那个槽的节点负责。

## 要点
- [kp1|3] 集群共有 16384 个槽，key 通过 CRC16 取模映射到槽
- [kp2|3] 用 `cluster addslots` 给节点分配槽，每个槽只归一个节点
- [kp3|2] 只有持有该槽的节点才响应对应 key 的命令
- [kp4] 槽没有全部分配完，默认整个集群不可用

## 详解
### 先搞懂：快递柜按格子编号
一个大快递站有 16384 个格子，编好号。三个管理员各管一段格子：谁的格子，谁来收发。取件时只看单号对应哪个格子，就知道该找哪个管理员。

先说几个词：

- **槽（slot）**：数据分片的最小单位，一共 16384 个，编号从 0 开始。
- **key 到槽的映射**：对 key 做 CRC16 校验，再对 16384 取余，结果就是槽号。
- **MOVED 重定向**：客户端找错节点时，节点回复“这个槽在另一个节点上”。

### 分配槽：谁拿哪些格子
刚握手完的集群，所有槽都没有主人。要用 `CLUSTER ADDSLOTS` 把槽编号一段一段分给各个主节点。例如三个主节点平分：

- 节点 1：0 到 5460
- 节点 2：5461 到 10922
- 节点 3：10923 到 16383

用 `redis-cli --cluster create` 时，工具会替你自动完成这件事。

### 分配之后：只有主人才响应
节点收到一个读写命令，先算出 key 的槽号：

1. 槽属于自己，就直接执行；
2. 槽不属于自己，回复 MOVED，告诉客户端该去哪个节点。

没有分配槽的节点，不会响应任何和键相关的命令。槽分配的结果会通过 Gossip 传给其他节点，所以每个节点都知道每个槽归谁。

### 为什么要多一层槽
如果直接用“key 对节点数取余”，加减节点时几乎所有 key 都要搬家。有了槽，key 到槽的关系永远不变，增减节点只需要把一部分槽连同数据迁走。

### 集群什么时候算可用
默认配置下，只有 16384 个槽都被分配出去，集群状态才是正常的。只要有一个槽没人负责，集群就会拒绝服务。

## 示例
```bash
# 把 0~5460 号槽分给 7000 节点（bash 的花括号展开）
redis-cli -p 7000 cluster addslots {0..5460}
# 查看集群状态
redis-cli -p 7000 cluster info
```

## 易错点
- 以为 key 直接对节点数取余；实际是先映射到槽，再由槽对应到节点
- 以为一个槽可以同时分给两个主节点；一个槽同一时刻只归一个主节点
- 以为分了一部分槽集群就能用；默认要全部槽都有主人

## 追问
### [f1] 为什么槽数是 16384，而不是更大？
作者的解释主要是节点之间心跳消息里要带槽位图，16384 位大约 2KB，体积合适，而集群规模本来也不会很大。
