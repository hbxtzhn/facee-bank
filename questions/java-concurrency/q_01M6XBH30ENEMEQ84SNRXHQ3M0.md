## 一句话
乐观锁假设冲突很少，操作时不先加锁，提交时检查有没有被别人改过，改过了就重试；CAS 和数据库的版本号机制都是典型实现。

## 要点
- [kp1|3] 乐观锁先操作、不加锁，提交时才检测是否有冲突
- [kp2|3] 检测到冲突就重试或放弃，而不是提前阻止别人
- [kp3|2] 典型实现：Java 的 CAS 和数据库表里的 version 字段
- [kp4|2] 适合读多写少、冲突很少的场景；冲突频繁时重试会浪费资源
- [kp5] 与之相对的悲观锁先加锁，如 synchronized、ReentrantLock

## 详解
### 先搞懂：先改后核对，还是先占位再改
两个同事同时编辑共享表格里的库存数字。

- **悲观**：我认为你一定会来抢，所以我编辑期间把表格锁住，你只能等。
- **乐观**：我认为我们不太会撞车，所以我先改，保存时检查：「我读到的版本还是最新的吗？」是就保存成功，不是就重新读一遍再改。

第二种就是乐观锁。大部分时候没有冲突，不用锁住别人，大家效率都更高。

后文用到的术语：

- **冲突**：两个线程同时改同一份数据。
- **版本号**：数据里的一个计数，每次修改加 1，用来判断是否被改过。
- **悲观锁**：认为冲突很多，先加锁再操作。

### 乐观锁怎么实现
**1. Java 里的 CAS**

线程读到变量的旧值，计算新值，用 CAS 写回：当前值还是旧值才写入，否则失败重试。`AtomicInteger` 等原子类就是这样做的，全程没有锁，线程不会被阻塞。

**2. 数据库的版本号**

表里加一个 `version` 字段。读数据时顺便读出版本号，更新时带上条件：

```sql
UPDATE stock SET count = count - 1, version = version + 1
WHERE id = 1 AND version = 5;
```

如果别人先改过，version 已经不是 5，这条更新影响的行数是 0，程序就知道冲突了，可以重新读取再试。

### 对比：乐观锁和悲观锁
| 对比项 | 乐观锁 | 悲观锁 |
|---|---|---|
| 假设 | 冲突很少 | 冲突很多 |
| 做法 | 先操作，提交时检查，冲突就重试 | 先加锁，再操作 |
| 线程是否阻塞 | 不阻塞 | 拿不到锁会阻塞 |
| 代表 | CAS、版本号 | synchronized、ReentrantLock、`SELECT ... FOR UPDATE` |
| 适合 | 读多写少、冲突少 | 写多、冲突频繁 |

结论：冲突少就用乐观锁，省掉加锁的开销；冲突频繁时，反复重试会浪费资源，用悲观锁更划算。

## 示例
```sql
-- 数据库乐观锁：更新行数为 0 表示被别人抢先修改了
UPDATE account SET balance = 900, version = version + 1
WHERE id = 1 AND version = 3;
```

## 易错点
- 以为乐观锁真的「没有锁」那么简单；它依然要保证检查和修改是原子的，CAS 靠 CPU 指令，数据库靠一条 UPDATE 语句
- 以为乐观锁一定比悲观锁快；冲突频繁时重试成本很高
- 版本号机制里，忘记在 UPDATE 的条件里带上版本号，那就起不到乐观锁的作用
- 以为乐观锁不会失败；它会失败，必须处理失败后的重试或放弃

## 追问
### [f1] 乐观锁什么时候不适用？
写操作很多、冲突频繁时，大量重试会消耗 CPU，反而不如直接加锁。

### [f2] 数据库乐观锁更新失败后怎么办？
重新读取最新数据，再重新计算、再提交；或者重试几次后放弃，提示用户稍后重试。
