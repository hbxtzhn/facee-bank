## 一句话
垃圾回收（GC）是 JVM 自动找出程序不再使用的对象、回收它们占用的堆内存，程序员不用手动释放。

## 要点
- [kp1|3] GC 自动回收堆里不再被使用的对象，不用手动 free
- [kp2|3] 判断依据是对象还能不能被程序访问到，访问不到就是垃圾
- [kp3|2] 回收时通常要暂停应用线程（STW），收集器的目标之一就是缩短停顿
- [kp4] 内存泄漏是对象仍被引用着但已没用，GC 回收不了它

## 详解
### 先搞懂：为什么需要垃圾回收
写业务代码时，`new` 出来的订单对象、用户对象都放在**堆**里。请求处理完，这些对象没人再用了，如果一直留着，内存迟早被占满。

可以把堆想成一间公共自习室，对象是占着座位的人。有些人早就离开了，只是书包还放在桌上。GC 就是管理员，定期巡查：确认没人要用的座位，把东西清走，让新来的人坐。

后文用到的术语：

- **堆**：JVM 里存放对象的内存区域。
- **垃圾**：程序以后再也访问不到的对象。
- **STW（Stop The World）**：GC 的某些阶段需要暂停所有应用线程。

### 垃圾回收做了什么
1. **找垃圾**：从一些起点（GC Roots，比如方法里的局部变量、类的静态变量）出发，顺着引用关系能走到的对象是活的，走不到的就是垃圾。
2. **清垃圾**：把垃圾占的内存回收，供后面分配新对象使用。
3. **整理内存**：有的收集器还会把存活对象挪到一起，避免内存碎片。

Java 里没有 `free` 或 `delete`。把变量赋为 `null` 也只是让对象没人引用，具体什么时候回收，由 GC 决定。

### 为什么这样设计
手动释放内存容易出两类错：忘了释放造成内存越占越多，或者释放了还在用造成程序崩溃。交给 JVM 自动管理，业务代码少了这类 bug。代价是回收时机不由程序控制，并且回收期间可能出现停顿，所以后面才有各种收集器和调优手段，目的都是让停顿更短。

## 易错点
- 以为 `System.gc()` 一定会马上回收；它只是建议 JVM 回收，不保证何时执行
- 以为有 GC 就不会内存泄漏；对象一直被静态集合之类的引用着，GC 认为它还在用，不会回收
- 以为 GC 回收的是所有内存；它管的主要是堆，不负责关闭文件、连接等外部资源

## 追问
### [f1] 内存泄漏和内存溢出有什么区别？
内存泄漏是已经没用的对象仍被引用，GC 回收不掉；泄漏积累多了，堆放不下新对象就会内存溢出（OOM）。溢出也可能是单纯堆设得太小，不一定有泄漏。
