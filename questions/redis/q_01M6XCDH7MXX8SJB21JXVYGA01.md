## 一句话
Redis 锁快而简单，但主从切换时可能丢锁；ZooKeeper 锁靠多数节点确认，一致性强，代价是更重、更慢，需要多维护一套组件。

## 要点
- [kp1|3] Redis 锁偏重可用性，主从异步复制，切换时锁可能丢
- [kp2|3] ZooKeeper 锁偏重一致性，写入要多数节点确认，已确认的不会丢
- [kp3|2] ZooKeeper 用临时顺序节点实现锁，客户端断开节点自动删除
- [kp4|2] Redis 靠过期时间释放，ZooKeeper 靠会话断开释放
- [kp5] 两者在长时间 GC 暂停下，都可能出现旧持有者以为自己还有锁

## 详解
### 先搞懂：记账本的两种风格
Redis 像一个前台小本子：写得快，用起来方便，但前台换班时可能漏抄。ZooKeeper 像一个需要多人签字的公证簿：每一笔都要大多数人确认才算数，慢一点，但写进去的不会随便丢。

后文用到的词：

- **CP**：出现网络分区时，优先保证一致性，宁可暂时不可用。
- **AP**：优先保证可用，数据可能暂时不一致。
- **临时顺序节点**：ZooKeeper 里和客户端会话绑定、编号递增的节点；会话结束就自动删除。

### Redis 锁的机制
用 `SET NX EX` 或 Redisson 创建一个 key。没拿到锁的客户端等着重试。锁的释放有两种：主动删除，或到时间过期。

问题是主从复制是异步的，主节点宕机时锁可能没同步，新主上没有这把锁。从 CAP 的角度看，Redis 主从更接近 AP，倾向于“先可用”。

### ZooKeeper 锁的机制
1. 每个客户端在锁的目录下创建一个临时顺序节点；
2. 检查自己的编号是不是最小的，是就拿到锁；
3. 不是，就只监听比自己小的上一个节点；
4. 上一个节点被删除，说明轮到自己了。

持有者宕机，会话超时，节点自动删除，下一个等待者被通知。不依赖过期时间。ZooKeeper 写入要多数节点确认，已确认的数据在主节点切换后也不会丢，属于 CP。

### 方案对比：Redis 与 ZooKeeper
| 维度 | Redis 锁 | ZooKeeper 锁 |
|---|---|---|
| 一致性 | 主从切换可能丢锁 | 多数节点确认，强一致 |
| 释放方式 | 过期时间到或主动删除 | 会话断开自动删除 |
| 等待方式 | 轮询或订阅通知 | 监听前一个节点 |
| 复杂度 | 很多项目已有 Redis | 需要额外部署维护 |
| 适合 | 一般业务，能容忍极小概率重复 | 对互斥要求严格的场景 |

结论：多数业务选 Redis 加数据库兜底；对互斥要求严、愿意多维护一套组件，再选 ZooKeeper。

### 两者共同的盲区
ZooKeeper 也靠会话超时判断客户端是否还活着。如果持有者因为长时间 GC 暂停，会话已经超时、锁被别人拿走，它醒来仍以为自己持有锁。所以重要数据不能只靠分布式锁，还要有数据库层的校验。

## 易错点
- 以为 ZooKeeper 锁绝对不会出问题；暂停和会话超时仍有边界情况
- 以为 Redis 锁不能用；大多数业务场景下它足够
- 把 CAP 理解成三选二的永久标签；它描述的是网络分区时的取舍

## 追问
### [f1] 为什么 ZooKeeper 只监听前一个节点，不监听全部？
所有客户端都监听同一个节点，锁一释放，所有人同时被唤醒，只有一个能成功，其余白忙。只监听前一个，每次只唤醒一个，避免惊群。
