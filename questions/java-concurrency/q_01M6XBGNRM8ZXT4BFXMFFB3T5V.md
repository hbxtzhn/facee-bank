## 一句话
线程安全问题是指多个线程同时读写同一份数据时，结果和一个一个执行不一样。根源是 count++ 这类操作不是一步完成的，几个线程的步骤会交错，导致更新丢失。

## 要点
- [kp1|3] 多个线程同时读写同一个共享变量，才可能出现线程安全问题
- [kp2|3] count++ 分读取、加一、写回三步，线程的步骤会交错
- [kp3|2] 交错后两个线程都基于旧值计算，一次更新被覆盖丢失，这叫竞态条件
- [kp4] 解决思路：加锁互斥、使用原子类，或者不共享数据

## 详解
### 先搞懂：两个人同时改一个数
想象一份在线共享表格，库存是 10。小王和小李同时打开，各自看到 10，小王卖出 1 个改成 9，小李也卖出 1 个改成 9。其实卖了两个，库存却只少了 1。

多线程改同一个变量就是这个场景。

后文用到的几个词：
- **共享数据**：多个线程都能访问到的变量，比如类的成员变量、静态变量。
- **竞态条件**：结果取决于线程谁先谁后的时机，同样的代码有时对、有时错。
- **线程安全**：多个线程同时用，结果仍然正确。

### 为什么 count++ 会出错
`count++` 看起来是一行，实际分三步：

1. 读取 count 当前值；
2. 把值加一；
3. 把结果写回 count。

假设 count 是 0，线程 A 和线程 B 同时执行：A 读到 0，B 也读到 0，A 算出 1 写回，B 也算出 1 写回。两次自增，最终结果是 1，丢了一次。

这类问题的特点是：偶尔才出现，压力越大越容易出现，所以测试时很难发现，上线后才暴露。

### 怎么避免
- **加锁**：用 `synchronized` 或 `Lock`，同一时刻只让一个线程执行这段代码。
- **原子类**：计数场景用 `AtomicInteger`，一步完成自增。
- **不共享**：每个线程用自己的变量（局部变量、`ThreadLocal`），或者数据不可变，就没有冲突。

## 示例
```java
class Counter {
    int count = 0;
    void add() { count++; } // 非线程安全：多线程并发调用，最终结果可能小于预期
}
```

## 易错点
- 以为只有「写」才有问题；一个线程在读、另一个线程在写，也可能读到不一致的数据
- 以为 count++ 是一条语句就不会被打断；它在字节码层面是多步操作
- 以为只读数据一定线程安全；只读且没人修改才安全，如果有线程在改，读也会出问题

## 追问
### [f1] 局部变量会有线程安全问题吗？
一般不会。局部变量在每个线程自己的栈里，各线程互不干扰。除非局部变量引用的对象被发布给了其他线程。
