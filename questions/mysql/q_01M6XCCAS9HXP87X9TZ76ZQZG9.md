## 一句话
二级索引存主键值，是因为行的物理位置会变，而主键值不会变。这样行搬家时只需要改聚簇索引，不用动所有二级索引。

## 要点
- [kp1|3] InnoDB 二级索引的叶子节点存的是索引列加主键值
- [kp2|3] 行的物理位置会因页分裂、重组而变，主键值是稳定的
- [kp3|2] 存主键值后，行移动时只需维护聚簇索引，二级索引不用改
- [kp4] 代价是多一次主键查找，且主键越长，所有二级索引越大

## 详解
### 先搞懂：快递地址和身份证号
假设你在小区里登记住户：一种办法是记住户现在住几栋几号，另一种是记身份证号，再去户籍库查地址。住户经常搬家，前一种办法每搬一次，所有登记簿都要改；后一种办法，登记簿永远不用动，只改户籍库里那一条。

InnoDB 选的就是第二种。几个术语：

- **聚簇索引**：以主键为键的那棵 B+ 树，叶子节点里直接存整行数据。
- **二级索引**：除主键外你建的其他索引，叶子节点只存索引列和主键值。
- **回表**：先在二级索引里找到主键值，再拿主键值去聚簇索引取整行。
- **页分裂**：一个数据页放不下了，InnoDB 把它拆成两页，一部分行会换到新页里。

### 为什么不存物理地址：行会搬家
InnoDB 的行是放在聚簇索引的叶子页里的，位置不是固定的：

1. 往页里插入新行，页满了会发生页分裂，一部分行被搬到新页。
2. 删除、更新变长字段后，页内的行会重新整理。
3. 表重建或碎片整理后，行的位置全部重排。

如果二级索引存物理地址，上面每一次搬家，都要找到这行对应的每个二级索引项逐个修改。表上有几个二级索引，就要多改几处，页分裂时一页里很多行同时搬家，代价会非常高。

### 存主键值：搬家不用通知
主键值是这行数据的逻辑身份，只要主键不改，它就一直不变。二级索引存主键值之后：

- 行在页间怎么搬，只影响聚簇索引自己，二级索引完全不用知道；
- 页分裂、重组这些内部操作，不会牵连二级索引的维护；
- 查询时多走一步：二级索引找到主键，再到聚簇索引取整行。

这是用「读时多查一次」换「写时少改很多处」。

### 方案对比：存主键值和存物理地址
| 方案 | 二级索引存什么 | 行移动时 | 读取整行 | 代表 |
|---|---|---|---|---|
| 存主键值 | 索引列加主键值 | 二级索引不用改 | 再查一次聚簇索引 | InnoDB |
| 存物理地址 | 索引列加行位置 | 要改所有二级索引 | 直接按地址读 | MyISAM |

结论：InnoDB 行会频繁移动，所以选主键值；代价是回表多一次树查找，所以主键要尽量短。

### 进阶：这个设计带来的后果（基础薄弱可先跳过）
- 主键越长，每个二级索引项都跟着变长，索引占的空间更大，所以主键常选自增整数。
- 如果表没有定义主键，InnoDB 会选一个非空唯一索引当聚簇索引，再没有就生成一个隐藏的行 ID 当主键，二级索引里存的是它。
- 覆盖索引能直接从二级索引拿到想要的列，省掉回表，因为主键值本来就在二级索引里。

## 示例
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50),
  age INT,
  KEY idx_name (name)
);
-- idx_name 的叶子节点存的是 (name, id)
-- 下面这条先查 idx_name 拿到 id，再按 id 回表取整行
SELECT * FROM user WHERE name = 'Tom';
```

## 易错点
- 以为二级索引叶子节点存整行数据；实际只存索引列和主键值，整行在聚簇索引里
- 以为二级索引存的是行的磁盘地址；那是 MyISAM 的做法，InnoDB 不是
- 以为主键长短无所谓；主键会被复制进每个二级索引，越长索引越大

## 追问
### [f1] 为什么主键推荐用自增整数？
自增整数短，复制到每个二级索引里占的空间小；而且新行总是插在最后一页，很少触发页分裂。

### [f2] 更新主键值会有什么后果？
主键值就是行的身份，改主键等于删旧行再插新行，所有二级索引里存的主键值也要一起改，代价很高，应该避免。
