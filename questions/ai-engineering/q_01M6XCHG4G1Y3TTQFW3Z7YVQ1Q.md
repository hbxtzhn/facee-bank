## 一句话
全局工作流保证主干流程可控，在没法预先写死的节点里嵌入 Agent 子循环，让模型在局部自由探索，兼顾可控和灵活。

## 要点
- [kp1|3] 全局工作流定死主干步骤，流程可预测、好调试
- [kp2|3] 在不确定的节点里嵌入 Agent 循环，让模型自己决定怎么做
- [kp3|2] 子循环要有边界：限定可用工具、最大轮次和输出格式
- [kp4|2] 子循环结束后把结果写回共享状态，主干流程继续往下走
- [kp5] 两头的缺点互补：纯工作流太死板，纯 Agent 太不可控

## 详解
### 先搞懂：旅行社定行程，导游临场发挥
旅行社把整个行程定好：第一天到酒店、第二天去景区、第三天返程，这是主干。但在景区里怎么逛、遇到下雨怎么办，交给导游现场判断。

全局工作流就是行程，Agent 子循环就是导游的临场发挥。大方向不乱，细节有弹性。

后文用到的术语：
- **全局工作流**：开发者提前设计好的主干流程。
- **Agent 子循环**：嵌在某个节点里的推理、行动、观察循环。
- **边界**：给子循环设的限制，防止它失控。

### 为什么不全用工作流，也不全用 Agent
全用工作流：每个步骤都要提前写好。遇到「调研一个问题要查几次资料」这种没法预知的步骤，就写不下去了。

全用 Agent：整个任务让模型自由发挥，步骤越长越容易偏离目标、重复绕路，出了问题也很难定位。

混合做法取两者的长处：确定的部分用工作流，不确定的部分才交给 Agent。

### 怎么嵌入
1. 在工作流里找出不确定的节点，比如「搜集资料」「排查故障」；
2. 把这个节点实现为一个 Agent 子循环，给它需要的工具；
3. 设好边界：最大轮次、可用工具、期望的输出格式；
4. 子循环结束后，把结果写回状态，工作流继续执行后续节点。

### 对比：三种架构
| 方案 | 可控性 | 灵活性 | 适合 |
|---|---|---|---|
| 纯工作流 | 高 | 低 | 步骤固定的业务 |
| 纯 Agent | 低 | 高 | 开放式探索任务 |
| 工作流嵌入 Agent | 主干高，局部较低 | 局部高 | 大多数有不确定环节的任务 |

结论：多数实际业务先用工作流搭主干，只在确实无法预先定义的节点才嵌入 Agent。

## 示例
```python
def research_node(state):
    # 不确定的节点：用有边界的 Agent 子循环
    state["notes"] = run_agent(
        task=state["question"], tools=[search, read_page], max_steps=8)
    return state

pipeline = [parse_question, research_node, write_report]   # 主干固定
```

## 易错点
- 以为嵌入 Agent 后整个流程就不可控了；主干仍是固定的，只有局部有弹性
- 以为子循环可以不设限制；没有轮次和工具边界，它会拖垮整个流程
- 以为所有节点都该换成 Agent；确定的步骤用普通节点更稳、更便宜

## 追问
### [f1] 子循环失败了怎么办？
设最大轮次和超时，失败时把失败信息写入状态，由主干流程决定重试、走降级分支或交给人处理。

### [f2] 怎么判断哪个节点该用 Agent？
如果这一步的做法无法提前列出，要靠中间结果决定下一步，就适合 Agent。如果能写成固定几步，就用普通节点。
