## 一句话
Redis 主从之间是异步复制，锁刚写进主节点还没同步到从节点，主节点就挂了，新主上没有这把锁，别的客户端就能再拿到锁。

## 要点
- [kp1|3] 主从复制是异步的，主节点写成功就返回，不等从节点
- [kp2|3] 锁没同步到从节点时主节点宕机，从节点升主后没有这把锁
- [kp3|2] 结果是同一把锁被两个客户端同时持有，互斥失效
- [kp4|2] 缓解办法：多实例加锁的红锁、用 ZooKeeper 等强一致方案
- [kp5] 单节点部署没有主从切换问题，但单点故障

## 详解
### 先搞懂：先收了钱，账本还没抄给副店
设想一家连锁店，总店收了一笔预订，立刻回复客人“订好了”，同时安排人去抄给分店。如果总店在抄送之前突然关门，分店升级成新总店，它的账本里就没有这笔预订，下一个客人来订同一个位子，也会被答应。

Redis 的主从就是这样。后文用到的词：

- **主节点**：接收写入的节点。
- **从节点**：复制主节点数据的备份节点。
- **异步复制**：主节点不等从节点确认，先返回成功。
- **故障切换**：主节点故障后，由一个从节点升为新主节点。

### 问题是怎么发生的
按时间顺序：

1. 客户端 A 向主节点加锁，主节点写入后立刻返回成功；
2. 主节点还没来得及把这条数据同步给从节点，就宕机了；
3. 哨兵或集群把某个从节点升为新主节点；
4. 新主节点里没有这把锁；
5. 客户端 B 来加锁，成功；此时 A 还认为自己持有锁。

两个客户端同时进入临界区，分布式锁的互斥就被破坏了。

### 为什么 Redis 默认没解决
Redis 主从选择了可用性和响应速度：写入时不等从节点确认。这样快，但在故障瞬间可能丢失刚写入的数据，锁也是数据，所以会丢。

### 怎么缓解
- **红锁（RedLock）**：不只在一个实例上加锁，而是在多个独立实例上加，超过半数成功才算拿到。实现复杂，也有争议。
- **ZooKeeper**：写入要多数节点确认，主节点切换也不会丢已确认的数据，强一致，但吞吐和部署成本不同。
- **业务兜底**：即使有锁，也在数据库层用唯一索引、版本号保证最终正确。

### 方案对比：应对丢锁的办法
| 方案 | 思路 | 代价 | 适合 |
|---|---|---|---|
| 单 Redis 加主从 | 接受极小概率丢锁 | 低 | 偶尔重复执行没后果的场景 |
| 红锁 | 多个独立实例过半成功 | 实现复杂 | 不想引入 ZooKeeper 的场景 |
| ZooKeeper | 多数节点确认，强一致 | 多一套组件 | 对互斥要求很严的场景 |
| 数据库兜底 | 唯一约束、乐观锁 | 业务改造 | 所有场景都建议加 |

结论：大多数业务用 Redis 锁加数据库兜底就够；对互斥要求极严才考虑 ZooKeeper。

## 易错点
- 以为主从切换时数据一定不丢；异步复制下刚写入的数据可能丢失
- 以为锁加了超时时间就没有这个问题；这是两个独立的问题
- 以为这是 Redisson 的缺陷；这是 Redis 主从异步复制的特性

## 追问
### [f1] 单实例 Redis 做分布式锁有这个问题吗？
没有主从切换的问题，但 Redis 一旦宕机，整个锁服务不可用。如果开了持久化也可能因为重启丢失部分数据。
