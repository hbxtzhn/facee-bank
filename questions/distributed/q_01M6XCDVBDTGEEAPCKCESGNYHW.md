## 一句话
MQTT 是一种轻量的发布订阅消息协议，报文小、开销低，适合物联网这种带宽低、网络不稳定的环境。

## 要点
- [kp1|3] MQTT 是轻量级的发布/订阅协议，传输开销小
- [kp2|3] 适合物联网：设备资源少、带宽低、网络经常断
- [kp3|2] 消息发到某个主题，订阅了该主题的设备都能收到
- [kp4] 有不同的服务质量等级，可以在可靠性和开销之间选择
- [kp5] RabbitMQ 可以通过插件支持 MQTT

## 详解
### 先搞懂：智能家居里的传感器
想象你家里有温度传感器、智能灯、手机 App。传感器每隔一会儿上报温度，手机想看温度，灯想根据温度调亮度。

如果每个设备都直接去连其他设备，线路会乱成一团。更好的做法是设一个「公告栏」：传感器把温度贴到「温度」这一栏，想看的设备自己去看这一栏。

这就是**发布订阅**：发布者往主题里发消息，订阅者订阅主题接收消息，双方互相不认识。**MQTT** 就是为这种场景设计的轻量协议。

后文术语：
- **Broker**：充当公告栏的服务端，负责接收和转发消息。
- **主题（Topic）**：消息的分类名称，如「家里/客厅/温度」。
- **发布 / 订阅**：往主题发消息 / 关注主题收消息。
- **QoS**：服务质量等级，决定消息投递的可靠程度。

### 为什么适合物联网
物联网设备往往资源很有限：芯片弱、电量少、信号差，还可能在移动中频繁断网。MQTT 针对这些情况设计：

- **报文头很小**，传输的数据量少，省流量；
- **协议简单**，设备端实现起来很轻；
- **长连接加心跳**，Broker 能知道设备是否在线；
- **支持断线后恢复**，网络不稳定时也能继续通信。

### QoS 服务质量
MQTT 定义了三种等级，可靠性依次升高，开销也依次升高：

- 最多一次：发出去就不管，可能丢；
- 至少一次：保证到达，但可能重复；
- 恰好一次：保证到达且不重复，流程最复杂。

像温度这种隔几秒就上报一次的数据，丢一两条无所谓，用低等级就够；控制指令则可以用更高的等级。

### 遗嘱消息
设备连接时可以预先留一条「遗嘱」。如果设备异常掉线，Broker 会代替它把这条消息发布出去，其他订阅者就能知道设备离线了。

## 示例
```bash
# 订阅主题（使用 mosquitto 命令行客户端）
mosquitto_sub -h broker.example.com -t "home/livingroom/temperature"

# 向主题发布一条消息
mosquitto_pub -h broker.example.com -t "home/livingroom/temperature" -m "26.5"
```

## 易错点
- 把 MQTT 当成 Kafka、RocketMQ 那样的业务消息队列；它主要用于设备通信，不擅长大规模堆积和复杂消费模型
- 以为 MQTT 一定不丢；是否可靠取决于选的 QoS 等级
- 以为设备之间直接通信；实际上都通过 Broker 转发

## 追问
### [f1] MQTT 和 HTTP 比有什么优势？
MQTT 报文更小，长连接可以由服务端主动推送消息，适合设备频繁上报和下发指令。HTTP 是请求响应模式，服务端不方便主动推给设备。
