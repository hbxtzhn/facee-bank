## 一句话
select 每次调用都要把整个 fd 集合拷进内核并逐个检查，还限制 fd 数量（常为 1024），连接一多就又慢又不够用。

## 要点
- [kp1|3] 每次调用都要把 fd_set 从用户态拷贝到内核态
- [kp2|3] 内核线性遍历所有 fd，返回后用户程序还要再遍历一遍找就绪的
- [kp3|2] fd_set 是固定大小的位图，上限由 FD_SETSIZE 决定，常为 1024
- [kp4] fd_set 会被内核改写，每次调用前要重新设置

## 详解
### 先搞懂：一个人看守很多个门铃
做网络服务时，一个线程要同时管很多个连接，不能傻等某一个。可以把它想成前台文员面对一排门铃：他不知道哪个会响，只能每隔一会儿把整排门铃挨个看一遍。门铃越多，看一遍越久，而真正响的往往只有几个。

后文用到的术语：

- **fd（文件描述符）**：操作系统给每个打开的文件或连接编的号。
- **fd_set**：select 用来存放“我关心哪些 fd”的集合，本质是一个位图（每个 fd 占一位）。
- **用户态 / 内核态**：普通程序运行的区域和操作系统内核运行的区域，两边传数据要拷贝。

### 缺点一：每次都全量拷贝
调用 select 时，程序要把读、写、异常三个 fd_set 传给内核。内核处理完，再把结果拷贝回来。

这件事每次调用都发生，哪怕监听的 fd 和上一次完全一样。监听的连接很多、真正活跃的很少时，大部分拷贝都是白做的。

### 缺点二：全量线性遍历
内核要从头到尾检查集合里的每个 fd，看它有没有就绪。时间花费和监听的 fd 数量成正比，和活跃的数量无关。

select 返回时只告诉你“有几个 fd 就绪”，没告诉你是哪几个。用户程序还得自己再遍历一遍集合，用 `FD_ISSET` 逐个判断。所以同样的遍历，内核做一次，用户程序再做一次。

### 缺点三：fd 数量有上限
fd_set 是固定大小的位图，大小由编译时的 `FD_SETSIZE` 决定，常见值是 1024。注意这里限制的是 fd 的编号范围，不只是个数：编号大于等于上限的 fd 放不进去。

### 缺点四：集合会被改写
select 返回时，内核会把没有就绪的位清掉，集合只剩就绪的 fd。所以下一轮循环之前，程序必须重新把要监听的 fd 全部设置一遍，这又多了一份开销。

### 进阶：为什么后来有了 poll 和 epoll（基础薄弱可先跳过）
- poll 改用数组，去掉了 1024 的上限，但仍是全量拷贝加线性遍历。
- epoll 把“要监听谁”保存在内核里，只返回就绪的 fd，所以不受这几个缺点影响。
- 监听的 fd 很少、而且大多活跃时，select 的这些开销并不明显，它的优点是各个平台都支持。

## 示例
```c
fd_set readfds;
while (1) {
    FD_ZERO(&readfds);                 // 每轮都要重新设置
    for (int i = 0; i < n; i++) FD_SET(fds[i], &readfds);
    select(maxfd + 1, &readfds, NULL, NULL, NULL);
    for (int i = 0; i < n; i++) {      // 返回后还要自己遍历找就绪的
        if (FD_ISSET(fds[i], &readfds)) handle(fds[i]);
    }
}
```

## 易错点
- 以为 select 返回后能直接拿到就绪的 fd 列表；它只告诉你有几个就绪，还得自己遍历
- 以为 1024 是连接数上限；它限制的是 fd 编号的范围
- 循环里不重新设置 fd_set，会漏掉之前没就绪、被清掉的 fd

## 追问
### [f1] 为什么 select 返回后还要重新设置 fd_set？
因为内核会把没就绪的位清掉，集合里只留就绪的 fd。不重新设置，下一轮就只监听上一轮就绪的那几个。

### [f2] 监听 fd 很少时，select 还有问题吗？
问题不大，全量拷贝和遍历的成本随数量增长，数量少时可以忽略。select 的好处是几乎所有平台都支持。
