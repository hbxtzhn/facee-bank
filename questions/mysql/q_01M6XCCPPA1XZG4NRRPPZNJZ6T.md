## 一句话
共享锁（读锁）可以多个事务同时持有，彼此不阻塞；排他锁（写锁）一次只能一个事务持有，和任何别的锁都冲突。

## 要点
- [kp1|3] 共享锁（S 锁）：多个事务可以同时持有，只读不写
- [kp2|3] 排他锁（X 锁）：一次只能一个事务持有，用于修改数据
- [kp3|2] 兼容规则：S 和 S 兼容，其余组合都冲突
- [kp4] UPDATE、DELETE、INSERT 会自动加排他锁
- [kp5] 普通 SELECT 默认不加锁，要加锁要写 FOR SHARE 或 FOR UPDATE

## 详解
### 先搞懂：多人看可以，多人改不行
想象一份共享文档：

- 很多人同时「只读」没问题，大家看到的内容一样；
- 一个人在「编辑」的时候，其他人既不能同时编辑，通常也不该读到改了一半的内容。

数据库的锁就是同样的规则。后文会用到这几个词：

- **共享锁（S 锁）**：也叫读锁，表示「我要读这行，别人别改」。
- **排他锁（X 锁）**：也叫写锁，表示「我要改这行，别人别碰」。
- **兼容**：两种锁可以同时加在同一行上。

### 兼容规则：只有读和读能同时
| 已持有 \ 想加 | S 锁 | X 锁 |
|---|---|---|
| S 锁 | 兼容 | 冲突，等待 |
| X 锁 | 冲突，等待 | 冲突，等待 |

也就是：多个事务可以一起读；只要有人要写，就必须等所有读锁和写锁释放。

### 什么时候加哪种锁
- **UPDATE、DELETE、INSERT**：自动在涉及的行上加排他锁，事务提交或回滚时才释放。
- **`SELECT ... FOR SHARE`**（旧写法 `LOCK IN SHARE MODE`）：显式加共享锁。
- **`SELECT ... FOR UPDATE`**：显式加排他锁，常用来「先锁住再改」。
- **普通 `SELECT`**：InnoDB 默认读的是快照，不加这两种锁，所以不会被写操作阻塞。

### 为什么要这样设计
读读不冲突，所以并发读的性能不会受影响。读写、写写需要互斥，保证一个事务在改数据时，别人不会同时改，也不会基于改到一半的数据做决定。

## 示例
```sql
-- 事务 A：加共享锁读取
SELECT * FROM account WHERE id = 1 FOR SHARE;

-- 事务 B：加排他锁，会等到 A 提交或回滚
SELECT * FROM account WHERE id = 1 FOR UPDATE;
```

## 易错点
- 以为普通 SELECT 也会加读锁；InnoDB 默认的普通读不加锁
- 以为共享锁之间也会冲突；多个共享锁可以并存
- 以为锁在语句执行完就释放；在事务里要等提交或回滚

## 追问
### [f1] FOR SHARE 和 FOR UPDATE 怎么选？
只想保证「读的这行在我提交前别人不能改」用 `FOR SHARE`。准备读完后马上修改，用 `FOR UPDATE`，直接拿排他锁，避免先拿共享锁再升级造成冲突。
