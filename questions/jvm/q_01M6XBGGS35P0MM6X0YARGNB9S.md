## 一句话
内存泄漏是对象已经不再使用，却因为还被某处引用着而无法被垃圾回收，内存被一直占用，积累多了就会导致内存溢出。

## 要点
- [kp1|3] 对象不再使用，但仍被引用，GC 无法回收
- [kp2|3] 泄漏本身不报错，内存慢慢被占满，最终可能抛出 OOM
- [kp3|2] 常见来源：静态集合只增不减、ThreadLocal 没 `remove()`、资源没关闭、监听器没注销
- [kp4] 现象是 GC 后老年代占用越来越高，可以通过堆转储定位

## 详解
### 先搞懂：忘了归还的图书
图书馆里有人借了书却一直不还，也不看，书架上就少了一本。借的人多了，书架就空了，新来的读者借不到书。内存泄漏就是这样：对象明明没用了，却一直被"借着"，系统回收不了。

后文用到的术语：
- **GC Roots**：回收时的起点，如静态变量、栈里的局部变量；从它们出发能到达的对象被认为在使用。
- **可达**：能从 GC Roots 沿着引用找到。
- **堆转储**：把堆里的对象保存下来用来分析。

### Java 有 GC，为什么还会泄漏
GC 只能回收"不可达"的对象。如果一个对象你已经不用了，但某个静态变量或长期存活的对象还指着它，GC 就认为它还在用，不会回收。

### 常见的泄漏场景
- **静态集合只增不减**：比如放在 `static Map` 里的缓存，一直放进去，从不清理。
- **ThreadLocal 用完没 `remove()`**：线程池里的线程长期存活，值一直留着。
- **资源没有关闭**：数据库连接、文件流等没关闭。
- **监听器、回调没有注销**：对象被注册的一方一直引用。
- **缓存没有上限**：无限增长。

### 怎么发现和定位
1. 观察 GC 日志或监控：每次 Full GC 之后，老年代占用仍然在持续升高；
2. 用堆转储工具（如 MAT）查看占用最多的对象，沿引用链找到是谁一直引用着它；
3. 修复代码：及时清理、设置缓存上限、用完调用 `remove()` 或 `close()`。

### 内存泄漏和内存溢出的关系
泄漏是"原因"，溢出是"结果"之一：泄漏的对象越积越多，最后空间不足，抛出 `OutOfMemoryError`。但溢出也可能是因为一次申请太多，不一定有泄漏。

## 示例
```java
public class LeakDemo {
    // 静态集合持有对象引用，只加不删，数据一直累积
    private static final List<byte[]> CACHE = new ArrayList<>();

    static void handle() {
        CACHE.add(new byte[1024 * 1024]);   // 用完也没有移除
    }
}
```

## 易错点
- 以为 Java 有垃圾回收就不会内存泄漏；对象仍被引用时，GC 不会回收
- 以为内存占用高就是泄漏；也可能是业务确实需要，要看 GC 后是否持续上涨
- 以为内存泄漏会立刻报错；它是慢慢累积的

## 追问
### [f1] ThreadLocal 为什么容易造成内存泄漏？
线程池里的线程会长期存活，线程对象一直引用着它的 ThreadLocal 数据。用完不调用 `remove()`，value 就一直留在里面无法回收。

### [f2] 怎么快速判断是否存在内存泄漏？
观察 Full GC 之后老年代的占用。如果每次回收后都比上一次更高，呈上升趋势，就很可能有泄漏，再用堆转储定位。
