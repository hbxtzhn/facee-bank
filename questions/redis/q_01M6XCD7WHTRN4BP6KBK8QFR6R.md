## 一句话
Redis 用惰性删除加定期删除两种方式清理过期 key，两者都没删掉、内存又不够时，由内存淘汰策略兜底。

## 要点
- [kp1|3] 惰性删除：访问某个 key 时才检查它是否过期，过期就删
- [kp2|3] 定期删除：每隔一段时间抽查一部分 key，删掉其中过期的
- [kp3|2] 惰性删除省 CPU，但没人访问的过期 key 会一直占内存
- [kp4|2] 定期删除限制每次的耗时和频率，避免拖慢主线程
- [kp5] 两种都漏掉时，靠内存淘汰策略释放空间

## 详解
### 先搞懂：过期的牛奶什么时候扔
冰箱里的牛奶有保质期。你可以：

- 每次要喝的时候看一眼，过期了就扔，不喝就不管；
- 或者每隔几天抽查几瓶，过期的就扔。

第一种省事，但冰箱里可能一直躺着过期的牛奶占地方。第二种能清理一些，但不可能每次把冰箱翻个遍，因为太费时间。Redis 两种方式一起用。

后文用到的术语：

- **TTL**：给 key 设置的存活时间，到点就算过期。
- **主线程**：Redis 处理命令的线程，耗时太久会阻塞所有请求。
- **内存淘汰**：内存不够时，按策略删除一些 key 腾出空间。

### 惰性删除：用到时再检查
访问某个 key 时，Redis 先检查它有没有过期，过期了就删除，并按「不存在」返回。

- 优点：只在需要时才检查，对 CPU 友好。
- 缺点：如果过期的 key 一直没人访问，就永远不会被删，一直占内存。

### 定期删除：隔一阵抽查一批
Redis 每隔一小段时间，从设置了过期时间的 key 里随机抽取一批检查，把过期的删掉。一次检查有时间和数量限制，避免占用主线程太久。

- 优点：能清理没人访问的过期 key，通过限制耗时降低对 CPU 的影响。
- 缺点：检查的频率和时长很难拿捏。太频繁、太久会影响正常请求，太少则过期 key 清理不及时。

### 为什么要两种配合
- 只用惰性删除：没人访问的过期 key 堆积，浪费内存。
- 只用定期删除：不可能每次扫完所有 key，总会有漏网之鱼，而且漏网之鱼被访问时还会返回过期数据。

配合后，被访问的 key 一定会在惰性删除时被检查，没人访问的 key 靠定期删除慢慢清理。

### 兜底：内存淘汰
即便这样，仍可能有大量过期 key 没被清理，加上新数据持续写入，内存会达到上限。这时由内存淘汰策略（如 `maxmemory-policy` 配置）选出一些 key 删除，释放空间。

## 易错点
- 以为 key 过期的那一刻就被删掉；实际可能延迟到被访问或被抽查到
- 以为定期删除会扫描所有 key；它只抽查一部分，并限制耗时
- 把过期删除和内存淘汰混为一谈；前者针对已过期的 key，后者是内存不足时的兜底

## 追问
### [f1] 内存淘汰策略有哪些？
常见的有 `noeviction`、`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-ttl`、`allkeys-random` 等。简单说，是在所有 key 还是只在设置了过期时间的 key 中，按最近最少使用、使用频率、剩余存活时间或随机选取淘汰。

### [f2] 过期的 key 在主从复制里怎么处理？
从节点自己不主动判断过期，由主节点删除 key 后，向从节点发送删除命令。这样保证主从数据一致。
