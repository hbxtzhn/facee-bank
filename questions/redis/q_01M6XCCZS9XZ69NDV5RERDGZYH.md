## 一句话
RDB 是把某一时刻的全部内存数据保存成一个 dump.rdb 文件；可以用 save 或 bgsave 手动触发，也可以用 `save 秒数 修改次数` 配置自动触发。

## 要点
- [kp1|3] RDB 保存的是某一时刻的数据快照，存成二进制文件，默认叫 dump.rdb
- [kp2|3] save 由主线程同步执行会阻塞请求，bgsave 由子进程后台执行
- [kp3|2] 配置 `save <秒数> <修改次数>`，时间内修改次数达到就自动触发
- [kp4] 正常关闭 Redis 时，如果配置了自动保存规则，也会生成一次 RDB

## 详解
### 先搞懂：给数据拍一张照片
快照就像给某一刻的数据拍照：拍完之后，照片不会随数据变化。Redis 把内存里的所有数据照下来，写进一个文件。出了故障，用这张照片就能恢复到拍照那一刻的样子。

后文用到的词：
- **RDB**：Redis 的快照持久化方式，产物是 dump.rdb 文件。
- **持久化**：把内存数据保存到磁盘，重启后还能找回来。

### 手动触发：save 和 bgsave
- `save`：主线程自己写文件，写完才返回。写的过程中所有客户端请求都得等，数据多时会卡很久，一般不在生产环境用。
- `bgsave`：先 fork 出一个子进程，由子进程写文件，主线程继续处理请求。命令几乎马上返回，生产环境用它。

### 自动触发：配置文件里的规则
在 redis.conf 里可以写：

```conf
save 60 10000
```

意思是：60 秒内至少有 10000 次修改，就自动做一次快照。这条指令可以写多条，满足任意一条就触发。自动触发用的是后台方式，和 bgsave 一样由子进程完成。

### 其他会产生 RDB 的场景
- 正常执行 `SHUTDOWN` 时，如果配置了保存规则，会先做一次快照再退出；
- 主从复制时，主节点给从节点做全量同步，也会生成 RDB。

### 优缺点一句话
RDB 文件紧凑、恢复快，适合备份。但两次快照之间的修改，宕机时会丢失。

## 示例
```bash
redis-cli save      # 同步保存，会阻塞
redis-cli bgsave    # 后台保存
redis-cli lastsave  # 查看最近一次成功保存的时间戳
```

## 易错点
- 以为 save 和 bgsave 效果一样；save 会阻塞所有请求
- 以为快照是实时的；它只反映触发那一刻的数据，之后的写入不在里面

## 追问
### [f1] 自动触发的 `save 900 1` 是什么意思？
900 秒内至少有 1 次修改就触发快照。数字越小触发越频繁，丢数据的窗口更小，但写磁盘更多。具体默认值随 Redis 版本不同，以所用版本的配置文件为准。
