## 一句话
JVM 用可达性分析判断垃圾：从 GC Roots 出发顺着引用往下找，找不到的对象就是垃圾。引用计数算法有循环引用问题，所以 JVM 不用它。

## 要点
- [kp1|3] 可达性分析：从 GC Roots 出发沿引用链搜索，不可达的对象判定为垃圾
- [kp2|3] 引用计数：对象记录被引用次数，次数为 0 即垃圾
- [kp3|2] 引用计数处理不了循环引用，两个对象互相引用时计数永远不为 0
- [kp4] 局部变量、静态变量等可以作为 GC Roots

## 详解
### 先搞懂：怎么判断一个人还要不要这个座位
继续用自习室的类比：怎么知道一个座位上的东西没人要了？

- **办法一：数人头**。每个座位记录「有几个人说这是我的」，数到 0 就清走。
- **办法二：顺藤摸瓜**。从几个肯定有人的地方（门口登记处）出发，顺着「谁认识谁」一路找，找得到的座位是有人用的，找不到的就是没人要的。

办法一是引用计数，办法二是可达性分析。

后文用到的术语：

- **引用**：一个对象保存着另一个对象的地址，比如 `a.next = b`。
- **GC Roots**：一组肯定活着的起点，如栈里的局部变量、类的静态变量。
- **引用链**：从 GC Roots 走到某个对象所经过的引用路径。

### 引用计数：每个对象记自己被引用几次
每多一个地方引用它，计数加一；引用失效，计数减一；减到 0 就回收。优点是简单，回收及时。

问题在循环引用：

```java
class Node { Node other; }
Node a = new Node();
Node b = new Node();
a.other = b;
b.other = a;
a = null;
b = null;
```

最后两个变量都置空了，外面再也没人能访问这两个对象，但它们互相引用，计数各自是 1，永远不会变成 0，于是回收不掉。

### 可达性分析：从 GC Roots 往下找
HotSpot 采用这种办法：

1. 以 GC Roots 为起点，沿着引用往下遍历，给走到的对象打上标记。
2. 遍历结束后，没被标记的对象就是不可达的，判定为垃圾。

刚才的循环引用在这里不构成问题：两个对象之间虽然互相指，但没有任何一条链能从 GC Roots 走到它们，所以仍然被判为垃圾。

### 方案对比：两种判断方式
| 方案 | 怎么判断 | 优点 | 缺点 | JVM 是否采用 |
|---|---|---|---|---|
| 引用计数 | 被引用次数为 0 | 实现简单，对象一没人用就能发现 | 循环引用回收不了，每次改引用都要更新计数 | 否 |
| 可达性分析 | 从 GC Roots 不可达 | 能处理循环引用 | 要遍历对象图，需要配合停顿或并发标记 | 是 |

结论：JVM 用可达性分析；引用计数只适合引用关系简单、不会成环的场景。

### 进阶：不可达也不是立刻回收（基础薄弱可先跳过）
- 对象第一次被判定不可达时，如果它重写了 `finalize()`，还有一次被「抢救」的机会；`finalize()` 已被弃用，不应依赖。
- Java 的引用分强、软、弱、虚四种，只有强引用能阻止对象被回收，软引用和弱引用的对象在可达性分析中有特殊处理。

## 易错点
- 以为对象被 null 就立刻回收；只是变成不可达，回收时机由 GC 决定
- 以为 Java 用引用计数；HotSpot 用的是可达性分析
- 以为互相引用的对象就回收不了；只要不能从 GC Roots 到达，就会被回收

## 追问
### [f1] 哪些对象可以作为 GC Roots？
常见的有：虚拟机栈里的局部变量引用、类的静态变量、JNI 引用，以及仍在运行的线程等。

### [f2] 可达性分析会不会误判存活的对象？
如果分析时应用线程还在修改引用，可能判错，所以标记阶段要么暂停应用线程，要么用专门的并发标记机制修正。
