## 一句话
解释执行是逐条翻译字节码，启动快但执行慢；JIT 把热点代码编译成机器码，编译要花时间，但之后执行快。HotSpot 两者配合：先解释，变热再编译。

## 要点
- [kp1|3] 解释器逐条翻译执行字节码，不需要等待，启动快但每次执行都要翻译
- [kp2|3] JIT 把热点代码整体编译成机器码，编译有开销，之后重复执行快
- [kp3|2] HotSpot 先解释执行，统计出热点后再交给 JIT 编译
- [kp4|2] 分层编译：先 C1 快速编译，再对更热的代码用 C2 深度优化
- [kp5] 程序要预热一阵才能达到稳定性能

## 详解
### 先搞懂：口译和提前翻译稿
去国外开会，你可以请一个口译员：对方说一句，他翻一句，马上就能开始沟通，但每句话都要现翻，速度有上限。另一种办法是把要反复说的内容提前翻成稿子，之后直接念稿，速度快得多，代价是写稿要花时间。

解释执行就是口译，JIT 编译就是写稿。如果一段话只说一次，口译更划算；要说上万遍，写稿更划算。

后文用到的术语：

- **字节码**：javac 生成的指令，和具体 CPU 无关。
- **机器码**：CPU 能直接执行的指令。
- **热点代码**：被反复执行的方法或循环。

### 解释执行：马上能跑，但一直慢
解释器读到一条字节码，就去执行对应的一小段本地逻辑，然后读下一条。优点是不需要等待编译，程序启动立刻就能跑，也占内存少。缺点是每次执行同一段代码，都要重复翻译一遍，反复执行时开销累积得很明显。

### JIT 编译：先花时间，换来后面更快
JIT 把一整个方法（或一个热点循环）一次性编译成机器码，保存在代码缓存里。以后再执行就直接运行机器码，不再翻译。编译时还能做优化，比如把小方法直接展开到调用处。缺点是编译要占用 CPU 和内存，刚启动时来不及编译，所以启动阶段偏慢。

### 方案对比：两种执行方式
| 方式 | 启动速度 | 长期运行速度 | 额外开销 | 适合 |
|---|---|---|---|---|
| 解释执行 | 快，立刻开始 | 较慢，重复翻译 | 内存占用小 | 刚启动的代码、只执行几次的代码 |
| JIT 编译 | 慢，要先编译 | 快，直接跑机器码 | 编译占 CPU 和内存 | 反复执行的热点代码 |

结论：两者不是二选一。HotSpot 默认先解释执行，运行中发现热点再编译，用解释器换启动速度，用 JIT 换长期速度。

### HotSpot 里怎么配合
1. 代码一开始由解释器执行，同时虚拟机记录方法调用次数和循环回边次数。
2. 次数达到阈值，说明变热了，提交给 JIT 编译。编译在后台线程做，编译期间程序继续解释执行。
3. 编译完成后，之后的调用直接进入机器码。
4. 采用分层编译：先由 C1 快速编译，较快得到一份够用的机器码；继续变热的代码再交给 C2，做更深入的优化。

### 进阶：编译后也可能退回解释（基础薄弱可先跳过）
- JIT 有时会基于运行中的观察做乐观假设，比如某个接口调用点一直只有一种实现，就直接按这种实现优化。后来假设不成立（又加载了新的实现类），虚拟机会丢弃这份机器码，退回解释执行，之后可能再重新编译。这叫去优化。
- 长时间运行的循环被发现很热时，JIT 可以在循环中途切换到编译后的版本，这叫栈上替换（OSR）。

## 易错点
- 以为 JIT 一定比解释执行好；只执行几次的代码，编译的成本比省下的时间还多
- 以为编译完成后就一直用机器码；假设失效时会退回解释执行
- 以为 Java 程序性能从一开始就是稳定的；需要预热

## 追问
### [f1] 为什么不一开始就把所有代码都编译掉？
编译要花 CPU 和内存，会拖慢启动，而且大部分代码只执行一两次，编译不划算。只编译热点代码，是在启动速度和长期速度之间取的平衡。

### [f2] 为什么 HotSpot 有 C1 和 C2 两个编译器？
C1 编译快，能让代码尽快提速；C2 优化深，生成的代码更快但编译慢，只用于最热的代码。分层编译把两者结合，兼顾预热速度和最终性能。
