## 一句话
哈希索引基于哈希表，等值查询（`=`、`IN`）很快，但不能做范围查询和排序；InnoDB 不允许手动创建哈希索引。

## 要点
- [kp1|3] 哈希索引基于哈希表，按键算出位置，等值查询一步定位
- [kp2|3] 只适合 `=` 和 `IN`，不支持范围查询（`BETWEEN`、`大于`、`小于`）
- [kp3|2] 哈希值是无序的，不能用来排序
- [kp4] InnoDB 不能手动建哈希索引，Memory 引擎支持

## 详解
### 先搞懂：按编号直接取快递
快递柜里，每个包裹都有取件码，输入取件码，柜子就直接打开对应的格子，不需要一格一格找。

哈希索引就是这样：把查询的值算一下，得到一个位置，直接去取。算位置的函数叫哈希函数。

后文用到的术语：

- **哈希表**：用哈希函数把键映射到存放位置的数据结构；
- **等值查询**：条件是 `=` 或 `IN`；
- **范围查询**：条件是「大于某值」「在某区间」。

### 为什么等值查询快
哈希表按键直接计算出位置，通常不需要像树那样一层层往下找，所以等值查询很快。

### 为什么不适合范围查询
哈希函数会把相近的值打散到毫不相关的位置，值的大小顺序没有保留下来。

- 想查 `age` 在 20 到 30 之间的人，没法找出一个连续的区域，只能逐个检查；
- 也不能用它来做 `ORDER BY` 排序。

B+ 树则不同，叶子节点有序，对范围查询和排序都友好。

### InnoDB 和哈希索引
InnoDB 不提供让你手动创建哈希索引的选项，因为 B+ 树已经能同时很好地支持等值和范围查询。Memory 引擎支持哈希索引。InnoDB 内部有一个自适应哈希索引的机制，由引擎自动管理，不由用户创建。

## 示例
```sql
CREATE TABLE t_cache (
    k VARCHAR(50),
    v VARCHAR(200),
    INDEX USING HASH (k)
) ENGINE = MEMORY;
```

## 易错点
- 以为哈希索引范围查询也快；它只适合等值查询
- 以为在 InnoDB 里可以用 `USING HASH` 创建哈希索引；InnoDB 不支持手动创建
- 以为哈希索引可以用来排序；哈希值是无序的

## 追问
### [f1] 哈希索引的缺点还有哪些？
不同的键可能算出同一个位置，叫哈希冲突，冲突多了会变慢。另外它不能用于最左前缀匹配，只能整个键匹配。

### [f2] 为什么 MySQL 索引默认用 B+ 树而不是哈希？
业务里既有等值查询，也有范围查询和排序。B+ 树都能支持，哈希只能支持等值。
