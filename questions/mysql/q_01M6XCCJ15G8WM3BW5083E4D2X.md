## 一句话
`SELECT *` 会把用不到的列也读出来、传出去，浪费 IO 和网络，还可能让本来能只靠索引完成的查询多一次回表。

## 要点
- [kp1|3] `SELECT *` 会多读用不到的列，增加磁盘 IO 和网络传输
- [kp2|3] 只查需要的列，有机会命中覆盖索引，省掉回表
- [kp3|2] 表结构新增列后，`SELECT *` 的结果会悄悄变化，容易影响代码
- [kp4] 大字段如 TEXT 被一起读出来时，代价更明显

## 详解
### 先搞懂：点菜只点要吃的
去餐厅，你只想吃一道菜，却把整本菜单上的菜都点一遍，浪费钱，厨房也累。`SELECT *` 就是把所有列都点了，哪怕代码里只用到其中两列。

后文用到的术语：

- **回表**：通过索引找到主键后，再回到完整数据行里取其他列。
- **覆盖索引**：查询需要的列都在索引里，不用回表。
- **IO**：读写磁盘。

### 问题一：多读了数据，白白浪费
- 数据库要把每一列都从存储里读出来，列越多、越大，IO 越多；
- 这些数据还要通过网络发给应用，占用带宽；
- 应用拿到后，大部分列根本没用，白白占内存。

如果表里有 `TEXT` 之类的大字段，影响更明显。

### 问题二：可能错过覆盖索引
假设有索引 `idx_name(name)`，而主键是 `id`。InnoDB 的二级索引里自带主键值，所以：

- `SELECT id, name FROM user WHERE name = '张三'`：需要的列都在索引里，不用回表；
- `SELECT * FROM user WHERE name = '张三'`：要取所有列，必须回表读完整的行。

两条语句找的是同一批行，但后一条多做了回表这一步。

### 问题三：表结构一变，结果也跟着变
`SELECT *` 的结果取决于表当时有什么列。别人给表加了一列，你的代码拿到的结果就多了一列；按列位置取值的代码，还可能错位。明确写出列名，更稳定也更清楚。

### 什么时候用也没问题
临时在命令行里随手看看数据、表很小的时候，用 `SELECT *` 很方便。关键是写进业务代码和高频查询的语句，要写明列名。

## 示例
```sql
-- 不推荐：取出所有列
SELECT * FROM user WHERE name = '张三';

-- 推荐：只取需要的列；若 (name) 上有索引，可能直接用索引完成
SELECT id, name FROM user WHERE name = '张三';
```

## 易错点
- 以为 `SELECT *` 只是写法懒，对性能没影响；多读的列和多出的回表都有成本
- 以为只查两列就一定走覆盖索引；还要看这两列是否都在某个索引里
- 以为列越少越好，就把一次查询拆成很多次；次数多了，往返开销反而更大

## 追问
### [f1] 怎么确认查询用上了覆盖索引？
用 `EXPLAIN` 看 `Extra` 列。如果出现 `Using index`，说明只读索引就拿到了所有需要的列，没有回表。
