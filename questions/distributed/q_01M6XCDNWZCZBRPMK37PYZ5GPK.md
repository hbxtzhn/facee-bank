## 一句话
突发的大量请求先写进消息队列排队，后端消费者按自己的处理能力慢慢取，这样流量高峰就被“削平”，后端不会被冲垮。

## 要点
- [kp1|3] 突发请求先写入队列暂存，不直接打到后端
- [kp2|3] 消费者按自己的处理能力取消息，节奏平稳
- [kp3|2] 适合秒杀、促销这类短时间流量暴涨的场景
- [kp4] 代价是处理会有延迟，队列本身也要扛得住写入

## 详解
### 先搞懂：景区检票口
节假日景区门口，一万人同时涌来，但检票口一分钟只能放过一百人。如果让所有人一起挤进去，闸机会被挤坏。景区的做法是在门口拉出蜿蜒的队伍，大家排队，检票口按自己的速度一个个放人。

消息队列削峰就是这个蜿蜒的队伍。先说两个词：

- **流量峰值**：短时间内突然涌来的大量请求。
- **削峰**：把短时间的高峰，拉平成较长时间内的平稳流量。

### 没有队列时会发生什么
秒杀开始的一瞬间，请求数是平时的几十倍。这些请求直接打到订单服务和数据库，后端处理不过来，响应变慢，线程被占满，严重时服务直接崩溃。

### 加上队列后怎么做
1. 请求进来后，先做必要的校验，然后把请求写进消息队列；
2. 接口立刻告诉用户“已收到，处理中”；
3. 后端的消费者按自己的处理能力，一批一批从队列取消息处理；
4. 高峰过后，队列里堆积的消息会逐渐被消化完。

这样，后端面对的始终是它能承受的压力，高峰流量由队列这一层扛住了。

### 要注意什么
- **有延迟**：高峰期用户的请求要排队，结果不会马上出来，需要配合状态查询或通知；
- **队列要扛得住**：队列本身的写入能力要大于峰值流量，并且要设置容量上限；
- **配合限流**：队列再大也不是无限的，流量远超预期时，要在入口拒绝一部分请求。

## 示例
```java
// 伪代码：秒杀请求先入队，由消费者慢慢处理
public String seckill(long userId, long itemId) {
    mq.send("seckill-topic", userId + ":" + itemId);
    return "排队中，请稍后查看结果";
}
```

## 易错点
- 以为队列能让后端变快；它只是让后端按稳定的速度工作，总处理时间没有减少
- 以为队列可以无限堆积；积压太多会占满磁盘或让消息等待过久

## 追问
### [f1] 队列积压了很多怎么办？
先看消费者慢在哪，可以增加消费者实例、调大批量。如果积压的是已过期的请求，可以直接丢弃，同时在入口做限流，防止继续堆积。
