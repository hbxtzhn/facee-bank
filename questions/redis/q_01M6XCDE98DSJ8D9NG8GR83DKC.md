## 一句话
MULTI 之后的命令只入队不执行，EXEC 时按顺序一次执行完；用 WATCH 盯住的 key 被别人改过，EXEC 就整体放弃。

## 要点
- [kp1|3] MULTI 开启事务，之后的命令只放进队列，不立即执行
- [kp2|3] EXEC 按入队顺序执行，期间不会插入其他客户端的命令
- [kp3|2] WATCH 的 key 在 EXEC 前被改动，EXEC 返回空，队列全部不执行
- [kp4|2] 命令运行时出错不会回滚，已执行的命令照样生效
- [kp5] DISCARD 可放弃队列，入队时的语法错误会让 EXEC 直接失败

## 详解
### 先搞懂：事务像一张打包下单的购物清单
做项目时常见这样的需求：给用户加积分，同时记一条流水。两条命令分开发，中间可能被别的请求插进来。

可以把 Redis 事务想成交给收银员的一张清单：你先把要买的东西逐条写好，写的时候收银员不动手；最后说一声“结账”，收银员连续扫完整张清单，中途不接待别人。

后文会用到几个词：

- **入队**：命令被记在队列里，还没执行。
- **EXEC**：告诉 Redis 开始执行整个队列。
- **WATCH**：先盯住某些 key，用来判断别人有没有改过它们。

### MULTI 到 EXEC：先排队，再一口气执行
一个事务分三步：

1. 发 `MULTI`，Redis 回复 OK，进入事务状态。
2. 之后每发一条命令，Redis 只回复 `QUEUED`，命令被放进队列。
3. 发 `EXEC`，Redis 按顺序执行队列里的命令，把所有结果一起返回。

执行队列的这段时间里，Redis 不会去处理别的客户端的命令。所以事务里的几条命令中间不会被别人插进来，这是它说的“原子”的含义。

如果中途不想执行了，发 `DISCARD`，队列被清空，事务结束。

### 出错的处理：没有回滚
这是最容易误解的地方，要分两种情况看：

- **入队时出错**（比如命令名写错、参数个数不对）：Redis 会记下这个错误，之后 `EXEC` 直接拒绝整个事务，一条都不执行。
- **执行时出错**（比如对字符串 key 执行列表命令）：只有这一条返回错误，前后的命令照常执行，已经改的数据不会撤销。

所以 Redis 事务保证的是“不被打断”，不是关系型数据库那种“失败就回滚”。

### WATCH：用乐观锁防止基于旧值修改
场景：先读余额，在程序里算出新值，再写回。读和写之间余额可能被别人改了。

做法是：

1. `WATCH balance` 盯住这个 key；
2. 读出余额，开启 `MULTI`，把写入命令入队；
3. `EXEC` 时，Redis 检查被盯的 key 有没有被其他客户端修改过。

改过，`EXEC` 返回空结果，队列里的命令一条都不执行，由程序决定重试。没改过，就正常执行。这种“不加锁，冲突了再重试”的做法叫乐观锁。`EXEC` 或 `DISCARD` 之后，WATCH 自动取消。

### 进阶：和 Lua 脚本的取舍（基础薄弱可先跳过）
- 事务里的命令不能依赖前一条的结果，因为入队时还没有结果。需要“读了再判断再写”时，用 WATCH 加重试，或者直接写成 Lua 脚本一次执行。
- 脚本可以在服务端完成判断和写入，不需要来回重试，所以这类需求更常用脚本。

## 示例
```bash
WATCH balance
GET balance
MULTI
DECRBY balance 10
INCRBY points 10
EXEC
# 若 balance 在 WATCH 之后被别人改过，EXEC 返回 (nil)，两条命令都不执行
```

## 易错点
- 以为 EXEC 失败会回滚；命令执行时出错，其他命令照样生效
- 以为 MULTI 之后命令马上执行；其实只是入队，EXEC 才执行
- 以为 WATCH 会给 key 上锁；它不阻止别人修改，只是让 EXEC 失败
- 以为事务内可以根据前一条命令的结果做判断；入队阶段拿不到结果

## 追问
### [f1] WATCH 的 key 被改了，EXEC 会返回什么？
返回空结果（nil），队列里的命令全部不执行。程序需要自己重新读取数据、重新开事务，通常循环重试几次。

### [f2] Redis 事务和 MySQL 事务有什么区别？
Redis 事务只保证命令连续执行、不被打断，没有回滚。MySQL 事务有完整的回滚和隔离级别。
