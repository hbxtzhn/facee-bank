## 一句话
哨兵是一组专门盯着 Redis 主从的守护进程：监控节点是否正常，主节点挂了自动选新主，并告诉客户端新地址。

## 要点
- [kp1|3] 哨兵本身不存业务数据，只负责监控和决策
- [kp2|3] 主节点故障时，哨兵自动把一个从节点升级为新主节点
- [kp3|2] 客户端连哨兵询问当前主节点地址，主从切换后无需改配置
- [kp4] 哨兵要部署多个，避免哨兵自己成为单点

## 详解
### 先搞懂：为什么需要有人盯着主节点
假设你的网站用 Redis 做缓存，一主两从。某天主节点宕机，没人处理的话，所有写请求都会失败。运维半夜起床手动把一个从节点提升为主节点，再改应用配置，既慢又容易出错。

可以把哨兵想成小区的保安队：他们不负责住户的生活（不存数据），只负责巡逻。发现大楼出事，保安们商量好谁来处理，并通知所有住户新的出入口。

后文用到几个词：

- **主节点**：负责写数据的 Redis 实例。
- **从节点**：复制主节点数据的副本，平时可以读。
- **故障转移**：主节点出问题后，换一个从节点当新主节点。

### 哨兵做的三件事
- **监控**：哨兵不断检查主节点、从节点是否正常响应。
- **自动故障转移**：哨兵确认主节点真的不可用后，会选出一个从节点升级为新主节点。其他从节点改为复制新主节点。
- **配置提供者**：客户端启动时不直接写死主节点地址，而是问哨兵“现在谁是主节点”。故障转移后，哨兵也会把新地址告诉客户端。

### 为什么要多个哨兵
如果只有一个哨兵，它自己挂了，就没人监控了。而且单个哨兵可能因为自己的网络问题，误以为主节点挂了。

所以哨兵通常部署三个或更多，并且用奇数个。多个哨兵互相确认，大多数同意后才会真正切换主节点。

## 示例
```bash
# 向哨兵询问名为 mymaster 的主节点当前地址
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
```

## 易错点
- 以为哨兵会存数据或分担读写；哨兵只做监控和决策
- 以为一个哨兵就够了；单个哨兵既可能误判，自己挂了也没人接替
- 以为哨兵能把数据分片；它只解决高可用，不解决容量问题

## 追问
### [f1] 哨兵和 Redis Cluster 有什么区别？
哨兵解决的是主从架构的高可用，数据仍然在一个主节点上。Cluster 把数据分片到多个主节点，同时自带故障转移。
