## 一句话
指令重排序是编译器和 CPU 为了跑得更快，在不改变单线程结果的前提下，调整代码的实际执行顺序；多线程下，别的线程可能因此看到不符合代码书写顺序的中间状态。

## 要点
- [kp1|3] 重排序是编译器和 CPU 为提高效率做的优化，不是 bug
- [kp2|3] 重排序必须保证单线程执行结果不变，没有数据依赖的语句才可能被调换
- [kp3|2] 多线程下，其他线程可能看到先后顺序被打乱的结果
- [kp4] 用 volatile、synchronized 等手段可以限制重排序

## 详解
### 先搞懂：厨师为什么会换着做菜
你在餐厅点了两道菜：一道炖汤要 30 分钟，一道凉菜 1 分钟。聪明的厨师不会傻等汤炖好再切凉菜，而是先把汤放上火，趁炖的时候做凉菜。最后菜都上齐了，结果和按顺序做一样，但实际做菜的顺序已经变了。

编译器和 CPU 就像这位厨师：只要两件事互不依赖，换个顺序做更省时间，它们就会换。对一个人（单线程）来说，最终端上桌的菜没区别；但如果旁边有另一个人（另一个线程）在偷看厨房，他可能先看到凉菜做好了、汤还没开始炖。

后文用到的词：

- **重排序**：实际执行的顺序和代码书写的顺序不一致。
- **数据依赖**：后一条语句要用前一条语句的结果，比如先 `a = 1` 再 `b = a + 1`，这种不能换。
- **可见性**：一个线程写的值，别的线程能不能及时看到。

### 重排序发生在哪些环节
从代码到真正执行，有三个环节可能调整顺序：编译器生成指令时、CPU 同时执行多条指令时、CPU 通过缓存和写缓冲读写内存时。这三类在下一道题里会细讲，这里只要记住：它们都遵守同一条底线，就是不能改变单线程程序的结果。

### 为什么单线程没事、多线程有事
下面两行没有数据依赖：

```java
data = 42;      // 1
ready = true;   // 2
```

单线程里谁先谁后都一样，所以可能被调换。但如果另一个线程这样写：

```java
if (ready) { use(data); }
```

那么当 2 先于 1 生效时，它看到 `ready` 为 true，却读到旧的 `data`。这就是重排序带来的多线程问题。

### 怎么限制重排序
Java 内存模型规定了一套规则（叫 happens-before，即「前一个操作的结果对后一个操作可见」）。遵守这些规则的操作，重排序不会让你看到错乱的结果。常用手段有：

- 给变量加 `volatile`，限制它前后的重排序；
- 用 `synchronized` 或 `Lock`，加锁解锁之间的操作对下一个拿锁的线程可见；
- 使用线程启动、`join` 等规则保证的顺序。

经典例子是双重检查单例：创建对象的几个步骤被调换后，别的线程可能拿到一个还没初始化好的对象，所以实例要加 `volatile`。

## 示例
```java
class Demo {
    int data = 0;
    volatile boolean ready = false; // 加 volatile 后，data 的写入不会被重排到它之后

    void writer() {
        data = 42;
        ready = true;
    }

    void reader() {
        if (ready) {
            System.out.println(data); // 能保证看到 42
        }
    }
}
```

## 易错点
- 以为重排序会让单线程程序结果出错；规则保证单线程结果不变
- 以为代码写在前面就一定先执行；没有数据依赖时，实际顺序可能被调整
- 以为重排序只是编译器干的；CPU 和内存系统同样会调整顺序

## 追问
### [f1] 什么情况下两条语句不会被重排？
存在数据依赖时不会被重排，例如后一条要读前一条写入的值。另外，用 volatile、锁等建立了 happens-before 关系的操作，重排序也不能破坏它们的可见性保证。
