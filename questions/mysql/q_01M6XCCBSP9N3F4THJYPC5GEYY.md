## 一句话
不是。索引能加快查询，但每个索引都占磁盘，增删改时还要同步维护，建得越多，写入越慢。

## 要点
- [kp1|3] 每个索引是一棵独立的树，都要占磁盘空间
- [kp2|3] 增删改数据时，所有相关索引都要同步更新，写入变慢
- [kp3|2] 索引太多时，优化器要多评估几种方案，也可能选错
- [kp4] 建索引要对应真实查询，没人用的索引应该删掉

## 详解
### 先搞懂：目录越多，翻书越累
一本书有一个目录很方便。但如果同一本书做了十个不同的目录，每次改一页内容，十个目录都要重新对一遍，纸张也多用了不少。

几个术语：

- **索引维护**：数据变化后，把索引里对应的内容一起改掉。
- **优化器**：MySQL 里负责决定一条查询走哪个索引的组件。

### 索引多了有什么代价
1. **占磁盘和内存**：每个索引都有自己的 B+ 树，数据多时占的空间不小，缓存里能放的有用数据变少。
2. **拖慢写入**：插入一行，要往每个索引里各插一条；改了某列，包含这列的索引都要调整；删除也一样。
3. **增加选择成本**：查询时优化器要在多个候选索引里挑一个，候选越多，评估越费事，偶尔还会选了不理想的那个。

### 怎么控制索引数量
- 以实际的查询为依据，只建真正用得到的索引；
- 能用联合索引覆盖多个查询条件时，不要拆成很多单列索引；
- 定期检查，把长期没人用的、被其他索引包含的重复索引删掉；
- 读多写少的表可以多建一些，写多读少的表要更克制。

## 示例
```sql
-- 已有联合索引 (user_id, status)，单独的 idx_user 通常是多余的
CREATE INDEX idx_user_status ON orders(user_id, status);
-- CREATE INDEX idx_user ON orders(user_id);  -- 重复，可以不建
```

## 易错点
- 以为每一列都建索引最保险；写入变慢、空间变大，得不偿失
- 以为索引对读写都有利；索引只加速读，写入一定要多做事
- 以为建了索引就一定会被使用；优化器可能判断全表扫描更划算

## 追问
### [f1] 什么情况下索引是多余的？
最常见的是被联合索引的最左前缀包含，例如已有 `(a, b)`，再建单列 `(a)` 通常就多余了。
