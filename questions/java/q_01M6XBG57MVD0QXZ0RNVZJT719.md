## 一句话
gRPC 基于 HTTP/2 传输、用 Protocol Buffers 序列化，天然跨语言；Dubbo 是 Java 生态的 RPC 框架，自带服务治理，协议和序列化可以配置选择。

## 要点
- [kp1|3] gRPC：HTTP/2 传输，Protocol Buffers 序列化，通过 .proto 文件定义接口
- [kp2|3] Dubbo：阿里开源，以 Java 为主，提供服务注册发现、负载均衡等治理能力
- [kp3|2] Dubbo 的协议和序列化方式可配置，不是固定一种
- [kp4|2] gRPC 适合跨语言的服务间调用，Dubbo 适合 Java 微服务体系
- [kp5] 二者都屏蔽了底层网络细节，业务只写接口和实现

## 详解
### 先搞懂：同样是寄快递，规格不一样
RPC 框架都在做一件事：帮你把调用打包、送到对端、再拆开。区别在于：用什么“快递公司”送（传输协议），用什么“包装规则”打包（序列化），以及送货之外附带什么服务（服务治理）。

后文术语：
- **传输协议**：数据在网络上怎么传。
- **序列化**：对象怎么变成字节。
- **服务治理**：服务注册发现、负载均衡、限流熔断等管理能力。
- **IDL**：接口定义语言，用一个中立的文件描述接口，再生成各语言代码。

### gRPC：跨语言优先
- 传输：基于 HTTP/2；
- 序列化：默认使用 Protocol Buffers，一种二进制格式，体积小；
- 接口：先写 `.proto` 文件，用工具生成各语言的客户端和服务端代码，所以不同语言的服务能互相调用。

### Dubbo：Java 微服务体系
- 阿里开源，最初面向 Java 服务；
- 内置服务注册发现、负载均衡、容错等治理能力，通常配合注册中心使用；
- 协议和序列化可以选择，具体支持哪些以所用版本的官方文档为准。

### 方案对比：gRPC 与 Dubbo
| 框架 | 传输协议 | 序列化 | 语言 | 适合 |
|---|---|---|---|---|
| gRPC | HTTP/2 | Protocol Buffers | 多语言 | 跨语言服务间调用 |
| Dubbo | 可配置（有自己的协议） | 可配置 | 以 Java 为主 | Java 微服务，需要治理能力 |

结论：团队服务用多种语言、需要统一接口定义时优先选 gRPC；全是 Java 微服务、希望开箱即用服务治理时选 Dubbo。具体以团队技术栈和现有基础设施为准。

### 选择时看什么
- 要不要跨语言：要，倾向 gRPC；
- 是否需要成熟的服务治理：Dubbo 内置较完整；
- 团队现有技术栈：已经有的基础设施往往比理论优劣更重要。

## 易错点
- 以为 gRPC 只能用 Protocol Buffers；这是默认和最常用的方式，不代表唯一
- 以为 Dubbo 固定使用某一种协议和序列化；它们可以配置
- 以为 RPC 框架性能的比较有统一答案；要在自己的场景压测

## 追问
### [f1] 为什么 gRPC 要先写 .proto 文件？
.proto 用中立的方式描述接口和数据结构，工具据此为各种语言生成代码，这样不同语言的服务才能按同一份约定通信。
