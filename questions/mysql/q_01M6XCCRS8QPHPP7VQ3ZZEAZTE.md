## 一句话
意向锁是加在表上的锁，表示「这个事务正要或已经在表里的某些行上加锁」。别人要锁整张表时，看一眼意向锁就够了，不用逐行检查。

## 要点
- [kp1|3] 意向锁是表级锁，分意向共享锁 IS 和意向排他锁 IX
- [kp2|3] 加行锁之前，InnoDB 会先在表上加对应的意向锁
- [kp3|2] 加表锁时只看意向锁，不用遍历所有行判断是否有行锁
- [kp4] 意向锁之间互相兼容，只和表级的 S、X 锁冲突
- [kp5] 和插入意向锁是两回事

## 详解
### 先搞懂：酒店前台怎么知道能不能包下整层楼
酒店有一层楼的很多房间。有的客人订了个别房间。现在来了一个团队，想包下整层楼。

前台怎么判断能不能包？

- 没有任何标记：要一间一间房去查有没有人住；
- 每个客人入住时，在前台的登记本上写一笔「这层楼有人住」：团队来了，看登记本一眼，就知道不能包整层。

意向锁就是这个登记本。后文会用到这几个词：

- **多粒度锁**：表锁和行锁同时存在的锁体系。
- **意向共享锁（IS）**：表示「我要在某些行上加共享锁」。
- **意向排他锁（IX）**：表示「我要在某些行上加排他锁」。

### 问题：表锁和行锁怎么共存
InnoDB 既有行锁，也允许加表锁（如 `LOCK TABLES ... WRITE`）。

事务 A 已经锁了表里的某一行。这时事务 B 想给整张表加排他锁，必须先判断：表里有没有行被别人锁着？

如果没有意向锁，只能遍历全表所有行，逐行检查有没有行锁，成本很高。

### 意向锁的做法
1. 事务 A 想给某行加共享锁，先在**表**上加意向共享锁（IS），再在行上加 S 锁；
2. 想给某行加排他锁，先在表上加 IX，再在行上加 X 锁；
3. 事务 B 要加表锁时，只需要检查表上有没有冲突的意向锁，一次判断就够了。

### 兼容关系
| 已持有 \ 想加 | IS | IX | S | X |
|---|---|---|---|---|
| IS | 兼容 | 兼容 | 兼容 | 冲突 |
| IX | 兼容 | 兼容 | 冲突 | 冲突 |
| S | 兼容 | 冲突 | 兼容 | 冲突 |
| X | 冲突 | 冲突 | 冲突 | 冲突 |

规律：意向锁之间互相兼容，因为它们只是「我要在某些行上加锁」的声明，真正的冲突在行上判断。意向锁只会挡住想锁整张表的请求。

### 谁来加
意向锁由 InnoDB 自动加，不需要手写。普通的 `SELECT ... FOR UPDATE`、`UPDATE` 等语句会自动在表上加 IX，在行上加 X。

## 示例
```sql
-- 事务 A：锁住一行，同时表上自动加了 IX
START TRANSACTION;
SELECT * FROM account WHERE id = 1 FOR UPDATE;

-- 事务 B：想锁整张表，与 A 的 IX 冲突，会等待
LOCK TABLES account WRITE;
```

## 易错点
- 把意向锁和插入意向锁混淆；前者是表级锁，后者是间隙上的锁
- 以为两个 IX 会互相阻塞；意向锁之间是兼容的
- 以为意向锁会阻塞行级操作；它只挡表级的 S、X 请求

## 追问
### [f1] 为什么意向锁之间不冲突？
意向锁只表示「打算在某些行上加锁」。真正会不会冲突，要看具体的行。不同事务锁不同的行，完全可以同时进行，所以表上的意向锁不需要互相阻塞。
