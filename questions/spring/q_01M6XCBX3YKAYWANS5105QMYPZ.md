## 一句话
物理分页就是让数据库自己完成分页：在 SQL 里写 limit、offset 之类的分页条件，数据库只返回当前页的数据。

## 要点
- [kp1|3] 物理分页由数据库执行，返回结果里只有当前页的数据
- [kp2|3] 可以在 SQL 里直接写分页语法，MySQL 常用 `limit` 加 `offset`
- [kp3|2] 也可以用分页插件，自动把原 SQL 改写成分页 SQL
- [kp4] 不同数据库分页语法不同，插件用方言来适配

## 详解
### 先搞懂：让图书管理员只复印你要的那几页
网站上的商品列表，一页只显示 10 件。用户翻到第 3 页，你只需要第 21 到 30 件。

如果把所有商品都查出来再从中挑，就像把整本书搬过来再翻页，既慢又占内存。物理分页的做法是：告诉数据库“只给我第 21 到 30 条”，数据库只返回这 10 条。

后文用到的词：

- **offset**：跳过前面多少条。
- **limit**：最多返回多少条。
- **方言**：不同数据库在语法上的差异，比如分页怎么写。

### 做法一：SQL 里直接写分页参数
在 MySQL 里，最常见的写法是在查询末尾加 `limit` 和 `offset`：

- `limit 10` 表示最多返回 10 条；
- `offset 20` 表示跳过前 20 条。

页码转换公式：跳过的条数是（页码减 1）乘每页条数。第 3 页、每页 10 条，就是跳过 20 条。

在 MyBatis 里，可以把 offset 和 limit 作为参数传进 Mapper，在 XML 里用 `#{offset}` 和 `#{limit}` 取值。

这种做法简单直接，缺点是每个查询都要自己写，换数据库时语法也要改。

### 做法二：使用分页插件
像 PageHelper 这样的插件，会在查询执行前自动改写 SQL，加上分页条件。你的 Mapper 里仍然写普通的查询，不用关心分页语法。

插件会根据数据库类型选择对应的方言，所以同一份代码可以换数据库使用。

### 方案对比：物理分页和内存分页
| 方案 | 谁来截取 | 数据库返回 | 特点 |
|---|---|---|---|
| 物理分页 | 数据库 | 只返回当前页 | 性能较好，生产常用 |
| 内存分页（`RowBounds`） | MyBatis | 完整结果集 | 简单，但大数据量不适用 |

结论：数据量不小就用物理分页；想少写代码就用分页插件，想完全可控就手写 `limit`。

## 示例
```xml
<select id="selectPage" resultType="User">
    select * from user order by id
    limit #{size} offset #{offset}
</select>
```

```java
// 第 3 页，每页 10 条：跳过 (3 - 1) * 10 = 20 条
List<User> list = userMapper.selectPage(10, 20);
```

## 易错点
- 分页查询不写 `order by`，不同页之间可能重复或遗漏数据，因为顺序不固定
- 以为物理分页在任何页码都一样快；页码很大时，数据库仍然要先跳过大量行
- 页码从 1 开始，却直接当 offset 用，导致跳过了错误的条数

## 追问
### [f1] 页码很深时为什么慢？
数据库要先找到并跳过前面的所有行，再返回需要的。offset 越大，要跳过的越多。常见优化是记住上一页最后一条的 id，下一页用条件查询。
