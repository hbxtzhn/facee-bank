## 一句话
`#{}` 走预编译，参数值只是数据，能防 SQL 注入；`${}` 是直接把文本拼进 SQL，有注入风险，只用在表名、排序列等位置。

## 要点
- [kp1|3] `#{}` 会变成 `?` 占位符，再用预编译方式传参数值
- [kp2|3] `${}` 把参数值当字符串直接替换进 SQL，不经过预编译
- [kp3|2] `#{}` 能防注入，`${}` 参数来自用户时有注入风险
- [kp4|2] 表名、列名、排序字段不能用占位符，才用 `${}`

## 详解
### 先搞懂：数据和指令要分开
假设登录页让用户输入用户名。正常输入 `tom`，没问题。有人输入 `' or '1'='1`，如果你把这段文字直接拼进 SQL，整条语句的意思就被改了，这就是 **SQL 注入**。

可以想成填表：`#{}` 是在表格的空格里填内容，不管填什么，都只当内容；`${}` 是直接在表格上改印刷好的文字，用户能改动表格本身。

术语说明：

- **预编译**：先把 SQL 的结构发给数据库编译好，参数之后再单独传；
- **占位符**：SQL 里的 `?`，等着被填入参数值；
- **字符串替换**：先在 Java 里把文本拼好，再把整条 SQL 发给数据库。

### #{}：占位符，先编译后传值
`#{id}` 在运行时变成 `?`，值是之后通过 `PreparedStatement` 设进去的。数据库已经知道 SQL 结构，传来的内容只当作值，不会被当作 SQL 语句执行。字符串值会被正确转义，所以能防注入。

### ${}：文本替换，直接拼
`${name}` 在 MyBatis 里先被换成参数的字面文本，然后整条 SQL 才发给数据库。传 `tom` 就变成 `tom`，传一段恶意文本也照样拼进去。

它不是没用，有些地方只能这样：

- 动态表名，如按月分表；
- 动态列名；
- `order by` 后面的排序字段和方向。

因为占位符只能代表“值”，不能代表表名或列名。

### 方案对比：#{} 与 ${}
| 写法 | 处理方式 | 安全性 | 适合 |
|---|---|---|---|
| `#{}` | 预编译，传参数值 | 防注入，字符串自动转义 | 所有条件值、插入值 |
| `${}` | 直接替换文本 | 有注入风险，要提前校验 | 表名、列名、排序字段 |

结论：能用 `#{}` 就用 `#{}`；必须用 `${}` 时，参数不能直接来自用户，要用白名单校验。

## 示例
```xml
<!-- 条件值：用 #{} -->
<select id="findByName" resultType="User">
  select * from user where name = #{name}
</select>

<!-- 排序列：只能用 ${}，调用前要校验 -->
<select id="listOrdered" resultType="User">
  select * from user order by ${column}
</select>
```

## 易错点
- 为了图方便，所有条件都写 `${}`，直接让注入漏洞出现
- 以为 `${}` 传字符串会自动加引号，其实不会，要自己拼
- 以为只要用了 `#{}` 就安全，但 `order by` 处仍需白名单校验

## 追问
### [f1] 排序字段要用户选，怎么安全地写？
在代码里用白名单，把用户的选项映射成固定的列名，再传给 `${}`。不要把用户输入的文本直接传进去。
