## 一句话
轻量级锁靠 CAS 加自旋抢锁；自旋一段时间还抢不到，说明真有竞争，就升级成重量级锁，让等待的线程阻塞。

## 要点
- [kp1|3] 轻量级锁适合多个线程交替使用、没有真正同时抢的情况
- [kp2|3] 抢不到的线程先自旋；自旋失败，锁膨胀为重量级锁
- [kp3|2] 重量级锁基于操作系统互斥机制，拿不到锁的线程被阻塞挂起
- [kp4] 调用 wait() 也会让锁直接膨胀为重量级锁
- [kp5] 自旋次数由 JVM 自适应调整，不是固定值

## 详解
### 先搞懂：先在门口等一小会儿，不行再回休息区
去银行柜台办业务，前面的人快办完了，你站在旁边等几秒就行，没必要先去休息区坐下再被叫号。但如果前面的人要办很久，你一直站着干等就浪费了，不如去休息区坐着等。

轻量级锁和重量级锁就是这两种等法：

- 轻量级锁：站在原地等一会儿（自旋），不睡觉。
- 重量级锁：交给操作系统，拿不到就睡觉，释放后再被叫醒。

后文用到的术语：

- **CAS**：比较并交换，一条原子操作，要么改成功要么失败。
- **自旋**：拿不到锁时在原地循环重试，不进入睡眠。
- **阻塞**：线程被操作系统挂起，不占 CPU，等被唤醒才继续。
- **锁膨胀**：锁从轻量级升级为重量级。

### 轻量级锁：CAS 加自旋
线程进入同步块时，先在自己的栈里留一份「锁记录」，把对象头的 Mark Word 备份进去，再用 CAS 把对象头改成指向这份锁记录的指针。CAS 成功就拿到了锁，不用惊动操作系统。

如果 CAS 失败，说明别的线程正占着锁。这时线程不马上睡觉，而是自旋，在原地反复再试几次。绝大多数持有锁的时间都很短，所以通常稍等一下就能拿到。

### 什么时候升级为重量级锁
- **自旋之后仍然拿不到锁**：说明持有者占用时间比较长，或者有多个线程在抢。继续空转只会白白消耗 CPU，于是锁膨胀为重量级锁。
- **有其他线程已经在等待**：竞争确实存在，轻量级锁这套「交替使用」的假设不成立了。
- **调用了 `wait()`**：等待队列放在重量级锁的监视器里，所以直接膨胀。

膨胀之后，锁的状态指向一个监视器（由操作系统的互斥量支撑），拿不到锁的线程进入等待队列并被阻塞，持有者释放锁时再唤醒它们。

### 对比：轻量级锁 vs 重量级锁
| 对比项 | 轻量级锁 | 重量级锁 |
|---|---|---|
| 抢锁方式 | CAS 加自旋 | 进入监视器，失败则阻塞 |
| 拿不到锁的线程 | 在原地空转 | 被操作系统挂起 |
| 适用情形 | 持有时间短、交替使用 | 竞争激烈或持有时间长 |
| 缺点 | 空转浪费 CPU | 阻塞和唤醒要进内核，开销较大 |

结论：竞争不激烈用轻量级锁最划算，竞争激烈时让线程睡下去更省 CPU；这个切换由 JVM 自动完成。

### 进阶：自旋多少次？（基础薄弱可先跳过）
早期版本自旋次数是个固定参数，后来 HotSpot 改成自适应自旋：如果上次在同一把锁上自旋成功过，这次就多等一会儿；很少成功，就少转甚至不转。所以面试里不要背某个具体次数，说明「有上限、会自适应」就够了。

## 易错点
- 以为轻量级锁完全没有开销；它每次加锁解锁都有 CAS，拿不到还要消耗 CPU 自旋
- 以为自旋次数是固定的；JVM 会按历史情况自适应
- 以为升级为重量级锁之后线程仍然自旋；重量级锁里的等待线程是阻塞挂起的
- 以为 wait() 只和等待有关，不影响锁状态；它会让锁膨胀

## 追问
### [f1] 为什么不一开始就用重量级锁？
因为多数同步块持有锁的时间很短，线程挂起再唤醒的开销比等一会儿还大。先用轻量级锁，没有竞争时更便宜。

### [f2] 自旋的缺点是什么？
自旋期间线程不干活却占着 CPU。持有者很久不释放时，空转就是浪费，所以要限制自旋，超过就升级。
