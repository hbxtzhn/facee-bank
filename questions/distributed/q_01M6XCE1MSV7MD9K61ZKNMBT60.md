## 一句话
用业务唯一键（如订单号）做去重依据，配合唯一索引、状态机、消费记录表或 Redis 短时去重，保证同一条业务只生效一次。

## 要点
- [kp1|3] 去重依据用业务唯一键，不用 MQ 自动生成的消息 ID
- [kp2|3] 唯一索引：重复插入会被数据库拒绝，最可靠简单
- [kp3|2] 状态机：只允许状态按流程单向流转，重复消息会被忽略
- [kp4|2] 消费记录表：处理前先查是否已处理，和业务在同一事务内
- [kp5] Redis 短时去重：适合挡住短时间内的重复，不适合作唯一依据

## 详解
### 先搞懂：签到簿
参加活动要签到，签到簿上写着名字。有人再来签一次，管理员一看已经有名字，就不再记录。这个签到簿就是去重记录，名字就是业务唯一键。

后文用到的几个词：
- **业务唯一键**：能唯一标识一次业务的值，比如订单号加操作类型。
- **唯一索引**：数据库保证某列值不重复的机制。
- **状态机**：规定状态只能按固定路径变化的设计。

### 先说为什么不用 MQ 的消息 ID
生产者重试时，可能生成新的消息 ID，两条消息 ID 不同，但业务上是同一件事。补偿任务重发消息也一样。所以要用业务本身的唯一键，比如订单号，这样怎么重试都能识别。

### 唯一索引：让数据库拦住重复
比如给「订单号加操作类型」建唯一索引，重复插入会报错，捕获后当作已处理即可。简单可靠，适合新增类的操作。

### 状态机：状态只能往前走
订单状态从待支付到已支付，再到已发货。收到「支付成功」消息时，先判断订单是否还是待支付，如果已经是已支付，就说明处理过，直接忽略。

### 消费记录表：处理前先查
建一张表记录已处理的业务键。处理时在同一个数据库事务里，先插入记录，再执行业务。重复的消息插入记录会失败，业务就不会再执行。

### Redis 短时去重：挡重复的第一道关
用业务键做 key，设置一个较短的过期时间，先检查是否存在。它速度快，但 Redis 数据可能丢失，key 也会过期，不能作为唯一依据，最好配合数据库手段。

### 方案对比：怎么选
| 方案 | 原理 | 可靠性 | 适合 |
|---|---|---|---|
| 唯一索引 | 数据库拒绝重复 | 高 | 新增类操作 |
| 状态机 | 状态只能单向流转 | 高 | 有明确流程的订单 |
| 消费记录表 | 先记录再处理 | 高 | 通用，需要事务 |
| Redis 短时去重 | 缓存里判重 | 一般 | 挡短时重复 |

结论：核心业务以数据库手段（唯一索引、状态机、记录表）为准；Redis 只作为前置过滤。

## 示例
```sql
-- 消费记录表：业务键唯一，重复插入会失败
CREATE TABLE consume_record (
  biz_key VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (biz_key)
);

-- 在同一事务里：先插入记录，成功才执行业务
INSERT INTO consume_record (biz_key, created_at) VALUES ('order-1001-pay', NOW());
```

## 易错点
- 用 MQ 的消息 ID 去重；重试后消息 ID 可能变，业务上仍重复
- 先执行业务再写记录，且不在同一事务里；中途崩溃会重复执行
- 只依赖 Redis 去重；Redis 数据丢失或过期后，重复消息会漏过

## 追问
### [f1] 消费记录表会不会越来越大？
会，所以要定期清理过期记录，保留时间要大于消息可能被重投的最长窗口。

### [f2] 去重和业务不在同一个事务里会怎样？
可能出现记录写成功但业务没做，消息就再也不会被处理；或者业务做完记录没写成，导致重复。所以最好放在同一事务。
