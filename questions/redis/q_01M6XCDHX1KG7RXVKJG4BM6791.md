## 一句话
单机 Redis 的内存有上限，写压力也集中在一个节点；集群把数据分到多个主节点上，容量能扩大，读写也被分摊。

## 要点
- [kp1|3] 单机内存是上限，数据量超过一台机器就放不下
- [kp2|3] 写请求都落在一个主节点上，成为瓶颈
- [kp3|2] 集群把数据按槽分到多个主节点，容量随节点增加而变大
- [kp4|2] 集群为每个主节点配从节点，主节点故障能自动切换
- [kp5] 主从复制只解决读和备份，每个节点仍存全量数据

## 详解
### 先搞懂：一家小店撑不住了
一家小面馆，只有一个灶台、一间仓库。客人多了，灶台忙不过来；食材多了，仓库放不下。主从复制相当于开一个分店只负责接待堂食，但每家店都得存全部食材，仓库问题没解决。

集群的办法是：开多家分店，每家分管一部分食材和一部分客人，各存各的，总容量就大了。

后文用到的词：

- **主从复制**：从节点复制主节点的全部数据，用来备份和分担读。
- **分片**：把数据拆成几份，分散到不同节点。

### 单机的三个瓶颈
- **内存**：数据全放在一台机器的内存里，机器内存是硬上限。
- **写入**：写请求只能由一个主节点处理，主从复制并不能分担写。
- **单点**：一台机器出问题，整个服务不可用。

### 主从和哨兵为什么不够
主从加哨兵能解决单点问题：主节点挂了，从节点顶上。但每个节点仍然保存全量数据，内存上限没变，写入也还在一个主节点上。

### 集群怎么解决
- **容量**：数据按哈希槽分到多个主节点，每个节点只存一部分，加节点就能扩容。
- **读写**：不同的 key 落在不同主节点上，读写请求被分散。
- **高可用**：每个主节点配从节点，主节点故障时自动切换，不需要单独部署哨兵。

### 代价
集群也有限制：跨槽的多 key 命令受限，运维比单机复杂，客户端要支持集群协议。数据量不大、一台机器够用时，没必要上集群。

## 易错点
- 以为主从复制能扩大容量；每个节点还是存全量数据
- 以为集群能线性提升一切性能；跨节点的多 key 操作会受限
- 数据量很小也上集群；会徒增复杂度

## 追问
### [f1] 数据量不大时，需要上 Redis 集群吗？
不需要。一台机器内存够用、写压力不大时，主从加哨兵就能满足高可用，集群的复杂度是不必要的开销。
