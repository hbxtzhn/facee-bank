## 一句话
拉模式的好处是消费者自己掌握节奏、Broker 很轻；坏处是有延迟和空轮询，可以用长轮询来缓解。

## 要点
- [kp1|3] 优点：消费者自主控制拉取，处理不过来就暂停
- [kp2|2] 优点：Broker 只负责存储，职责轻，便于批量拉取
- [kp3|2] 缺点：拉取间隔大延迟高，间隔小会产生大量空请求
- [kp4|3] 长轮询：没消息时 Broker 挂起请求，有消息或超时才返回

## 详解
### 先搞懂：自己去信箱看信
信件寄到了信箱，你自己决定什么时候去看：想看就下楼拿，忙就晚点再去。可是你不知道信什么时候到，如果每隔五分钟下楼一次，大多数时候是白跑；如果半天才去一次，信又会晚拿到很久。

拉模式就是这样。先说几个词：

- **拉模式**：消费者主动向 Broker 请求消息，Broker 被动响应。
- **轮询**：消费者每隔一段时间就去问一次“有消息吗”。
- **空轮询**：问了但没有消息，白白浪费一次请求。

### 拉模式的优点
- **消费者自己掌握节奏**：消费不过来就暂停拉取，消息安全地留在 Broker，不会把自己压垮；
- **Broker 很轻**：基本只负责存消息，不需要记录每个消费者能处理多快；
- **方便批量**：消费者可以一次拉很多条，减少交互次数。

### 拉模式的缺点
消费者不知道消息什么时候到，只能一遍遍问：

- 拉取间隔设得大，消息到了要等很久才被取走，延迟高；
- 拉取间隔设得小，大部分请求拿不到消息，空耗消费者和 Broker 的资源。

### 解决空轮询：长轮询
消费者发出拉取请求后，Broker 此刻可能没有消息。这时 Broker 不立即回复“没有”。它把这个请求挂起，等一段时间，比如几秒到几十秒。

等待期间一旦有新消息到达，就立刻返回。一直没有，就等到超时再返回。

这样有消息时几乎马上能收到，没消息时也不会每秒都发请求，既接近实时，又不空耗。

## 示例
```java
// 长轮询伪代码：没有消息时，Broker 会挂起请求，最多等 timeoutMs
while (running) {
    List<Message> msgs = broker.pull(topic, 32, 5000); // 最多拉 32 条，最长等 5 秒
    for (Message m : msgs) {
        handle(m);
    }
}
```

## 易错点
- 以为拉模式一定有高延迟；用了长轮询后，延迟可以很低
- 以为长轮询是推模式；它仍然是消费者发起请求，只是 Broker 迟一点再回复
- 拉取间隔设得过小，把拉模式变成了不断打扰 Broker 的忙请求

## 追问
### [f1] 长轮询的超时时间设多长合适？
太短会退化成频繁的空轮询，太长则请求长时间占着连接，也可能被网络设备断开。要结合网络和连接限制，在几秒到几十秒间取值。
