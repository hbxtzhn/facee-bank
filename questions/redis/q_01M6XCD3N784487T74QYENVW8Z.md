## 一句话
不同元素算出的位置会重叠，不存在的元素的 k 个位置恰好都被别人置成 1，就会被误判成存在；位数组越小越容易误判。

## 要点
- [kp1|3] 误判来自哈希位置重叠：别的元素把某元素的位置都置成了 1
- [kp2|3] 位数组越小、元素越多，位越拥挤，误判率越高
- [kp3|2] 位数组越大误判率越低，但占用更多内存
- [kp4] 误判只会把“不存在”判成“存在”，不会把“存在”判成“不存在”

## 详解
### 先搞懂：黑板上钩打多了
还是黑板上打钩的比喻：黑板只有 10 格，已经有很多人登记过，格子差不多都打满了钩。这时来一个从没登记的人，算出的 3 个格子凑巧都有钩，门卫就会误以为他登记过。黑板越小、登记的人越多，这种“凑巧”越常见。

后文用到的词：
- **哈希冲突**：不同元素算出了相同的位置。
- **误判率**：不存在的元素被判成存在的概率。
- **填充率**：位数组里已经是 1 的位置占多少比例。

### 误判是怎么发生的
1. 元素 A 写入，位置 1、4、7 被置 1；
2. 元素 B 写入，位置 4、8、9 被置 1；
3. 元素 C 从没写入，但它算出的位置是 1、8、9，这三位恰好都是 1（分别来自 A 和 B）；
4. 查询 C 时，三位都是 1，被判为“可能存在”，但 C 其实不存在。

### 什么因素影响误判率
- **位数组大小**：数组越小，位置越容易重叠，误判率越高；数组越大越低，但占用内存也更多；
- **已写入的元素数量**：写入越多，被置 1 的位越多，误判率越高；
- **哈希函数个数**：太少区分度不够，太多会很快把位占满，存在一个比较合适的值。

### 怎么控制
创建时根据预计元素数量和能接受的误判率，来决定位数组大小和哈希函数个数。很多库（如 Guava、RedisBloom）创建时直接让你传这两个参数，库帮你算。如果实际元素比预计多很多，误判率会超出预期，需要重建更大的过滤器。

### 误判会带来什么后果
在防穿透场景下，误判只是让少量不存在的请求漏过去，进一步查缓存和数据库，不会出错。所以这是一种可以接受的代价，用很小的空间换来拦截大部分无效请求。

## 示例
```java
// 预计 100 万个元素，期望误判率 1%，库会据此计算位数组大小和哈希函数个数
BloomFilter<Long> filter =
        BloomFilter.create(Funnels.longFunnel(), 1_000_000, 0.01);
```

## 易错点
- 以为误判会导致“存在的数据查不到”；布隆过滤器不会漏判
- 以为位数组大小可以随意设小；元素数量远超预期时，误判率会很高
- 以为增加哈希函数个数一定能降低误判率；太多反而更快占满位

## 追问
### [f1] 误判率能降到 0 吗？
不能。用有限的位表示无限的元素，必然有重叠。只能通过增大位数组、选合适的哈希函数个数把误判率降低。
