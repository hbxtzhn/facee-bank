## 一句话
HTTP 是应用层的请求-响应协议，规定浏览器和服务器怎么说话；它通常跑在 TCP 连接上，由 TCP 负责可靠传输。

## 要点
- [kp1|3] HTTP 是应用层协议，规定请求和响应的格式
- [kp2|3] 通信方式是客户端发请求，服务器回响应
- [kp3|2] HTTP 通常运行在 TCP 之上，依靠 TCP 保证可靠
- [kp4] HTTP 自己不负责传输，只定义“说什么”

## 详解
### 先搞懂：点餐的规矩和送餐的服务员
你在餐厅点餐：先说“我要一份宫保鸡丁”，后厨做好，端给你。点餐和上菜遵守约定的流程和格式，这就是 HTTP 的角色。

但是你的话要靠服务员传到后厨，菜也要靠服务员送回来，这个负责可靠送达的服务员，就是 TCP。几个词：

- **应用层协议**：规定应用之间交换的内容和格式。
- **请求-响应**：客户端先发请求，服务器处理后回响应。
- **TCP**：传输层协议，保证数据可靠、有序地送到。

### HTTP 做了什么
你在浏览器输入网址，浏览器发出一个 HTTP 请求，里面写明：要什么资源、用什么方法（如获取、提交）、带哪些附加信息。服务器处理后，返回 HTTP 响应：状态码（成功、失败等）、响应头、响应内容，比如网页、图片、JSON 数据。

HTTP 规定的是这些内容的格式和含义。至于数据怎么可靠地送过去，不归它管。

### HTTP 和 TCP 的关系
HTTP 是应用层，TCP 是传输层，HTTP 在 TCP 之上。流程大致是：

1. 浏览器先和服务器建立 TCP 连接；
2. 在这条连接上发送 HTTP 请求；
3. 服务器通过同一条连接返回 HTTP 响应；
4. 连接可以复用，也可以关闭。

因为有 TCP 保证，HTTP 不用操心丢包和重传，只需关心“说什么”。

### 补充：不一定是 TCP
较新的 HTTP/3 运行在基于 UDP 的 QUIC 之上，但常见的 HTTP/1.1 和 HTTP/2 仍然跑在 TCP 上。所以说“通常”运行在 TCP 上。

## 易错点
- 以为 HTTP 和 TCP 是同一层；HTTP 在应用层，TCP 在传输层
- 以为 HTTP 一定用 TCP；HTTP/3 用的是 QUIC
- 以为 HTTP 负责保证数据不丢；这是 TCP 的工作

## 追问
### [f1] HTTP 请求结束后，TCP 连接会立刻断开吗？
不一定。现在通常复用连接，请求结束后保持一段时间，后面的请求可以继续使用，省去重新建立连接的开销。
