## 一句话
锁的有效时长要大于业务正常耗时；拿不准时，用后台线程定期延长过期时间，Redisson 的看门狗就是这么做的。

## 要点
- [kp1|3] 过期时间太短，业务没做完锁就没了，两个线程会同时执行
- [kp2|3] 方式一：按业务正常耗时预估，留出余量，实现简单但不灵活
- [kp3|2] 方式二：另起线程定期给锁续期，业务做完就停止续期
- [kp4|2] 续期前要确认锁还是自己的，且进程宕机后续期也会停止
- [kp5] Redisson 不传 leaseTime 才会启用看门狗

## 详解
### 先搞懂：租会议室要定多长时间
租一间会议室，要提前报一个预计时长。报短了，会议没开完就被下一拨人赶出来；报得太长，万一你提前走了或者人没来，会议室一直空着浪费。

锁的过期时间也是这样的两难：

- 太短：业务还在执行，锁已经过期，别的线程拿到锁，互斥被破坏。
- 太长：持有锁的服务宕机后，别人要等很久才能拿到锁。

后文用到的词：

- **预估时长**：根据业务耗时，直接写死过期时间。
- **续期**：业务还没结束时，把锁的过期时间往后延。
- **看门狗**：负责定期续期的后台线程。

### 方式一：按业务耗时预估
先测一下这段业务正常要多久，再留出余量。例如平时 2 秒完成，就设 10 秒。

优点是简单，没有额外线程。缺点是业务耗时会波动：数据库变慢、网络抖动、Full GC，都可能让耗时超出预期。

适合耗时稳定、可预测的短任务。

### 方式二：开线程续期
思路是：加锁时先设一个较短的过期时间，另开一个线程每隔一段时间检查业务是否还在执行。还在执行，就把过期时间重新延长；业务结束，就停止续期并释放锁。

这样过期时间可以设得比较短，既不怕业务变慢，也不怕宕机后久等：持有者宕机，续期线程也跟着没了，锁很快自己过期。

续期要注意两点：

- 续期前要判断锁还是自己的，用 Lua 脚本一并完成。
- 业务结束后要停止续期，否则锁永远不会过期。

### 方案对比：预估与续期
| 方案 | 实现难度 | 业务变慢时 | 宕机后恢复 | 适合 |
|---|---|---|---|---|
| 预估时长 | 低 | 锁可能提前失效 | 要等到过期 | 耗时稳定的短任务 |
| 续期线程 | 较高 | 持续延长，不会提前失效 | 续期停止后很快过期 | 耗时不稳定的任务 |

结论：耗时稳定就预估；耗时波动大就用续期，不用自己写，直接用 Redisson 的看门狗。

### 进阶：Redisson 的看门狗参数（基础薄弱可先跳过）
- 调用 `lock()` 或 `tryLock` 时不指定 leaseTime，就启用看门狗；默认锁过期时间是 30 秒，大约每隔三分之一的时间续期一次。
- 如果显式指定了 leaseTime，看门狗不会启动，到点锁就过期。
- 续期只防“业务慢”，不能防“JVM 长时间暂停”；极端情况下仍可能有两个线程同时持锁，对正确性要求很高时要配合数据库唯一约束等兜底。

## 示例
```java
RLock lock = redisson.getLock("lock:order:1001");
// 不指定 leaseTime：启用看门狗自动续期
lock.lock();
try {
    doBusiness();
} finally {
    lock.unlock();
}
```

## 易错点
- 把过期时间设得极长来省事；持有者宕机后别人要等很久
- 指定了 leaseTime 还以为有自动续期；指定后看门狗不启动
- 续期线程只管延长，不判断锁是不是自己的；可能延长了别人的锁

## 追问
### [f1] 业务线程已经卡死，看门狗还在续期怎么办？
看门狗只要进程活着就会续期，所以业务线程卡死会导致锁一直不释放。要给业务加超时控制，并且监控长时间持锁的情况。
