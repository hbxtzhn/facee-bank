## 一句话
先查清是生产突增、消费变慢、分区不足还是 Broker 异常，再按限流止血、扩容、优化消费逻辑、批量消化历史积压的顺序处理。

## 要点
- [kp1|3] 第一步先定位根因，原因不同，处理方式完全不同
- [kp2|3] 处理顺序：限流止血，扩容消费者和分区，优化慢消费，再清历史积压
- [kp3|2] 扩容消费者要同时看分区数，消费者多于分区时多出的是空闲的
- [kp4] 历史积压可以单独起临时消费者批量处理，别拖累实时消息

## 详解
### 先搞懂：像水池又进水又排水
想象一个水池，进水管（生产者）比排水管（消费者）粗，水位就一直涨。处理的思路很直接：先让水别再涨（止血），再把排水管加粗（扩容、优化），最后把已经存下的水放掉（清历史积压）。

后文用到的词：

- **消费位点**：消费者已经处理到队列的哪个位置。
- **堆积量**：最新消息的位置减去消费位点，就是还没处理的消息数。
- **分区**：主题被拆成的多条通道，一个分区同一时刻通常只让组内一个消费者处理。

### 第一步：定位根因
看监控，判断是哪一类问题：

- **生产突增**：生产速率曲线突然升高。
- **消费变慢**：生产速率正常，但单条消息处理耗时变长，或者消费者在不停报错重试。
- **分区不足**：消费者机器不忙，但吞吐上不去，说明并行度被分区数卡住。
- **Broker 异常**：Broker 磁盘、网络、节点状态有告警。

### 第二步：限流止血
先让积压别继续扩大。可以在生产端限流或降级，暂停非核心业务的消息，必要时把不重要的消息丢到别的通道。不先止血，后面所有的扩容都是追着一个越来越大的数字跑。

### 第三步：扩容消费者和分区
- 消费者数量没到分区数时，直接加消费者实例。
- 消费者数量已经等于分区数，就要先增加分区，再加消费者。
- 注意：有的消息系统按 key 路由分区，增加分区可能改变同一个 key 的分布，要确认顺序要求。

### 第四步：优化慢消费逻辑
扩容只是加机器，治本要让单条消息处理得更快：

- 慢接口或慢 SQL 改成批量调用，或加缓存。
- 把消费里的非关键步骤异步化。
- 消费失败时限制重试次数，失败消息转入死信队列，别让一条坏消息卡住整个分区。
- 消费逻辑要幂等，因为扩容、重试期间可能重复消费。

### 第五步：批量处理历史积压
实时消息恢复正常后，堆下来的历史消息可以另外处理：起一批临时消费者，用更大的批量、更高的并发去消化，处理完再下线。这样历史积压不会拖慢新消息。

### 方案对比：几种处理手段
| 手段 | 解决什么 | 代价 | 适合 |
|---|---|---|---|
| 限流降级 | 生产突增 | 部分业务受影响 | 积压还在扩大时 |
| 加消费者 | 消费能力不足 | 机器成本 | 消费者少于分区数 |
| 加分区 | 并行度被卡住 | 可能影响消息顺序 | 消费者已等于分区数 |
| 优化消费逻辑 | 单条处理慢 | 需要改代码和发布 | 根因在处理耗时 |
| 临时批量消费 | 历史积压 | 临时资源 | 实时流量已恢复后 |

结论：先限流止血，再扩容，根因在代码就优化消费逻辑，最后用临时消费者清历史积压。

## 示例
```bash
# 以 Kafka 为例，查看消费组每个分区落后多少条消息（LAG 列）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-consumer
```

## 易错点
- 一上来就加机器；根因是慢 SQL 或 Broker 故障时，加机器没有用
- 消费者数量超过分区数还继续加；多出的消费者拿不到分区，只能空闲
- 为了追赶进度直接丢弃积压消息；有业务要求时会造成数据丢失
- 扩容和重试时没有做幂等；同一条消息被重复处理，会造成重复扣款一类问题

## 追问
### [f1] 积压了几百万条，消费者处理不过来怎么办？
先限流止血，再临时增加分区和消费者，用批量方式处理。可以新建一个临时主题，让原消费者只把消息转发过去，再由大量消费者并行处理。
