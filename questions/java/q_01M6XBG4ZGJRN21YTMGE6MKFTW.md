## 一句话
RPC 是远程过程调用：调用方像调用本地方法一样调用另一台服务器上的方法，序列化、网络传输这些细节都由框架包好了。

## 要点
- [kp1|3] RPC 让远程方法调用看起来像本地方法调用
- [kp2|3] 框架负责：把参数序列化、通过网络发送、接收并反序列化结果
- [kp3|2] 调用方通常只持有接口，背后由代理对象完成远程通信
- [kp4|2] RPC 通常基于 Socket（TCP）通信实现
- [kp5] 远程调用会失败、超时，比本地调用多出网络问题要处理

## 详解
### 先搞懂：打电话点外卖
你想吃饭，打电话给餐厅说“来份宫保鸡丁”，半小时后饭到了。你不用管厨房怎么做、骑手怎么送。

RPC 类似：订单服务想查用户信息，调用 `userService.getUser(1)`，看起来是个本地方法，实际上用户服务在另一台机器上。中间的“打电话、传话”，由 RPC 框架做完。

后文术语：
- **调用方（客户端）**：发起调用的一方。
- **服务提供方（服务端）**：真正执行方法的一方。
- **代理**：调用方手里的“替身”对象，看起来是接口，实际负责发网络请求。

### 一次 RPC 调用经历了什么
1. 调用方调用接口方法，实际调到的是代理对象；
2. 代理把方法名、参数**序列化**成字节；
3. 通过网络（通常基于 Socket）发送给服务端；
4. 服务端收到后**反序列化**，找到对应的方法并执行；
5. 结果同样序列化后发回，调用方的代理反序列化，把结果返回给业务代码。

### 为什么需要它
服务拆成多个之后，服务之间需要互相调用。如果每次都手写 HTTP 请求、拼 JSON，重复又麻烦。RPC 框架把这些统一封装，开发者只关注业务。

### 和本地调用的区别
虽然写法像本地调用，但网络可能断、对方可能慢或挂掉，所以 RPC 框架一般会提供超时、重试、负载均衡等机制。使用时不能把它当成一定成功的本地调用。

## 易错点
- 以为 RPC 就是 HTTP；RPC 是一种调用方式，底层可以用 HTTP/2（如 gRPC），也可以用自定义 TCP 协议
- 以为远程调用和本地调用一样可靠；网络故障和超时必须考虑
- 以为 RPC 一定要用 JSON；序列化方式由框架决定

## 追问
### [f1] RPC 和 HTTP 接口调用有什么区别？
HTTP 是一种通信协议；RPC 是一种调用方式，可以基于 HTTP，也可以基于自定义 TCP 协议。RPC 框架通常额外提供服务发现、负载均衡、超时重试等能力。
