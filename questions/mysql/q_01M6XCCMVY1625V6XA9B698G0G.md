## 一句话
连接时，外层表每取一行，都要去内层表查一次。外层行数越少，内层查找次数越少，所以让小表当外层更省。

## 要点
- [kp1|3] 嵌套循环连接：外层每取一行，就到内层表查一次匹配行
- [kp2|3] 内层查找次数等于外层行数，所以外层要小
- [kp3|2] 内层的连接列要有索引，每次查找才不用扫全表
- [kp4] 内连接的顺序通常由优化器选，LEFT JOIN 的左表固定当外层
- [kp5] 比的是过滤之后的行数，不是表的总行数

## 详解
### 先搞懂：先拿哪一张表去配对
比如要查「VIP 用户的所有订单」。用户表里 VIP 只有几十人，订单表有上百万行。

可以这样类比：手里有一小摞快递单，仓库里有一大堆按编号摆放的包裹。

- 拿每张快递单去仓库按编号取包裹：单子只有几十张，就只跑几十趟；
- 反过来，拿每个包裹去翻快递单：包裹有上百万个，就要跑上百万趟。

数据库连接表的做法和第一种一样。后文会用到这几个词：

- **驱动表（外层表）**：先读的那张表，一行一行往下取。
- **被驱动表（内层表）**：每取到外层一行，就到这张表里找匹配的行。
- **嵌套循环连接**：MySQL 最基础的连接方式，就是上面的「外层一行配内层一次」。

### 嵌套循环：外层一行，内层一次
执行过程按顺序是这样的：

1. 从外层表取出一行（先应用该表自己的过滤条件）；
2. 用这一行的连接列值，去内层表找匹配的行；
3. 把匹配上的行拼起来输出，回到第 1 步取下一行。

所以总工作量大致是：外层行数 × 每次内层查找的成本。外层小，乘数就小。

### 内层要有索引：每次查找才便宜
「小表驱动大表」有个前提：内层表的连接列有索引。有索引时，每次查找走 B+ 树，很快就能定位到匹配行。

没有索引时，每次查找都要扫一遍内层表，外层行数再少也会很慢。MySQL 8.0 在没有索引的等值连接上，可以改用哈希连接来缓解。但最稳妥的做法仍然是给连接列建索引。

### 谁算小表：看过滤后的行数
「小」指的是应用了 WHERE 条件之后，真正要参与连接的行数。一张一千万行的表，如果过滤后只剩十行，它反而适合当驱动表。

### 优化器会自己选，你要知道何时干预
- 普通的 `INNER JOIN`：优化器会根据统计信息估算成本，自己决定连接顺序，大多数时候不用管。
- `LEFT JOIN`：左表是外层，顺序由语义决定，优化器一般不能随意调换。
- 想强制顺序：可以用 `STRAIGHT_JOIN`，左边的表就是驱动表。
- 看结果：`EXPLAIN` 输出里靠前的那一行，就是先读的表。

## 示例
```sql
-- 只有少量 VIP 用户，让 users 当外层；orders.user_id 上要有索引
SELECT o.*
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.is_vip = 1;
```

## 易错点
- 以为写在 FROM 后面的第一张表就一定是驱动表；内连接时顺序由优化器决定
- 只看表的总行数，不看过滤后的行数
- 只想着调整顺序，却忘了给内层表的连接列建索引

## 追问
### [f1] 怎么确认哪张表是驱动表？
看 `EXPLAIN` 的输出，靠前的那一行对应先读取的表，也就是驱动表。再结合 `rows` 和 `key` 列，看内层查找是否用到了索引。

### [f2] 内层表没有索引会怎样？
外层每取一行，内层都要整表扫描一遍，总工作量会急剧增加。应当先给连接列建索引。MySQL 8.0 在等值连接下也可能改用哈希连接，但不能当作建索引的替代方案。
