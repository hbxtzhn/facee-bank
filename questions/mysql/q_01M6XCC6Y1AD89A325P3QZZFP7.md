## 一句话
InnoDB 支持事务、行锁、外键，数据按主键聚簇存放；MyISAM 都不支持，只有表锁。需要可靠和并发写的业务表，选 InnoDB。

## 要点
- [kp1|3] InnoDB 支持事务和崩溃恢复，MyISAM 不支持事务
- [kp2|3] InnoDB 支持行锁，MyISAM 只有表锁，并发写时更容易互相阻塞
- [kp3|2] InnoDB 支持外键，MyISAM 不支持
- [kp4|2] InnoDB 主键索引是聚簇索引，叶子节点存整行数据；MyISAM 索引和数据文件分开
- [kp5] MySQL 5.5 起 InnoDB 是默认引擎

## 详解
### 先搞懂：转账为什么不能用 MyISAM
想象银行转账：A 扣 100，B 加 100。如果扣完 A 之后系统宕机，B 没加上，钱就凭空消失了。要避免这种情况，需要「两步要么都成功，要么都不成功」的保证。

InnoDB 能提供这个保证，MyISAM 不能。这是两个引擎最大的区别。

后文用到的术语：

- **事务**：一组操作，要么全部生效，要么全部不生效；
- **行锁、表锁**：一次锁一行，还是一次锁整张表；
- **聚簇索引**：索引的叶子节点里直接放整行数据；
- **外键**：让一张表的字段必须对应另一张表里存在的记录。

### 方案对比：InnoDB 和 MyISAM
| 对比项 | InnoDB | MyISAM |
|---|---|---|
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行锁（也有表锁） | 表锁 |
| 外键 | 支持 | 不支持 |
| 索引与数据 | 主键是聚簇索引，数据在叶子节点 | 索引和数据文件分开，索引指向数据位置 |
| 崩溃恢复 | 有日志，能恢复 | 较弱，崩溃后表可能损坏 |
| 并发写 | 不同行的修改可以同时进行 | 写入时整表被锁 |

结论：业务系统默认选 InnoDB。只有几乎只读、不需要事务的老系统场景，才可能见到 MyISAM。

### 锁粒度：为什么影响并发写
两个人同时修改同一张表的不同行：

- 用 InnoDB，各锁各的行，可以同时进行；
- 用 MyISAM，写操作要锁整张表，后来的人要等前一个人改完。

所以写入频繁的业务表，用 MyISAM 容易排队。

### 聚簇索引：数据放在哪
InnoDB 的主键索引，叶子节点里放的就是整行数据，按主键查一次就拿到完整的行。MyISAM 的索引叶子节点只存数据文件里的位置，查到之后还要再去数据文件读一次。

## 易错点
- 以为 MyISAM 一定比 InnoDB 快；没有确凿依据不能这样下结论，而且它写入要锁整表
- 以为 InnoDB 只有行锁；它也有表锁，行锁是靠索引加的
- 以为 MyISAM 支持事务；它不支持，语句执行完就直接生效

## 追问
### [f1] 为什么 InnoDB 能崩溃后恢复数据？
因为它修改数据前会先写 redo log（重做日志），宕机重启后可以用这份日志把已提交的修改重新做一遍。

### [f2] 现在还有必要用 MyISAM 吗？
新业务基本没有。它不支持事务，崩溃后恢复能力也弱，InnoDB 能满足绝大多数需求。
