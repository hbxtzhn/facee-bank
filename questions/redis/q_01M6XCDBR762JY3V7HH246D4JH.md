## 一句话
定期删除是 Redis 周期性地随机抽查一批设了过期时间的 key，删掉过期的，并限制每次耗时，在 CPU 和内存之间取平衡。

## 要点
- [kp1|3] 周期性运行，每次只随机抽样一批带过期时间的 key
- [kp2|3] 抽到的 key 里已过期的会被删除
- [kp3|2] 过期比例较高就继续抽下一批，否则本轮结束
- [kp4|2] 每次有执行时间上限，避免长时间阻塞主线程

## 详解
### 先搞懂：为什么不全部检查
惰性删除有个缺点：过期了但没人访问的 key 一直留着。所以 Redis 还要主动去清理。

但如果每次都把所有设了过期时间的 key 检查一遍，几百万个 key 就会让主线程卡住，客户端请求都得排队。

所以 Redis 的做法像抽检：不检查所有，每次抽一小撮，删掉过期的。过期的多，说明还有很多，再抽一次；过期的少，说明差不多干净了，收工。

后文用到几个词：

- **抽样**：随机取一小部分。
- **主线程**：Redis 处理命令的线程，被占用时命令会变慢。

### 定期删除：抽查加限时
一轮定期删除大致这样做：

1. 从有过期时间的 key 中随机抽取一批，常见实现里每批是 20 个。
2. 检查它们，把过期的删掉。
3. 如果这一批里过期的比例较高，常见实现里是超过 10%，就再抽一批重复。
4. 如果比例不高，或者本轮用时超过上限，就结束，等下一次。

时间上限很关键，它保证了定期删除不会长时间占用主线程。代价是，一次清理可能不彻底。

### 两种运行模式
Redis 里定期删除有 SLOW 和 FAST 两种模式，运行方式不同，见后面两道题。

### 和惰性删除配合
- 定期删除负责清理一部分没被访问的过期 key。
- 惰性删除保证访问到的 key 一定被正确处理。

即使两者都用了，还是可能有漏网的 key 一直占内存，这时就靠内存淘汰策略兜底。

### 进阶：具体数字以版本为准（基础薄弱可先跳过）
抽样数量、比例阈值、执行频率都是实现细节，不同版本可能有调整。可以通过 `hz` 配置调整定期任务的频率，调高会更勤快地清理，但消耗更多 CPU。

## 易错点
- 以为定期删除会把所有过期 key 扫一遍；它只做随机抽样
- 以为有了定期删除过期 key 就一定会被及时删除；仍可能有残留
- 以为定期删除没有时间限制；它限制了单次执行时间

## 追问
### [f1] 为什么不给每个 key 设一个定时器，到点就删？
每个 key 一个定时器要额外占内存，到点集中触发还会占用大量 CPU，在 key 很多时会拖慢主线程，所以 Redis 不这么做。
