## 一句话
长轮询是消费者发起拉取后，如果 Broker 暂时没有消息，就先挂起这个请求，等有消息或超时再返回，既接近实时又减少空请求。

## 要点
- [kp1|3] 消费者向 Broker 发拉取请求，仍是拉模式
- [kp2|3] 没有消息时，Broker 不立即返回，而是把请求挂起等待
- [kp3|2] 有新消息到达或等待超时，Broker 立即返回响应
- [kp4|2] 有消息时几乎秒回，没消息时不会频繁发空请求
- [kp5] Kafka 和 RocketMQ 都用长轮询弥补拉模式的缺点

## 详解
### 先搞懂：在柜台前等叫号
你去窗口办事，问“我的材料好了吗”。普通轮询的做法是：工作人员看一眼，说“没好”，你走开，五分钟后再来问一遍，来来回回很折腾。

长轮询的做法是：你站在窗口前，工作人员说“你先在这等着，好了我马上叫你”。你等一会儿，材料好了立刻拿到，等了很久还没好，工作人员告诉你“还没好，先回去吧”，你再重新来一次。

先说几个词：

- **普通轮询**：每隔一小段时间问一次，Broker 当场回答有或没有。
- **挂起**：Broker 先不回复，把请求暂存，等条件满足再回复。
- **超时返回**：等了设定的时间还没有消息，就返回一个空结果。

### 长轮询的流程
1. 消费者向 Broker 发拉取请求，并带上最长等待时间（比如几秒或几十秒）；
2. 如果 Broker 此刻有消息，立刻返回；
3. 如果没有消息，Broker 把请求挂起；
4. 挂起期间一旦有新消息到达，立即用它回复这个请求；
5. 一直没有消息，等到超时，返回空结果；
6. 消费者收到响应后，马上再发下一次拉取请求。

### 为什么这样做更好
- **延迟低**：消息到达后立刻返回，不用等下一个轮询周期；
- **请求少**：没有消息时一次请求可以覆盖很长一段等待时间，不会每隔几百毫秒就空跑一次。

### 要注意的地方
挂起的请求会占用连接和 Broker 的资源，消费者很多时要考虑数量。超时时间也要合理：太短会退化成频繁的空轮询，太长可能被中间的网络设备断开。

## 示例
```java
// 长轮询伪代码：请求最多在 Broker 处等待 30 秒
while (running) {
    List<Message> msgs = broker.pull("order-topic", 32, 30_000);
    msgs.forEach(this::handle);
}
```

## 易错点
- 以为长轮询是 Broker 主动推送；请求依然是消费者发起的
- 以为长轮询完全没有空请求；超时时仍会返回一次空结果

## 追问
### [f1] 长轮询和 WebSocket 有什么区别？
长轮询仍是一问一答，每次响应后要重新发请求。WebSocket 建立后是长期的双向连接，服务端可以随时主动发消息。
