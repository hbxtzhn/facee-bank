## 一句话
最常用的办法是让所有线程按同一个顺序加锁；也可以一次拿齐所有锁，或者用 tryLock 带超时去拿，拿不到就放弃已有的锁重来。

## 要点
- [kp1|3] 统一加锁顺序，破坏循环等待，是最常用、最实用的办法
- [kp2|3] 用 tryLock 带超时获取锁，拿不到就释放已持有的锁，破坏不可剥夺
- [kp3|2] 一次性获取所有需要的锁，破坏持有并等待，但会降低并发度
- [kp4|2] 缩小锁的范围，持锁时不要调用外部方法或做耗时操作
- [kp5] 出问题时用 jstack 查看线程栈定位死锁

## 详解
### 先搞懂：别让两个人在窄路上碰头
转账时，线程 1 先锁账户 A 再锁账户 B，线程 2 先锁 B 再锁 A，就可能互相卡住。避免死锁的思路，就是让这种「相向而行」不会出现：

- 规定大家都走同一个方向（统一顺序）；
- 或者一次把路全占了再走（一次拿齐）；
- 或者在路上等不下去就退回来重走（超时放弃）。

后文用到的词：
- **加锁顺序**：多把锁一起用时，先拿哪把、后拿哪把。
- **tryLock**：ReentrantLock 提供的「尝试加锁」方法，拿不到可以立刻返回或等一段时间后返回，不会一直卡着。
- **死锁**：线程互相持有对方要的锁，谁也等不到。

### 统一加锁顺序：大家都先拿小号锁
死锁需要「循环等待」，只要所有线程都按同一个顺序拿锁，就不可能形成环。

做法是给每把锁定一个固定的先后，比如转账时按账户 ID 从小到大加锁：不管是 A 转 B 还是 B 转 A，都先锁 ID 小的那个。这样两个线程都先抢同一把锁，抢到的继续，抢不到的等待，不会各占一把互相等。

这是最常用的办法，成本低，也不影响并发。

### 一次性获取所有锁：不要边拿边等
死锁还需要「持有并等待」：拿着一把锁又去等另一把。

做法是线程开始前，一次性把需要的所有锁都申请到，要么全拿到，要么一把都不持有。实现上可以用一个「总锁」包住申请过程，或者统一让一个调度者分配资源。缺点是锁持有的时间变长、范围变大，并发度下降，也要事先知道要拿哪些锁。

### 超时和 tryLock：拿不到就放手重来
`ReentrantLock.tryLock(timeout, unit)` 在超时后返回 false，而不是一直阻塞。线程拿不到第二把锁时，把第一把也释放掉，稍等片刻后重试。这就破坏了「不可剥夺」：虽然别人抢不走，但线程自己主动让出。

注意：多个线程可能同时重试、同时失败，所以重试前最好加一个随机的短暂等待，避免互相谦让没完没了。

### 方案对比：几种避免方法
| 方案 | 破坏的条件 | 做法 | 优点 | 缺点 |
|---|---|---|---|---|
| 统一加锁顺序 | 循环等待 | 所有线程按固定顺序拿锁 | 简单，不影响并发 | 需要所有代码遵守约定 |
| 一次性获取所有锁 | 持有并等待 | 先拿齐再执行 | 不会中途卡住 | 锁占用时间长，并发度低 |
| tryLock 加超时 | 不可剥夺 | 拿不到就释放已有锁并重试 | 不会无限等待 | 要处理失败和重试逻辑 |

结论：默认用统一加锁顺序；做不到顺序统一（例如锁是运行时动态决定的）时，用 tryLock 加超时兜底。

### 进阶：设计上少用嵌套锁（基础薄弱可先跳过）
- 持锁期间尽量不要调用外部方法（回调、不明来源的代码），它们可能又去拿别的锁。
- 能不用锁就不用：不可变对象、局部变量、原子类都不会产生死锁。
- 即使已经设计过，上线后也要有排查手段，用 `jstack` 检查线程栈中的死锁提示。

## 示例
```java
// 按 id 从小到大加锁，避免 A->B 与 B->A 同时转账时死锁
void transfer(Account from, Account to, int amount) {
    Account first = from.id < to.id ? from : to;
    Account second = from.id < to.id ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.balance -= amount;
            to.balance += amount;
        }
    }
}

// tryLock 带超时：拿不到第二把锁就释放第一把
if (lock1.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lock2.tryLock(1, TimeUnit.SECONDS)) {
            try { /* 业务逻辑 */ } finally { lock2.unlock(); }
        }
    } finally { lock1.unlock(); }
}
```

## 易错点
- 只在部分代码里统一顺序，别的代码仍按相反顺序加锁，死锁依旧会发生
- 用 tryLock 拿到第一把锁后，拿不到第二把就直接返回，却忘了释放第一把
- 以为加上超时就不会有问题；超时只是不再无限等，业务上仍要处理失败

## 追问
### [f1] 锁是运行时动态决定的，怎么统一顺序？
可以用一个稳定的标识来排序，比如对象的业务 ID；没有 ID 时可以比较 `System.identityHashCode`，但它可能重复，重复时需要再加一把全局锁来决出先后。

### [f2] 为什么说破坏互斥条件通常做不到？
锁的目的就是互斥，去掉互斥就等于不保护共享数据。能做的是减少需要互斥的场合，比如使用不可变对象或线程本地变量。
