## 一句话
`!=` 和 `<>` 命中的是除某个值之外的大部分行，这些行分散在索引两端，走索引要回表太多次，所以优化器一般选全表扫描。

## 要点
- [kp1|3] `!=` 命中的行分散在索引两端，不像等值那样集中在一小段
- [kp2|3] 优化器估算命中比例高，就会选全表扫描
- [kp3|2] 是否走索引由优化器根据数据分布决定，不是语法一律禁止
- [kp4] 变通写法：拆成范围条件，或在值很少时枚举成 `IN`

## 详解
### 先搞懂：找「不是某个人」比找「是某个人」难
班里 50 个人，找「叫张三的」，翻花名册按姓名排序的那一页就行。但找「不叫张三的所有人」，几乎要把整本花名册都看一遍。`!=` 就是后一种。

后文用到的术语：

- **索引**：按某列排好序的目录，像花名册按姓名排序。
- **全表扫描**：不用索引，从头到尾一行一行看。
- **优化器**：MySQL 里负责挑选执行方式的部分。

### 为什么索引帮不上忙
索引是排好序的。等值查询 `name = '张三'`，命中的行在索引里挨在一起，一次定位就能全部取到。

而 `name != '张三'`，命中的是除张三之外的所有行，在索引里分在张三的左边和右边两头，数量通常占了表的绝大部分。

### 优化器怎么选
走索引后，每个命中的行还要回表取完整数据。命中的行很多时，大量的回表比直接从头扫描整张表更慢。优化器会估算两种方式的代价，选更便宜的，结果往往是全表扫描。

所以准确地说：不是 `!=` 一定不能用索引，而是通常情况下用索引不划算。如果某个值占了表的绝大多数行，比如 99% 的订单状态都是「已完成」，那么 `status != '已完成'` 命中的很少，优化器可能选择走索引。

### 能怎么改写
1. **拆成范围条件**：`age != 18` 可以写成 `age < 18 OR age > 18`，更多时候是拆成两条 SELECT 用 `UNION ALL` 合并，每条走各自的范围索引；
2. **枚举**：状态只有几个固定值时，把「不等于已完成」改写成 `status IN ('待支付', '已取消')`；
3. **换思路**：看是否真的需要「不等于」，也许业务上可以改成查具体要的那几种状态。

### 怎么确认
不要凭印象判断，用 `EXPLAIN` 看实际的 `key` 和 `type`，以优化器真实的选择为准。

## 示例
```sql
-- 通常是全表扫描
EXPLAIN SELECT * FROM orders WHERE status != 'done';

-- 状态值有限时，改写成 IN，更容易用上索引
EXPLAIN SELECT * FROM orders WHERE status IN ('pending', 'canceled');
```

## 易错点
- 以为 `!=` 在任何情况下都绝对用不了索引；命中行很少时，优化器可能选择走索引
- 把原因理解成语法限制；实际是优化器估算代价后做出的选择
- 用 `OR` 拼出两个范围就以为一定走索引；要用 `EXPLAIN` 验证

## 追问
### [f1] 为什么 `IS NOT NULL` 也经常不走索引？
道理类似：表里大多数行不是 NULL 时，命中的行占比很高，走索引后回表代价大，优化器就会选全表扫描。
