## 一句话
被查询得很频繁、而且关联的数据几乎不变时，可以把对方表的字段直接存一份到本表，省掉 JOIN。代价是要自己维护两边数据一致。

## 要点
- [kp1|3] 冗余字段：把关联表里的字段复制一份存在本表，查询时不用 JOIN
- [kp2|3] 适合读多写少、关联数据很少变化的场景
- [kp3|2] 代价是一致性：源数据改了，所有冗余副本都要同步
- [kp4] 同步可以靠业务代码、事务或异步消息，但都有出错的可能
- [kp5] 先确认 JOIN 真的慢，再考虑冗余，索引能解决就不冗余

## 详解
### 先搞懂：订单列表里的用户名
订单列表页要显示「下单人昵称」。昵称在用户表里，订单表只有 `user_id`。每次打开列表都要 JOIN 用户表，才能拿到昵称。

类比：快递单上，如果只写「收件人编号」，每次派件都要回总部查名册；直接把姓名也抄在单子上，派件时看一眼就行。代价是：收件人改名了，已经写好的单子就得跟着改。

后文会用到这几个词：

- **冗余字段**：本来存在别的表里的数据，在本表里再存一份。
- **反范式设计**：为了读得快，有意允许数据重复。
- **一致性**：同一份数据在不同地方的值要保持相同。

### 什么时候值得冗余
同时满足下面几条，冗余才划算：

1. 这个查询非常高频，JOIN 的开销已经能感觉到；
2. 要冗余的字段很少变化，比如商品名称、分类名称；
3. 这个字段不改，或者晚一点才改，业务也能接受。

有些场景天然适合冗余：订单里存下单时的商品名称和单价。这不是偷懒，而是业务要求的「快照」。商品后来改价，历史订单不该跟着变。

### 代价：数据一致性
冗余之后，一份数据变成多份。源数据修改时，要保证所有副本一起更新：

- 同一个事务里更新多张表：简单，但更新的行多了，锁和耗时都会上升；
- 业务代码里漏改一处，数据就悄悄不一致了；
- 异步同步（消息、定时任务）：存在短暂不一致，要接受「最终一致」。

所以变化频繁、副本很多的字段，不建议冗余。

### 先试试别的办法
在冗余之前，先看更便宜的手段：

- 连接列有没有索引，`EXPLAIN` 里是不是在扫全表；
- 能不能先查出一批 id，再批量查一次关联表，在应用层拼；
- 热点数据能不能放缓存。

## 示例
```sql
-- 订单表直接存下单人昵称，列表查询不再 JOIN 用户表
ALTER TABLE orders ADD COLUMN user_nick VARCHAR(64) NOT NULL DEFAULT '';

SELECT id, user_nick, amount
FROM orders
WHERE created_at >= '2026-11-01';
```

## 易错点
- 一说性能就冗余；很多慢查询只是缺索引，冗余并没有解决根因
- 冗余了经常变化的字段，结果同步逻辑比 JOIN 还复杂
- 只改了源表，忘了更新冗余字段，页面上就出现新旧两种数据

## 追问
### [f1] 冗余字段怎么保证和源数据一致？
常见做法是在更新源数据的同一个事务里一并更新副本；跨服务时用消息异步同步，接受最终一致。再配一个定期对账的任务，发现不一致就修正。

### [f2] 冗余和反范式是一回事吗？
冗余是反范式设计里最常见的手段。反范式的意思是为了读得更快，有意不完全遵守范式，允许数据重复。
