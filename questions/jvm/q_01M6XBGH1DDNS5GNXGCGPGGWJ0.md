## 一句话
内存溢出是申请内存时发现空间不够，抛出 OutOfMemoryError；内存泄漏是不再使用的对象一直释放不掉。泄漏攒得多了，就会引发溢出。

## 要点
- [kp1|3] 内存溢出是结果：申请内存时空间不足，Java 里表现为 OutOfMemoryError
- [kp2|3] 内存泄漏是原因：对象已经没用了，却仍被引用，GC 回收不掉
- [kp3|2] 泄漏长期累积会让可用内存越来越少，最终导致溢出
- [kp4] 溢出不一定是泄漏：一次性加载超大数据或内存参数太小，也会溢出

## 详解
### 先搞懂：一个是“装不下”，一个是“东西没人清”
想象一个仓库。

- 货架已经放满，新货进不来，这是**溢出**；
- 有些货早就不用了，但没人搬走，天天占着位置，这是**泄漏**。

泄漏不会马上让仓库爆满，而是慢慢占满；占到最后新货进不来，就变成溢出。但仓库本来就小，或者一次性运来一大批货，也会装不下，这时候并没有泄漏。

后文用到的术语：
- **GC（垃圾回收）**：JVM 自动清理没人用的对象；
- **可达**：从程序还在用的变量出发，能顺着引用找到某个对象，它就是可达的，GC 不会回收可达对象。

### 内存溢出：申请时发现不够
程序创建对象、数组时，JVM 要在对应内存区域里划一块空间。GC 回收之后仍然不够，JVM 就抛出 `OutOfMemoryError`（简称 OOM）。

常见触发情况有两类：
- 一次性申请太大：比如把一个很大的文件整个读进内存，或一次查出几百万行数据；
- 内存参数设得太小：业务本身需要的内存，就比堆上限大。

### 内存泄漏：对象没用了，却还被引用着
Java 靠“可达性”判断能不能回收。一个对象业务上已经不用了，但某个长期存活的对象还持有它的引用，它依然可达，GC 就不能回收。

典型例子：往静态的 `Map` 里放缓存，只放不删。`Map` 活多久，里面的对象就活多久。

### 两者的关系
| 对比项 | 内存溢出 | 内存泄漏 |
|---|---|---|
| 本质 | 空间不够用 | 无用对象释放不掉 |
| 表现 | 抛出 OutOfMemoryError | 可用内存逐渐减少，GC 越来越频繁 |
| 发生时机 | 申请内存的那一刻 | 长期运行中慢慢累积 |
| 能否独立出现 | 能，如一次申请过大 | 能，量小时不会报错 |

结论：泄漏是病因之一，溢出是发作的结果；排查时先判断是“装得太多”还是“清得不够”，再决定是调大内存还是改代码。

## 易错点
- 把两者当成同一件事；泄漏量小时程序可以长期正常运行，不会报错
- 以为出现 OOM 就一定是泄漏；一次性处理超大数据同样会 OOM
- 以为调大堆内存能解决泄漏；泄漏只是被推迟发生，根因没有消除

## 追问
### [f1] Java 有 GC，为什么还会内存泄漏？
GC 只回收不可达的对象。对象业务上没用了但仍被引用，就不会被回收。典型是静态集合只加不删、资源没关闭。

### [f2] 怎么区分是泄漏还是单纯内存不够？
观察每次 Full GC 之后的堆占用：如果回收后仍然越来越高，通常是泄漏；如果回收后很低，只是峰值时放不下，更像是内存不够或一次申请过大。
