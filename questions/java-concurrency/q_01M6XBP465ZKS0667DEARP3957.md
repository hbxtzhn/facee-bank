## 一句话
写 volatile 变量后新值要让别的线程可见，读时必须读到最新值；底层靠内存屏障和缓存一致性实现。

## 要点
- [kp1|3] 写 volatile 后，新值要让其他线程可见，模型上叫刷回主内存
- [kp2|3] 读 volatile 时不能用旧缓存，要读到最新值
- [kp3|2] 底层靠内存屏障指令实现，JMM 说的写屏障、读屏障是简化模型
- [kp4] 每次读写 volatile 都有同步开销，不要滥用

## 详解
### 先搞懂：便签纸和白板
还是办公室的比方：白板上是公共数据（主内存），每个人手边有便签纸（线程的工作内存，其实对应 CPU 缓存和寄存器）。平时大家抄了数字回自己座位做事，别人改了白板你不知道。

volatile 的规矩是两条：改了数字，马上写回白板；读数字，别看便签，重新看白板。后文术语：

- **主内存、工作内存**：Java 内存模型用来描述线程怎么共享变量的抽象概念，并不是电脑里真有两块这样的内存。
- **内存屏障**：一种特殊的 CPU 指令，规定在它之前的读写必须先完成，才能执行它之后的。

### 写操作：改完要让别人看到
线程写 volatile 变量时，JVM 通常会在写之后插入一个写屏障。效果是把工作内存里的新值刷新到主内存，同时让其他线程缓存里的旧值失效。

### 读操作：不用旧的，读最新的
线程读 volatile 变量时，JVM 通常会在读之前插入读屏障。效果是从主内存重新读取这个变量，而不是用自己缓存的旧值。

这样，一个线程写入之后，另一个线程再读就一定能读到新值。

### 实际底层是怎么做的
上面「刷回主内存、从主内存取」是 JMM 的简化讲法。真实的硬件上，CPU 之间靠缓存一致性协议工作，保证各核缓存里的同一数据不会长期不一致。JVM 在 volatile 读写处生成相应的屏障指令，让写入不会停留在缓冲区里，读取也不会用过期数据。不同 CPU 架构生成的指令不同，所以面试里回答到「内存屏障 + 强制读写主内存」就够了。

### 进阶：为什么说屏障是简化模型（基础薄弱可先跳过）
JMM 规范本身是用 happens-before 来定义 volatile 的。对 volatile 变量的写，happens-before 之后对它的读。屏障是 JVM 为了满足这个规范，在不同平台上采用的实现手段。它并非规范的一部分。

## 示例
```java
class Flag {
    private volatile boolean stop = false;

    void stopIt() {
        stop = true;          // 写：新值对其他线程可见
    }

    void loop() {
        while (!stop) {       // 读：每次都读最新值
            // 做事
        }
    }
}
```

## 易错点
- 以为 volatile 把变量放在某个特殊内存里；它只是约束读写时的可见性规则
- 以为有了写屏障读屏障就能保证 `count++` 安全；可见性不等于原子性
- 以为所有平台的屏障指令都一样；不同 CPU 的实现不同，规范只规定效果

## 追问
### [f1] 为什么普通变量没有这种保证？
普通变量的读写可以停留在 CPU 缓存或缓冲区里，也可能被编译器优化成只读一次寄存器，所以另一个线程的修改可能很久看不到。

### [f2] volatile 写之前的普通变量修改也能被看到吗？
能。写 volatile 之前的普通写入，不会被重排到它之后；读线程读到 volatile 新值后，也能看到这些普通变量的修改。
