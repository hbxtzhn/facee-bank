## 一句话
数据库修改后，把变更消息发到消息队列，由缓存服务消费消息再更新或删除缓存，缓存会稍晚一点变成新值，达到最终一致。

## 要点
- [kp1|3] 业务改完数据库，向 MQ 发一条变更消息
- [kp2|3] 缓存服务消费消息，再删除或更新对应缓存
- [kp3|2] 这是异步更新，存在短暂延迟，只保证最终一致
- [kp4|2] 消费失败可以重试，重复消费要做到幂等
- [kp5] 业务代码和缓存更新解耦，缓存逻辑集中在消费端

## 详解
### 先搞懂：改完数据，贴个便条通知别人
你修改了一份公共文件，不用挨个通知所有同事，只要在公告栏贴一张便条「文件已更新」。关心这份文件的人看到便条，就去更新自己手里的副本。

消息队列就是这块公告栏。业务服务只负责改数据库、发消息，缓存服务订阅消息，各自负责更新缓存。

后文用到的术语：

- **MQ（消息队列）**：暂存消息、让生产者和消费者异步通信的中间件，如 RocketMQ、Kafka。
- **最终一致**：允许短暂不一致，但过一会儿两边会一致。
- **幂等**：同一操作重复执行，结果不变。

### 流程
1. 业务服务修改数据库。
2. 业务服务向 MQ 发送一条消息，内容是被修改的数据 ID 或变更后的值。
3. 缓存服务从 MQ 取出消息。
4. 缓存服务删除（或更新）对应的缓存。

下次有读请求，缓存没有就从数据库加载最新值。

### 为什么这样做
- **解耦**：业务代码不用直接处理缓存，缓存逻辑集中在消费端。
- **可重试**：缓存更新失败，消息还在队列里，可以重新消费，比业务线程里直接失败可靠得多。
- **削峰**：写入高峰时，消息先排队，缓存更新可以平稳处理。

### 要注意什么
- **数据库修改和发消息要可靠**：数据库改成功但消息没发出去，缓存就永远是旧值。常见做法是使用事务消息，或把消息写进本地消息表。
- **消息可能重复**：重试或重复投递会让同一条消息被处理多次，删除缓存天然幂等，更新缓存要小心顺序。
- **消息顺序**：同一个数据的多条消息要按顺序处理，否则旧值可能覆盖新值。可以按数据 ID 分区保证顺序。
- **有延迟**：消息处理之前，缓存里仍是旧值，所以只适合允许短暂不一致的场景。

## 易错点
- 以为 MQ 方案是强一致；它是最终一致，有延迟窗口
- 数据库改成功但消息发送失败，没有补偿；缓存会长期是旧值
- 更新缓存时不考虑顺序；旧消息后到可能覆盖新值

## 追问
### [f1] 这个方案和 canal 方案有什么区别？
MQ 方案要业务代码主动发消息，有侵入。canal 通过读取 MySQL 的 binlog 获得变更，业务代码不用改，也不会因为忘记发消息而漏掉变更。
