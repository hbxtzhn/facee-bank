## 一句话
忙等待锁拿不到锁就原地循环检查，一直占着 CPU；无忙等待锁拿不到就让出 CPU 去阻塞，锁释放后再被唤醒。

## 要点
- [kp1|3] 忙等待锁（自旋锁）获取失败后，线程在 CPU 上循环检查锁是否空闲
- [kp2|3] 无忙等待锁获取失败后，线程让出 CPU，进入阻塞状态
- [kp3|2] 锁释放时，阻塞的线程会被唤醒，重新尝试加锁
- [kp4|2] 锁持有时间很短，适合忙等待；等待较久，适合阻塞
- [kp5] 忙等待依赖原子操作（如 CAS）实现

## 详解
### 先搞懂：排队等电梯
你按了电梯，电梯还没来。有两种等法：一种是站在电梯口一直盯着楼层数字（忙等待），另一种是回座位继续看手机，电梯到了有人叫你（阻塞后被唤醒）。

盯着看的好处是电梯一到立刻上去；坏处是你什么别的事也干不了。

后文会用到几个词：

- **忙等待（自旋）**：线程不停循环检查条件，不让出 CPU。
- **阻塞**：线程暂停执行，等待某事件，不占 CPU。
- **唤醒**：事件发生时，系统让阻塞的线程重新变为可运行。
- **原子操作**：一次完成、中间不会被打断的操作。

### 忙等待锁：不停地问
线程拿不到锁，就在一个循环里反复用原子指令（如 CAS，比较并交换）尝试加锁。

好处是没有进入内核、没有上下文切换，锁一释放就能立刻拿到。坏处是等待期间白白占用 CPU 时间。持有锁的线程如果很久不放，等待的线程就一直空转。

### 无忙等待锁：让出 CPU
线程拿不到锁，就把自己挂到等待队列里并让出 CPU。锁被释放时，系统从队列里唤醒一个线程，让它重新尝试加锁。

好处是等待期间不浪费 CPU。坏处是阻塞和唤醒要进入内核，涉及上下文切换，这本身有开销。

### 怎么选
- 临界区非常短、锁很快就会释放：忙等待更合适，因为阻塞和唤醒的成本可能比等待本身还大。
- 临界区较长或可能要等 IO：阻塞更合适，别的线程可以利用这段时间的 CPU。
- 单核 CPU 上，忙等待通常没有意义，因为持锁线程根本没机会运行。

### 方案对比：两种锁
| 维度 | 忙等待锁 | 无忙等待锁 |
|---|---|---|
| 拿不到锁时 | 原地循环检查 | 让出 CPU，阻塞 |
| 等待期间 CPU | 被占用 | 不占用 |
| 是否有上下文切换 | 没有 | 有 |
| 适合 | 持锁时间很短 | 等待时间较长 |

结论：锁持有时间很短、且是多核时用忙等待锁；其他情况默认用会阻塞的锁。

## 易错点
- 以为忙等待锁一定更快；等待时间长时，空转反而浪费 CPU
- 以为阻塞锁完全没有开销；挂起和唤醒要切换上下文
- 在单核机器上用自旋锁；持锁线程得不到 CPU，自旋只是空耗

## 追问
### [f1] Java 里有这两类锁吗？
有。`synchronized` 和 `ReentrantLock` 在竞争时会让线程阻塞；其实现中也会在阻塞前先短暂自旋。基于 CAS 的自旋写法也可以自己实现。
