## 一句话
配置中心把各服务的配置集中放在应用之外统一管理，应用启动时从中拉取配置，修改后还能在运行中刷新，不用重新打包或重启。

## 要点
- [kp1|3] 配置存放在应用之外的集中服务里，如 Nacos Config
- [kp2|3] 应用启动时从配置中心拉取配置，运行中配置变了可以动态刷新
- [kp3|2] 同一份配置可以按环境、按服务分开管理，不用每台机器各改一份
- [kp4] 常见实现有 Nacos Config、Spring Cloud Config、Apollo

## 详解
### 先搞懂：配置散在各处有多麻烦
比如数据库地址、线程池大小、功能开关，原来都写在每个服务自己的 `application.yml` 里。服务有几十个、每个服务又部署多台，想改一个开关，就得逐个改配置、重新打包、重启。改漏一台，线上行为就不一致。

配置中心像公司的公告栏：规则只贴在一个地方，大家都来这里看；规则变了，改一处就行。

后文用到的术语：
- **配置中心**：专门保存和下发配置的服务。
- **动态刷新**：配置变了，运行中的应用不重启就用上新值。
- **命名空间、分组**：Nacos 里区分环境（开发、测试、生产）和业务的方式。

### 配置中心做了什么
1. **集中存储**：配置放在配置中心里，应用本地只保留连接配置中心所需的少量信息。
2. **启动拉取**：应用启动时按服务名、环境去配置中心取对应配置，合并到自己的环境里使用。
3. **动态刷新**：在配置中心页面改了值，应用监听到变化后更新配置，标注了 `@RefreshScope` 的 Bean 会用新值重新创建。
4. **环境隔离和版本**：开发、测试、生产的配置分开放；一般还支持查看历史版本和回滚，具体能力取决于所选产品。

### 适合放什么，不适合放什么
适合放会变动的参数：线程池大小、限流阈值、功能开关、第三方地址。数据库密码等敏感信息要看配置中心是否支持加密和权限控制，不能想当然明文放进去。

## 示例
```yaml
# 应用侧：让 Spring Cloud 应用从 Nacos 读取配置
spring:
  application:
    name: order-service
  config:
    import: "nacos:order-service.yaml"
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
```

## 易错点
- 以为所有配置改了都能自动生效；有些值在启动时就用完了，需要用 `@RefreshScope` 等方式才能刷新
- 以为配置中心一挂应用就没法运行；应用通常有本地缓存或启动时才依赖它，具体看实现

## 追问
### [f1] 配置中心和直接用 application.yml 有什么区别？
`application.yml` 随应用一起打包，改一次要重新发布；配置中心把配置放在外面，集中管理、按环境隔离，运行中就能改。

### [f2] 配置中心里的配置怎么变化后让应用知道？
Nacos Config 的客户端会监听配置变化，有变化时服务端通知客户端，客户端更新本地配置并触发刷新。
