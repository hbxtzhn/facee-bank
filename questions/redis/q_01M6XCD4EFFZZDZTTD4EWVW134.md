## 一句话
逻辑过期是热点 key 不设真正的过期时间，只在数据里记一个过期时刻；发现过期后，一个线程在后台重建，其他线程先返回旧数据。

## 要点
- [kp1|3] 热点 key 不设 TTL，数据里额外存一个逻辑过期时间
- [kp2|3] 读到数据后比较时间，没过期直接返回，过期才触发重建
- [kp3|2] 抢到互斥锁的线程开新线程重建，自己立刻返回旧数据
- [kp4|2] 重建完成前所有请求都拿旧数据，保证可用但不强一致
- [kp5] 热点数据需要提前预热写入缓存，否则读到空值

## 详解
### 先搞懂：商品牌子上写着「保质期」，但东西不撤架
超市货架上的牛奶过了保质期，一种做法是立刻撤走，顾客就得等店员去仓库取新的，这相当于普通 TTL 过期。另一种做法是东西先留在货架上，同时派一个店员去补货，补好再换掉，顾客这段时间拿到的是旧货。

逻辑过期就是第二种。它专门用来对付热点 key 的击穿：key 从来不会真的消失，所以不会出现「缓存里什么都没有，大家一起冲向数据库」的瞬间。

后文用到的术语：

- **物理过期**：Redis 的 TTL，到点 key 被删除。
- **逻辑过期**：程序自己在 value 里存的时间字段，Redis 并不知道它。
- **预热**：上线前或活动前，先把热点数据写入缓存。

### 逻辑过期：数据里带着自己的过期时间
缓存里存的 value 不再只是业务数据，而是包一层，大致是：

```json
{"expireTime": "2026-11-08T12:00:00", "data": {"id": 1, "name": "商品A"}}
```

读取流程如下：

1. 查缓存。由于热点 key 事先预热过，通常一定能查到。
2. 看 `expireTime`：没过期，直接返回 `data`。
3. 过期了，尝试获取互斥锁。
4. 抢到锁的线程再检查一次是否已重建。确实没有，就**开一个新线程**去查库、写回新数据和新的过期时间，自己不等待，立刻返回旧数据。
5. 没抢到锁的线程说明已有人在重建，直接返回旧数据。

重建线程干活期间，其他请求谁也不会被阻塞。

### 它的取舍：快和稳，换来一点不一致
- 好处：没有线程等待，响应快，数据库同一时刻只被重建线程访问。可用性高。
- 代价：重建完成之前，用户看到的是旧数据，所以不是强一致。
- 额外成本：要预热数据，每个值要多存一个时间字段，代码比互斥锁复杂。

所以它适合热点数据、能接受短暂旧值的场景，比如商品详情、榜单。库存、余额这类要求实时准确的数据不适合。

### 方案对比：互斥锁和逻辑过期
| 方案 | 过期方式 | 没抢到锁的线程 | 一致性 | 性能 |
|---|---|---|---|---|
| 互斥锁 | 物理 TTL | 休眠后重试 | 强一致 | 有等待，较慢 |
| 逻辑过期 | 不设 TTL，存逻辑时间 | 返回旧数据 | 最终一致 | 无等待，较快 |

结论：要求数据实时准确，选互斥锁；热点数据、更看重不卡顿，选逻辑过期。

## 易错点
- 以为逻辑过期要给 key 设 TTL；恰恰相反，热点 key 不设物理过期
- 以为过期后所有线程都去重建；实际只有抢到锁的线程开新线程重建
- 以为返回旧数据是 bug；这正是用一致性换可用性的设计
- 忘了预热；缓存里没有数据时，没法靠逻辑时间判断

## 追问
### [f1] 逻辑过期怎么处理数据库里被删除的数据？
缓存里的旧数据不会自动消失，用户可能一直读到已删除的数据。业务上需要在删除时主动更新或清理缓存，不能只靠逻辑过期。

### [f2] 为什么重建要开新线程，而不是当前线程自己做？
当前线程自己重建会被查库拖慢，这个请求的响应时间变长。交给新线程，抢到锁的请求也能立刻拿旧数据返回。实际常用线程池提交重建任务，不要每次都新建线程。
