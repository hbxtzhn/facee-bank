## 一句话
Minor GC 太频繁，通常是新生代太小、Eden 很快被填满；可以用 -Xmn 增大新生代，同时排查代码里有没有对象创建过快。

## 要点
- [kp1|3] 频繁 Minor GC 的直接原因是 Eden 很快被填满
- [kp2|3] 用 -Xmn 增大新生代，Eden 随之变大，触发频率降低
- [kp3|2] 排查代码是否在循环或高频路径里创建了大量不必要的对象
- [kp4|2] 用 `jstat -gcutil` 或 GC 日志先确认频率，再调整
- [kp5] 新生代不是越大越好，要给老年代留够空间

## 详解
### 先搞懂：垃圾桶小，倒得就勤
Minor GC 在 Eden 区放不下新对象时触发。把 Eden 想成门口的垃圾桶：桶小，或者垃圾产生得太快，就得频繁去倒。要让倒垃圾的次数变少，办法就两个：换大桶，或者少产生垃圾。

后文用到的术语：

- **Eden 区**：新生代里放新对象的区域。
- **-Xmn**：设置新生代大小的 JVM 参数。
- **分配速率**：程序每秒创建多少对象占用的内存。

### 先确认：是不是真的频繁
不要凭感觉，先量化：

- 用 `jstat -gcutil <pid> 1000` 每秒打印一次各区使用率和 GC 次数，观察 Young GC 次数增长得多快。
- 或者打开 GC 日志，看两次 Minor GC 的时间间隔和每次的停顿。

如果间隔只有几百毫秒、每次停顿也很短，可能只是应用本身创建对象很快，不一定有问题；当 Minor GC 占用的时间明显影响了请求延迟，才需要处理。

### 办法一：增大新生代
新生代太小，Eden 就小，很快被填满。用 `-Xmn` 增大新生代，Eden 随之增大，每次回收的间隔就变长，触发频率降低。

要注意两点：

- 堆总大小不变的话，新生代变大，老年代就变小，可能导致对象晋升时老年代放不下，引发 Full GC。必要时同时增大堆总大小。
- 新生代变大后，单次回收通常处理的对象不会成比例增多，因为大部分对象已经死了，但存活对象多的程序要实际测量停顿时间。

### 办法二：减少对象创建
增大新生代只是治标。如果对象创建本来就不合理，要从代码入手：

- 循环里反复 `new` 的临时对象，能否复用或挪到循环外；
- 大量字符串拼接，可以改用 `StringBuilder`；
- 一次查询加载了远超实际需要的数据，应该分页或只查必要字段；
- 用 profiler 或堆分配分析工具，找出分配最多的代码位置。

### 办法三：检查晋升是否过快
如果每次 Minor GC 后很多对象直接进了老年代，说明 Survivor 区太小装不下，对象被迫提前晋升。这时只增大 Eden 不够，还要看 Survivor 区的大小是否合适。

## 示例
```bash
# 观察 GC 情况，每秒一次
jstat -gcutil <pid> 1000

# 启动时增大新生代（数值仅为示例，需按实际情况测量）
java -Xms2g -Xmx2g -Xmn1g -jar app.jar
```

## 易错点
- 以为把新生代调到越大越好；老年代被挤小，可能引发更多 Full GC
- 只调参数不看代码；对象创建过快才是根源时，参数只能缓解
- 没有量化频率就开始调参；先用 jstat 或 GC 日志看数据

## 追问
### [f1] 增大新生代后，单次 Minor GC 会变慢吗？
Minor GC 的主要成本和存活对象数量有关，不和新生代大小成正比。但存活对象很多的程序，单次停顿可能变长，需要实际测量。
