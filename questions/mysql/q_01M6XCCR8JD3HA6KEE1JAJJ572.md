## 一句话
临键锁是记录锁加间隙锁，锁住一条记录和它前面的间隙，区间左开右闭。InnoDB 在可重复读下做范围查询并命中记录时，默认用它。

## 要点
- [kp1|3] 临键锁 = 记录锁 + 这条记录前面的间隙，区间左开右闭
- [kp2|3] 可重复读下，范围查询命中记录时加临键锁
- [kp3|2] 它既防别人改这条记录，也防别人往前面的间隙插入
- [kp4] 唯一索引等值命中一行时，临键锁会退化成记录锁
- [kp5] 读已提交下一般不加临键锁

## 详解
### 先搞懂：记录和它前面的空地一起围起来
假设表里 id 有 1、5、10 三条记录。这些记录把数轴分成几段空隙：(-∞,1)、(1,5)、(5,10)、(10,+∞)。

临键锁的单位是「一条记录加它前面的空隙」。比如对 5 加临键锁，锁住的是 (1,5]：左边不含 1，右边含 5。

类比：每个座位都配一块「它左边的空地」，一起打包出租。

后文会用到这几个词：

- **记录锁**：锁一条索引记录。
- **间隙锁**：锁两条记录之间的空隙。
- **临键锁**：记录锁和间隙锁的组合，区间左开右闭。

### 什么时候生效
在可重复读隔离级别下，InnoDB 对索引扫描默认使用临键锁。典型场景是范围查询：

```sql
SELECT * FROM orders WHERE id > 3 FOR UPDATE;
```

扫描到的每条记录都加临键锁：命中 5，锁 (1,5]；命中 10，锁 (5,10]；最后还会锁住 10 之后直到无穷大的区间。结果是：已有的记录改不了，这些范围内也插不进新行。

### 为什么要这样设计
只锁记录，防不住别人插入新行，会产生幻读。只锁间隙，又防不住别人修改已有记录。两者合在一起，范围内的数据就都不能被别人改动，同一个事务里重复查询，结果一致。

### 它什么时候会变小
- **唯一索引等值查询命中一行**：不需要防止范围里出现新行，临键锁会退化成记录锁。
- **唯一索引等值查询没命中**：退化成间隙锁。
- **非唯一索引等值查询**：除了命中记录的临键锁，还会再对下一个间隙加锁。边界处的细节随版本略有差异，实际以 `performance_schema` 里的锁记录为准。

## 示例
```sql
-- 假设 id 有 1、5、10，可重复读，id 有索引
START TRANSACTION;
SELECT * FROM orders WHERE id > 3 FOR UPDATE;
-- 其他事务：修改 id=5、10，或插入 id=7、20 都会被阻塞

-- 查看当前持有的锁（MySQL 8.0）
SELECT index_name, lock_type, lock_mode, lock_data
FROM performance_schema.data_locks;
```

## 易错点
- 把临键锁理解成「锁记录后面的间隙」；它是记录加上前面的间隙
- 以为任何查询都是临键锁；唯一索引等值查询会退化
- 以为读已提交也加临键锁；大多数情况下它只加记录锁

## 追问
### [f1] 临键锁和间隙锁的区别？
间隙锁只锁空隙，不含记录；临键锁在间隙之外，还锁住右边那条记录本身。

### [f2] 怎么减少临键锁带来的阻塞？
让查询走唯一索引做精确命中，缩小扫描范围，缩短事务；业务允许的话，用读已提交隔离级别。
