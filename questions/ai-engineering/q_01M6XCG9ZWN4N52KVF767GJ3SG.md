## 一句话
工具描述写得不清，模型就会选错工具或填错参数；返回结果又长又乱，会挤占上下文、干扰后续推理，所以两头都要写清楚、收精简。

## 要点
- [kp1|3] 模型只能靠工具的名字和描述决定用不用、怎么用
- [kp2|3] 描述含糊或参数说明缺失，会导致选错工具或填错参数
- [kp3|2] 返回结果冗长、噪声多，会占用上下文并分散模型注意力
- [kp4|2] 返回结果应精简、结构化，出错时给出可读的错误提示
- [kp5] 功能相近的工具要在描述里写明区别

## 详解
### 先搞懂：给新同事留的工具说明书
你让新同事用公司内部系统，如果说明书只写「查询接口」，他不知道什么时候该用、要传什么。如果系统一次吐出一整页乱码，他也得花很久才能找到有用的那行。

模型调用工具就是这种处境。它看不到工具的代码，只能读你写的名字、描述和参数说明，再读返回的文本。

后文用到的术语：
- **工具描述**：告诉模型这个工具做什么、何时用的文字。
- **参数**：调用工具时要填的输入，如城市名、订单号。
- **观察**：工具返回的结果，会被放回上下文。

### 描述不清：选错工具、填错参数
常见问题有：

- 名字和描述太笼统，如叫 `search`，不说明搜什么；
- 两个工具功能相近，描述里没区分，模型随机选一个；
- 参数没说明格式，比如日期该写 2026-11-08 还是 11/08；
- 没说明必填还是可选，模型漏填或乱填。

好的描述要写清四件事：做什么、何时用、参数含义和格式、不能做什么。

### 返回结果差：挤占上下文、干扰推理
工具返回的内容会原样进入上下文。如果一次返回上万字的网页源码或一整张表，会带来两个问题：

1. 占用大量上下文，留给历史和推理的空间变少，成本也更高；
2. 噪声多，模型可能抓错重点，甚至被无关内容带偏。

所以返回前要精简：只返回模型下一步需要的字段，长内容截断或分页，格式保持统一。

### 出错时也要说人话
工具失败时，返回「错误 500」模型不知道怎么办。返回「订单号不存在，请检查是否多了前缀」，模型就能自己修正再试一次。

### 对比：差的和好的工具设计
| 对比点 | 容易出问题 | 更好的做法 |
|---|---|---|
| 描述 | 只写「查询」 | 写明用途、场景、边界 |
| 参数 | 没说明格式 | 写清类型、格式、示例 |
| 返回 | 整张表原样返回 | 只返回关键字段 |
| 错误 | 只有错误码 | 给出原因和修正建议 |

结论：调试 Agent 时，先检查工具描述和返回内容是否清楚，往往比换更强的模型更有效。

## 示例
```json
{
  "name": "get_order_status",
  "description": "按订单号查询订单当前状态。只用于查询，不能修改订单。",
  "parameters": {
    "order_id": "字符串，订单号，形如 A20261108001"
  }
}
```

## 易错点
- 以为模型能看懂工具内部实现；它只看得到名字、描述和返回
- 以为返回的信息越多越好；多余内容会增加成本，还可能误导模型
- 以为只有工具本身会出错；描述写得差同样会导致错误调用

## 追问
### [f1] 工具太多会有什么问题？
工具越多，描述占的上下文越多，模型也更容易选错。可以按场景只提供当前任务需要的工具，或者先让模型检索再选择。

### [f2] 怎么发现工具描述有问题？
看调用日志：如果模型经常选错工具或参数格式不对，通常是描述不够清楚。改描述后重新测试，比改提示词更直接。
