## 一句话
热 key 是短时间内被大量请求访问的 key，它会让所在的 Redis 节点流量、带宽和 CPU 过载，甚至超过单节点的承受能力。

## 要点
- [kp1|3] 热 key 指很短时间内被频繁访问的 key
- [kp2|3] 典型场景是热门商品、热点新闻、秒杀活动的库存
- [kp3|2] 集群里所有请求落在同一个节点，造成流量不均衡
- [kp4] 极端情况下，单个 key 的访问量超过一个节点的处理能力

## 详解
### 先搞懂：为什么一个 key 会拖垮一台机器
设想一个电商大促，某款手机限量抢购。成千上万的用户在同一秒刷新这个商品的详情页，每次都读同一个 key，比如 `product:1001`。

可以类比商场的一个热门柜台：所有人都挤在这一个柜台前，其他柜台冷冷清清。即使商场再大，这个柜台的服务员也忙不过来。

后文用到几个词：

- **OPS**：每秒处理的操作次数，反映 Redis 的繁忙程度。
- **分片**：集群把 key 分散到多个节点，每个 key 只存在一个节点上。

### 热 key 的危害
- **单节点过载**：同一个 key 只在一个节点上，请求都压到这个节点，它的 CPU 和网络带宽被占满。
- **集群负载不均**：其他节点很空闲，加机器也帮不上忙，因为热 key 仍在原来那个节点。
- **超出承受上限**：访问量太大时，这个节点处理不过来，请求变慢甚至超时，连累同一节点上的其他 key。
- **引发连锁问题**：节点不可用，缓存失效，请求打到数据库，数据库也可能被拖垮。

### 常见的热 key 来源
- 热门商品、热点新闻。
- 秒杀活动里的库存。
- 明星的主页或热搜话题。

### 一般怎么应对
先要发现，再处理。发现靠监控，见“怎么监控和发现热 key”。处理方法有：本地缓存热点数据、给热 key 做多个副本分散请求、读写分离等。

## 易错点
- 以为只有读会产生热 key；写入频繁的计数器同样会形成热点
- 以为集群加节点就能解决；一个 key 只在一个节点上，加节点不一定缓解
- 以为热 key 只会拖慢自己；同节点其他 key 也会受影响

## 追问
### [f1] 热 key 和大 key 有什么区别？
热 key 说的是访问次数多，大 key 说的是占用空间大。热 key 压的是节点的请求处理能力，大 key 压的是内存和网络传输。
