## 一句话
Gossip 协议是节点之间定期随机“串门聊天”、互相交换状态的办法，消息像传闲话一样慢慢传遍整个集群。

## 要点
- [kp1|3] Gossip 是节点定期随机挑几个对象交换状态信息
- [kp2|3] 信息一轮轮扩散，最终所有节点看到的状态趋于一致
- [kp3|2] Redis 集群用它做节点握手、发现新节点、传播故障
- [kp4] 没有中心节点，个别节点挂了也不影响传播

## 详解
### 先搞懂：办公室里的“传闲话”
公司来了新同事，没人发全员通知，但过几天大家都认识他了。因为每个人午休时会随机找几个同事聊天，顺便说“最近新来了某某”。几轮聊下来，全公司都知道了。

Gossip（流言）协议就是这个套路。后文会用到几个词：

- **节点**：集群里的一个 Redis 实例。
- **状态信息**：这个节点是否在线、负责哪些槽、主还是从。
- **最终一致**：不要求同一瞬间全体知道，但过一小会儿，大家知道的东西会一样。

### 它怎么工作：随机挑人，顺带捎消息
每个节点按固定节奏做两件事：

1. 随机挑几个其他节点，发一条消息过去；
2. 消息里除了自己的状态，还捎上自己知道的几个别的节点的状态。

收到消息的节点更新自己的记录，下一轮再去告诉别人。这样信息每一轮都扩散一圈，节点再多，也只需要不太多的轮数就能传遍。

### 在 Redis 集群里用在哪
Redis 集群的节点之间通过专用的集群通信端口互相发消息。默认端口是服务端口加 10000。消息主要有 MEET、PING、PONG、FAIL 几种。

- **握手**：新节点被 `CLUSTER MEET` 引入后，靠 Gossip 认识其他节点。
- **发现节点**：PING 和 PONG 里带着别的节点的信息，所以集群能自己长大。
- **传播故障**：某个节点觉得另一个节点挂了，这个判断也会顺着消息传给其他节点。

### 为什么这样设计
不用中心节点，就没有“中心挂了全体失明”的问题。每个节点每次只和少数几个节点通信，节点多了通信量也不会爆炸。代价是信息传到所有人需要一点时间。

## 示例
```bash
# 让 7000 端口的节点认识 7001 端口的节点
redis-cli -p 7000 cluster meet 127.0.0.1 7001
```

## 易错点
- 以为 Gossip 能让所有节点瞬间同步；它只保证过一段时间后趋于一致
- 以为集群需要一个中心节点汇总状态；Redis 集群里每个节点都平等地维护一份

## 追问
### [f1] 为什么不让每个节点每次都和所有节点通信？
节点一多，消息量会按节点数的平方增长，网络扛不住。随机挑少数节点，每个节点的负担很小，信息仍然能很快扩散出去。
