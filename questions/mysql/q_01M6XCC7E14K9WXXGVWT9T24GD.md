## 一句话
SELECT 依次经过连接器、解析器、优化器、执行器，最后由存储引擎读出数据；MySQL 5.7 及以前在连接之后还有查询缓存，8.0 起已移除。

## 要点
- [kp1|3] 顺序：连接器、（5.7 及以前的查询缓存）、解析器、优化器、执行器、引擎
- [kp2|3] 连接器负责建立连接、验证账号和权限
- [kp3|2] 解析器检查 SQL 语法，优化器决定用哪个索引和执行顺序
- [kp4|2] 执行器检查表权限，按方案调用引擎接口，逐行取数据
- [kp5] 查询缓存因命中率低且维护代价大，8.0 起移除

## 详解
### 先搞懂：点一份外卖，经过哪些环节
订外卖时，要先登录账号，然后系统看你点的东西合不合法，再安排最快的配送方案，最后骑手去取餐。

一条 SELECT 的过程类似：先建立连接，再检查语句，再决定怎么查，最后真正去取数据。

后文用到的术语：

- **连接器**：管理客户端连接，验证身份；
- **解析器**：把 SQL 拆开，检查语法并理解它；
- **优化器**：在多种查法里选一种；
- **执行器**：按方案执行，调用存储引擎取数据；
- **查询缓存**：把查询结果缓存起来，下次相同的 SQL 直接返回。

### 顺序：一步步走
1. **连接器**：客户端发来 SQL 前，先要建立连接，验证用户名密码，并读出这个用户有哪些权限。
2. **查询缓存**（仅 5.7 及以前）：以 SQL 文本为键查缓存，命中就直接返回。
3. **解析器**：先做词法分析，识别出哪些是关键字、表名、列名；再做语法分析，检查写法对不对。语法错了会在这里报错。
4. **优化器**：决定用哪个索引，多表连接时先查哪张表。同一条 SQL 可以有多种执行方案，优化器选它认为代价较小的那个。
5. **执行器**：先检查你对这张表有没有查询权限，然后调用存储引擎的接口，一行一行取数据，把满足条件的行返回客户端。

### 为什么移除查询缓存
只要表被更新，这张表上的所有缓存就会失效。更新频繁的表，缓存刚存进去就被清掉，命中率很低，维护它还有额外开销。所以 8.0 把它删掉了。

## 易错点
- 以为 8.0 里还有查询缓存；8.0 已经移除，这一步不存在
- 以为权限只在连接时检查一次；执行器在执行时还会检查表级权限
- 以为优化器一定选出最快的方案；它依据统计信息估算，选出的方案有时并不是最优

## 追问
### [f1] SQL 语法写错，是在哪一步报错的？
在解析器。语法分析发现写法不符合规则，就会返回类似 `You have an error in your SQL syntax` 的错误，不会走到优化器。

### [f2] 为什么说优化器选的不一定最优？
它根据表的统计信息估算各方案的代价。统计信息不准时，估算会偏差，可能选了较慢的索引。
