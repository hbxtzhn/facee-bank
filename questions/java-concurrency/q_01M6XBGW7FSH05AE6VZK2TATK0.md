## 一句话
先看线程数有没有到核心数，没到就建线程；到了就入队列；队列满了且没到最大线程数就再建线程；都满了就走拒绝策略。

## 要点
- [kp1|3] 线程数小于核心数：新建线程执行，即使别的线程空闲
- [kp2|3] 线程数达到核心数：任务先放进队列等待
- [kp3|2] 队列满且线程数小于最大值：创建非核心线程
- [kp4|2] 队列满且线程数已到最大值：交给拒绝策略处理

## 详解
### 先搞懂：餐厅的接客规则
餐厅有固定的几个正式服务员，门口还有等位区。客人来了，规矩是这样的：正式服务员没招满，就先招人来接待；招满了，客人去等位区坐下；等位区坐满了，才临时叫兼职来帮忙；兼职也叫满了，再来的客人只能谢绝。

线程池提交任务的决策就是这个流程。后文术语：

- **核心线程数（corePoolSize）**：正式服务员人数。
- **最大线程数（maximumPoolSize）**：正式加兼职的总人数上限。
- **任务队列（workQueue）**：等位区。
- **拒绝策略**：等位区满、人也满了怎么办。

### 四步决策
调用 `execute()` 提交一个任务，线程池依次判断：

1. **运行线程数小于核心数**：新建一个核心线程来执行这个任务。注意即使其他线程正好空闲，也照样新建，直到线程数凑够核心数。
2. **线程数已达核心数**：任务放入队列，等有线程空闲了再取走。
3. **队列已满，线程数小于最大数**：创建非核心线程，直接执行这个任务。
4. **队列已满，线程数也到最大数**：执行拒绝策略，默认抛出 `RejectedExecutionException`。

### 反直觉的地方：先排队，再扩线程
很多人以为任务多了线程会先涨到最大。实际顺序是：先涨到核心数，再排队，队列满了才继续涨。所以：

- 队列没有上限时，第 3 步永远不会触发，最大线程数没有用；
- 队列容量太大，任务大量排队，响应变慢，线程却长期停在核心数。

### 进阶：具体实现里的小细节（基础薄弱可先跳过）
- 第 2 步入队后，线程池还会再检查一次：如果此时池里已经没有线程了（比如核心线程数为 0），会补建一个线程，避免任务无人处理。
- 使用 `SynchronousQueue` 这种不存储任务的队列时，入队只有在有线程正好在等任务时才成功，否则相当于直接进入第 3 步。

## 示例
```java
// 核心 1、最大 3、队列容量 1
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        1, 3, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1));
// 同时提交 5 个长任务：
// 第 1 个：建核心线程
// 第 2 个：入队列
// 第 3、4 个：队列满，建非核心线程，线程数到 3
// 第 5 个：线程和队列都满，被拒绝
```

## 易错点
- 以为线程数先涨到最大再排队；实际是先排队，队列满了才扩
- 以为有空闲线程就不会新建线程；线程数没到核心数时仍会新建
- 用无界队列还设最大线程数；最大线程数永远用不上

## 追问
### [f1] 为什么设计成先排队、再扩线程？
线程创建和切换都有成本，先用队列缓冲可以避免为短暂高峰创建过多线程。代价是队列大时任务等待时间变长，所以队列容量要合理。

### [f2] 想让线程数先涨到最大再排队，怎么办？
需要换一种队列行为（例如自定义队列，让它在线程数没到最大时拒绝入队）。JDK 默认的线程池不提供这种模式，一般靠调大核心线程数来达到类似效果。
