## 一句话
RedLock 是在多个互相独立的 Redis 实例上依次加锁，过半数成功才算拿到锁；它能缓解主从切换丢锁，但实现复杂、争议较多，通常不推荐。

## 要点
- [kp1|3] 在多个互相独立的 Redis 主节点上分别加锁，不依赖主从复制
- [kp2|3] 过半数实例加锁成功，且总耗时小于锁有效期，才算拿到锁
- [kp3|2] 没拿到锁时，要向所有实例发解锁请求，清理已加的锁
- [kp4|2] 实现复杂、运维成本高，对时钟和暂停的假设有争议
- [kp5] 常见经典部署是 5 个实例，过半就是至少 3 个成功

## 详解
### 先搞懂：把一份登记同时放在五家店
前一题的问题是：一家总店记了账，还没抄给分店就关门了。红锁的想法是：干脆不依赖抄送，同时去五家互相独立的店各登记一份，超过半数登记成功，才算订到位子。

这样即使有一两家店出事，剩下的多数店里仍有记录，后来的人不容易再订到。

后文用到的词：

- **独立实例**：多个互相没有主从关系的 Redis 节点。
- **过半数**：节点总数的一半以上；5 个实例要至少 3 个。
- **锁有效期**：锁自动过期的时间。

### 加锁流程
1. 记下开始时间；
2. 依次向每个实例发 `SET key value NX PX 有效期`，每次请求设一个很短的超时，某个实例不可用时尽快跳过；
3. 全部尝试完，计算总共花了多久；
4. 同时满足两个条件才算成功：过半数实例成功，并且总耗时小于锁的有效期；
5. 实际有效时间要扣掉已经花掉的时间；
6. 失败时，向所有实例发起解锁，清掉已经加上的锁。

### 为什么不推荐
- **复杂**：要部署多套互相独立的实例，加锁、解锁逻辑都比单实例复杂。
- **慢**：一次加锁要请求多个实例，延迟更高。
- **争议**：分布式系统研究者指出，红锁依赖时钟基本准确，进程长时间暂停（比如 GC）也会让它出错；Redis 作者对此有反驳。结论是它的安全性前提并不稳固。
- **替代**：需要强一致，直接用 ZooKeeper 等共识系统更合适；一般业务用单 Redis 锁加数据库兜底。

### 进阶：围栏令牌（基础薄弱可先跳过）
批评者提出的补救办法是“围栏令牌”：每次加锁拿到一个递增的编号，写数据时带上编号，存储端拒绝比已见过的更小的编号。这样即使旧持有者醒来，也写不进去。Redis 锁本身不提供这种编号。

## 易错点
- 以为红锁是在一主多从上加多份锁；它要求的是互相独立的实例
- 以为加锁成功的实例数过半就行；还必须检查总耗时小于有效期
- 以为用了红锁就绝对安全；时钟漂移和进程暂停仍可能带来问题
- 以为红锁能代替业务层兜底；重要数据仍要靠唯一约束或版本号

## 追问
### [f1] 为什么要强调实例互相独立？
如果实例之间有主从关系，复制又是异步的，一个主节点挂了，锁可能随它一起丢。互相独立才能把风险分散。
