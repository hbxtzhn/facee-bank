## 一句话
发现热 key 的关键是统计访问次数：可以在客户端维护调用计数，或在 Twemproxy、Codis 这类代理端统计，也可以借助 Redis 自带的工具。

## 要点
- [kp1|3] 客户端：每次调用 Redis 前后，在本地字典里累加 key 的调用次数
- [kp2|3] 代理端：所有请求都经过代理，在代理上统计各 key 的访问量
- [kp3|2] Redis 自带 `redis-cli --hotkeys`，要求使用 LFU 淘汰策略
- [kp4] `MONITOR` 能看到所有命令，但开销大，不要在线上长时间使用

## 详解
### 先搞懂：发现热 key 就是“数人头”
商场想知道哪个柜台最挤，最直接的办法是在入口或柜台数人。Redis 也一样：谁访问得最多，就是热 key。问题只在于，在哪里数最方便。

后文用到几个词：

- **客户端**：你的应用程序里调用 Redis 的那部分代码。
- **代理**：夹在客户端和 Redis 之间的中间层，所有请求都经过它。

### 方式一：客户端统计
客户端离 key 最近，命令都是从这里发出的。可以在应用里维护一个全局字典，记录每个 key 被调用的次数。

- 优点：实现简单，不用动 Redis 本身。
- 缺点：每个客户端只能看到自己的流量，要把各台应用服务器的数据汇总；还要改代码，每种语言都得做一遍。

### 方式二：代理端统计
如果使用的是基于代理的 Redis 分布式方案，比如 Twemproxy、Codis，所有客户端请求都要经过代理，可以直接在代理里统计。

- 优点：统计的是全局流量，对应用无侵入。
- 缺点：只适用于使用代理的架构；代理本身会增加一点开销。

### 方式三：Redis 自带手段
- `redis-cli --hotkeys`：扫描并找出访问频率高的 key。需要 `maxmemory-policy` 设置为 LFU 类策略，因为它读取的是 LFU 计数。
- `MONITOR`：实时打印服务器收到的所有命令，可以用来抽样分析，但会明显拖慢服务器，不适合在线上长期开启。

### 方案对比：几种发现方式
| 方式 | 统计位置 | 优点 | 缺点 |
|---|---|---|---|
| 客户端统计 | 应用内 | 简单、成本低 | 数据分散，需汇总 |
| 代理端统计 | 代理层 | 全局视角、无侵入 | 依赖代理架构 |
| `--hotkeys` | Redis 实例 | 现成工具 | 要求 LFU 策略，扫描有开销 |
| `MONITOR` | Redis 实例 | 能看到全部命令 | 开销大，只能短时使用 |

结论：有代理就在代理端统计；没有代理就在客户端统计并汇总，必要时短时间用 `--hotkeys` 辅助排查。

## 易错点
- 以为 `redis-cli --hotkeys` 在任何配置下都能用；它需要 LFU 淘汰策略
- 以为 `MONITOR` 开着也没事；它会明显拖慢线上服务
- 以为单个客户端的统计就是全局热点；需要汇总所有客户端

## 追问
### [f1] 发现热 key 之后怎么处理？
常见做法是在应用里加本地缓存，减少对 Redis 的请求；或者把热 key 复制成多个带后缀的副本，随机读取，把流量分散到不同节点。
