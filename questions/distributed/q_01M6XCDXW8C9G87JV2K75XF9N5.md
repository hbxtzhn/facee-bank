## 一句话
ActiveMQ 经典版出现得早，性能和扩展性不如后来的 Kafka、RocketMQ，社区重心也不在这里，所以新项目一般不再首选它。

## 要点
- [kp1|3] 说它被淘汰是偏强的说法，更准确是新项目很少再选
- [kp2|3] 它出现较早，架构设计难以适应大规模、高吞吐的场景
- [kp3|2] 新一代的 Kafka、RocketMQ、Pulsar 在性能和生态上更受关注
- [kp4] 老系统里仍有它，维护和迁移要评估成本

## 详解
### 先搞懂：老牌工具不是不能用，而是不再是首选
就像老款手机，打电话没问题，但摄像头、续航比不上新款。ActiveMQ 是最早一批流行的 Java 消息队列，名气大，实现了 JMS 规范。

后文用到的几个词：
- **JMS**：Java 消息服务规范，定义了消息 API 的写法。
- **吞吐**：单位时间能处理多少消息。
- **选型**：做项目时挑选用哪个中间件。

### 为什么新项目很少选它
- **性能与扩展**：面对大规模流量，它的架构不如 Kafka、RocketMQ 那样专门为高吞吐设计。
- **迭代节奏**：社区更多精力转向新一代产品，新特性和生态支持相对少。
- **生态变化**：云原生、流处理这些新需求，由新中间件承接得更好。

### 它还能用在哪里
一些老系统一直在用 ActiveMQ，业务量不大时运行稳定。新项目里，如果规模小、团队熟悉 JMS，也不是不能用，只是缺乏选它的理由。

ActiveMQ 项目本身仍有后续的产品线，所以更准确的说法是不再主流，不是彻底消失。

### 方案对比：新项目怎么选
| 需求 | 更常见的选择 | 原因 |
|---|---|---|
| 日志、大数据流 | Kafka | 吞吐高、生态成熟 |
| 交易订单、事务消息 | RocketMQ | 原生事务、延时、顺序消息 |
| 复杂路由、中小规模 | RabbitMQ | Exchange 灵活 |
| 多租户、云原生 | Pulsar | 存算分离 |

结论：新项目按需求在上面几个里选；已有 ActiveMQ 的老系统，没有明显问题就不用急着迁移。

## 易错点
- 以为 ActiveMQ 完全不能用；它仍能稳定工作，只是不再是新项目的主流选择
- 把 JMS 当成中间件；JMS 是接口规范，ActiveMQ 是其中一种实现
- 以为淘汰等于立刻要迁移；迁移要评估业务风险和收益

## 追问
### [f1] 老系统用 ActiveMQ，要不要迁移？
先看有没有实际问题：吞吐瓶颈、维护困难、缺少新功能。没有明显痛点就继续用，真要迁就分阶段灰度，别一次切换。
