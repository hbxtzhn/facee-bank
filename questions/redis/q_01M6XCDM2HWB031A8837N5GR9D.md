## 一句话
节点之间定期 PING 和 PONG，一个节点超过 `cluster-node-timeout` 没回应，就被标为主观下线；多数主节点都认可后，升级为客观下线并广播。

## 要点
- [kp1|3] 节点间定期互发 PING，对方回 PONG，用来检测存活
- [kp2|3] 超过 `cluster-node-timeout` 没回应，标为主观下线（pfail）
- [kp3|2] 主观下线的判断会通过 Gossip 消息传给其他节点
- [kp4|2] 多数持槽主节点都认为它下线，才标为客观下线（fail）
- [kp5] 客观下线后会向全集群广播 FAIL 消息

## 详解
### 先搞懂：一个人说你迟到，不算数
班里一个同学没来上课。你给他打电话没人接，你觉得他可能缺勤了，但这只是你自己的看法。要多数同学都说联系不上他，老师才会正式记他缺勤。

Redis 集群发现故障就是这个思路。先说几个词：

- **PING / PONG**：节点互相问“你在吗”和回答“我在”的消息。
- **主观下线（pfail）**：某一个节点自己认为对方挂了，还没经过大家确认。
- **客观下线（fail）**：集群里多数节点都认为对方挂了，正式认定。

### 第一步：定期 PING，超时标主观下线
每个节点会定期给其他节点发 PING。如果在 `cluster-node-timeout` 配置的时间内一直没有收到某个节点的回应，发送方就把它标记为主观下线。

为什么只叫“主观”：也许只是发送方到对方的网络出了问题，对方其实活得好好的。所以不能凭一个节点的判断就开始换主。

### 第二步：靠 Gossip 传播各自的判断
节点发出的 PING 和 PONG 里，会捎带它对其他节点状态的看法。这样，A 认为 B 下线，这个信息会随着消息传给 C、D 等其他节点。

### 第三步：多数认可，升为客观下线并广播
当一个节点收集到的信息显示，持有槽的主节点中，超过一半都认为 B 主观下线，它就把 B 标记为客观下线，并向整个集群广播 FAIL 消息。其他节点收到后，也立即把 B 标记为下线。

这里只统计持有槽的主节点的意见，从节点和没有槽的节点不参与投票。

### 发现之后
如果下线的是持有槽的主节点，它的从节点就会发起故障恢复。这一步见下一题。

## 示例
```bash
# 在 redis.conf 中设置超时时间，单位毫秒（数值仅为示例）
cluster-node-timeout 15000
```

## 易错点
- 以为一个节点说你下线，你就下线；还需要多数主节点认可
- 以为所有节点都有投票权；只有持有槽的主节点才算数
- 把超时时间设得过小，网络稍有抖动就会误判，引发不必要的切换

## 追问
### [f1] 为什么不用一个节点说了算？
单个节点的判断可能是自己的网络出问题。让多数主节点一起确认，可以避免因为个别节点网络抖动就误换主。
