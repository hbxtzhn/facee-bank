## 一句话
API 网关是微服务系统对外的统一入口：所有外部请求先到网关，由它做路由转发、统一鉴权、限流等公共工作，再交给后面的具体服务。

## 要点
- [kp1|3] 网关是系统对外的唯一入口，客户端只需要知道网关地址
- [kp2|3] 网关按请求路径等规则把请求路由转发到对应的微服务
- [kp3|2] 登录校验（如 JWT）、限流等公共逻辑统一放在网关，不用每个服务各写一遍
- [kp4] Spring Cloud 中常用 Spring Cloud Gateway

## 详解
### 先搞懂：为什么需要一个统一入口
系统拆成了用户、订单、商品等十几个服务。如果让手机 App 直接调用每个服务，它要记住十几个地址；每个服务还都要自己写一遍登录校验，改一次规则就要改十几处。

网关就像小区门口的保安室：外面的人都从这个门进，保安登记、查证件，再告诉他去几号楼。楼里就不用每户各设一个保安。

后文用到的术语：
- **路由**：根据请求路径、域名等，决定转发到哪个服务。
- **鉴权**：确认请求者是谁、有没有权限。
- **JWT**：一种带签名的令牌，服务端校验签名就能知道登录信息，不用每次查库。
- **限流**：限制单位时间内放进来的请求量，保护后端服务。

### 网关做的事
1. **路由转发**：比如 `/order/**` 转到订单服务，`/user/**` 转到用户服务。配合注册中心时，可以只写服务名，由网关查出实例地址。
2. **统一鉴权**：在网关校验令牌，没登录或令牌无效的请求直接拒绝，通过的请求把用户信息带给后面的服务。
3. **限流和熔断**：流量太大时在入口处拦下一部分，避免把后面的服务压垮。
4. **其他公共功能**：日志记录、跨域处理、黑白名单、请求头改写等。

### 要注意的地方
网关是所有流量的必经之路，所以要部署多台避免单点故障，并且不要在里面写复杂的业务逻辑，只放通用功能。后端服务也不能完全信任网关，涉及权限的核心判断仍要在服务内做。

## 示例
```yaml
# Spring Cloud Gateway：把 /order/** 转发到注册中心里的 order-service
spring:
  cloud:
    gateway:
      routes:
        - id: order-route
          uri: lb://order-service
          predicates:
            - Path=/order/**
```

## 易错点
- 以为有了网关，服务内部就不用做任何权限控制；网关只做通用拦截，细粒度权限仍要在服务内判断
- 把业务逻辑写进网关；网关变重后，改动风险大，还会成为性能瓶颈

## 追问
### [f1] 网关和注册中心是什么关系？
网关转发时需要知道服务实例地址，通常去注册中心按服务名查实例列表，再做负载均衡。

### [f2] 网关挂了怎么办？
网关部署多台，前面再放一层负载均衡（如 Nginx）分发流量，任意一台挂掉不影响整体。
