## 一句话
读已提交和可重复读靠 MVCC 的读视图实现，区别是读视图生成的时机；串行化靠加锁让事务排队，读未提交基本不做保护。

## 要点
- [kp1|3] 读未提交：普通读直接读最新数据，不做可见性判断
- [kp2|3] 读已提交：每次查询都生成新读视图，只看已提交的数据
- [kp3|2] 可重复读：事务第一次查询时生成读视图，之后一直复用
- [kp4|2] 串行化：读也加锁，事务相互等待，基本不并发
- [kp5] 加锁的当前读不走快照，要靠行锁和间隙锁保证隔离

## 详解
### 先搞懂：隔离级别其实是两套手段
同一个订单，你在查，别人在改。数据库有两个办法让你们不打架：

- 让别人等你：加锁，安全但慢，像银行窗口排队。
- 给你一份旧账本：MVCC，你看旧账本，别人改新账本，互不影响。

四个隔离级别，就是在这两个办法之间选择。

后文会用到的术语：

- **MVCC（多版本并发控制）**：每行数据保留多个历史版本，读操作按规则挑一个版本看。
- **读视图（ReadView）**：一份快照信息，记录创建时有哪些事务还没提交，用来判断某个版本能不能看。
- **快照读**：普通 `SELECT`，读历史版本，不加锁。
- **当前读**：`SELECT ... FOR UPDATE`、`UPDATE` 等，读最新数据并加锁。

### 读未提交：基本没有保护
普通读不加锁，可能读到别的事务还没提交的版本。所以会读到别人还没提交的数据，也就是脏读。

### 读已提交：每次查询都换一份新视图
每次执行查询，InnoDB 都重新生成一个读视图。别人刚提交的改动，在你下一次查询时就能看到。

所以它避免了脏读，但同一事务里两次读同一行，可能因为别人中途提交而结果不同。

### 可重复读：整个事务只用同一份视图
事务里第一次执行普通查询时生成读视图，之后所有查询都复用它。别人后来提交的改动，对你来说都是不可见的，所以反复读同一行结果一致。

### 串行化：靠锁让事务排队
串行化下，关闭自动提交时，普通查询会被隐式改成加共享锁的读。读写互相阻塞，事务近似一个接一个执行。它最安全，但并发能力最差。

### 当前读怎么办：靠锁
可重复读下，快照读用读视图保证一致。但当前读要读最新数据，没法用旧快照，只能加行锁。

范围查询时，InnoDB 还会锁住记录之间的间隙，防止别人往范围里插数据，也就是防止幻读。

### 进阶：读视图依赖版本链（基础薄弱可先跳过）
每行记录带着事务 ID 和回滚指针，回滚指针指向 undo log 里的旧版本。读视图拿版本的事务 ID 做比较，沿着版本链往前找，直到遇到可见的版本为止。

## 易错点
- 以为读已提交不用 MVCC；它同样用读视图，只是每次查询重新生成
- 以为可重复读下 `UPDATE` 也读旧快照；更新读的是最新已提交的数据
- 以为串行化是单线程执行；它是靠加锁让冲突的事务等待

## 追问
### [f1] 可重复读下为什么还要加间隙锁？
快照读靠读视图就不会幻读，但当前读读的是最新数据，别人插入的新行会被看到。间隙锁锁住范围，让别人没法插入。

### [f2] 为什么很多公司把隔离级别调成读已提交？
读已提交下加锁范围更小、间隙锁基本不生效，死锁和锁等待相对少。代价是同一事务里两次读可能不一致，业务要能接受。
