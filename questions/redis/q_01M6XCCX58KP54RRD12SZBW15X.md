## 一句话
Redis 用一个线程按顺序执行命令，省去线程切换和加锁的开销；因为数据在内存、命令很快，CPU 通常不是瓶颈。

## 要点
- [kp1|3] 命令执行由一个主线程按顺序完成，天然不需要加锁
- [kp2|3] 数据在内存里，大多数命令执行很快，瓶颈多在网络
- [kp3|2] I/O 多路复用让一个线程同时监听很多个连接
- [kp4|2] 6.0 起可配置多线程做网络读写，命令执行仍是单线程
- [kp5] 单线程的代价：一条慢命令会阻塞所有其他请求

## 详解
### 先搞懂：一个收银员为什么也不慢
超市只有一个收银员，但他扫码很快，没有人跟他抢扫码枪，也不用商量谁先扫。反过来，如果请十个收银员共用一个收银台，他们反而要互相等、互相让。

Redis 的命令执行就像这个收银员：一个线程，快速依次处理。

后文会用到的术语：

- **线程切换**：CPU 从一个线程换到另一个线程运行，有额外开销。
- **锁**：多个线程改同一份数据时，用来排队的机制，也有开销。
- **I/O 多路复用**：让一个线程同时监听多个网络连接，哪个有数据就处理哪个。

### 为什么选单线程执行命令
- **不用加锁**：同一时刻只有一个命令在改数据，不会出现两个线程同时改同一个 key 的情况，代码也简单。
- **没有线程切换开销**：不用在多个线程之间来回切换。
- **够快**：数据在内存里，大部分命令很快就执行完，瓶颈往往是网络，而不是 CPU。

### 怎么同时服务很多客户端
一个线程不会傻等某一个客户端。Redis 用 I/O 多路复用（Linux 下通常是 epoll），一个线程同时监听很多连接。哪个连接有请求到来，就处理哪个，处理完再看下一个。

### 6.0 之后：网络读写可以多线程
网络读写和协议解析要花不少时间。6.0 起，可以通过配置开启多个 I/O 线程来分担这部分工作。

但执行命令这一步，仍然由主线程完成。所以不需要加锁的好处保留了。

### 单线程的代价
一个命令执行得慢，后面所有请求都得排队。比如对很大的集合执行 `KEYS *`，或一次删除一个超大的 key，整个服务都会卡住。

所以要避免耗时命令，用 `SCAN` 代替 `KEYS`，用 `UNLINK` 异步删除大 key。

## 易错点
- 以为 Redis 整个进程只有一个线程；后台还有持久化、异步删除等线程
- 以为 6.0 之后命令也并发执行；多线程只用于网络读写
- 以为单线程一定不能用多核；可以在一台机器上起多个实例，或用集群

## 追问
### [f1] 单线程怎么处理成千上万的连接？
靠 I/O 多路复用。一个线程让操作系统同时监听所有连接，有连接可读时才去处理，没有请求时不会空等在某一个连接上。

### [f2] 如何避免大 key 阻塞 Redis？
拆分大 key，避免一次性读写大集合；删除时用 `UNLINK`，让后台线程释放内存；遍历用 `SCAN` 分批进行。
