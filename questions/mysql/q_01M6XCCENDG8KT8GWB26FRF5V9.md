## 一句话
主库把修改记到 binlog，由转储线程发给从库；从库的 IO 线程把它写进中继日志，SQL 线程再读中继日志重放，数据就同步了。

## 要点
- [kp1|3] 主库记 binlog，二进制日志转储线程负责把日志发给从库
- [kp2|3] 从库 IO 线程接收日志，写入本地的中继日志
- [kp3|2] 从库 SQL 线程读取中继日志，在本地重放，应用修改
- [kp4] 默认是异步复制，主库提交后不等从库

## 详解
### 先搞懂：快递员、收件箱和拆件人
可以把整个过程想成寄快递：主库把每一次修改写成一张清单（binlog）；快递员（转储线程）把清单送到从库；从库的收件员（IO 线程）把清单放进收件箱（中继日志）；拆件员（SQL 线程）从收件箱里取出清单，按里面写的在自己的库里重做一遍。

几个术语：

- **binlog**：主库的二进制日志，记录所有数据变更。
- **中继日志**：Relay Log，从库本地存放从主库收到的日志的地方。
- **IO 线程**：从库上负责连接主库、接收日志的线程。
- **SQL 线程**：从库上负责读取中继日志并执行的线程。

### 三个线程、三个步骤
1. **主库写 binlog**：主库执行修改语句，事务提交时把变更记到 binlog。
2. **主库发送，从库接收**：主库上有一个二进制日志转储线程，读取 binlog 发给从库；从库的 IO 线程收到后，写入中继日志。
3. **从库重放**：从库的 SQL 线程读取中继日志里的事件，在本地执行，修改和主库一致。

### 为什么要多一个中继日志
有了这一层缓冲，接收和执行互不阻塞：IO 线程只管收，SQL 线程只管执行。即使重放比较慢，日志也能先收下来，不用让主库等着。

### 方案对比：几种复制模式
| 模式 | 主库提交时 | 数据安全 | 延迟影响 | 说明 |
|---|---|---|---|---|
| 异步复制 | 不等从库 | 主库宕机可能丢最新数据 | 对主库写入影响小 | 默认方式 |
| 半同步复制 | 等至少一个从库确认收到 | 更不容易丢数据 | 写入会多一点等待 | 需要配置 |
| 全同步 | 等所有从库执行完 | 最安全 | 写入明显变慢 | 很少采用 |

结论：默认异步复制就够多数场景；对数据丢失更敏感时，考虑半同步。

### 进阶：延迟从哪来（基础薄弱可先跳过）
从库的 SQL 线程只有一个线程串行重放时，如果主库并发写入很多，从库就可能追不上，产生延迟。新版本的 MySQL 支持多线程并行重放来缓解。

## 易错点
- 以为从库直接从主库复制数据文件；实际是传 binlog，再重放语句或行变更
- 以为从库只有一个线程；IO 线程和 SQL 线程是分开的
- 以为主库提交后一定已经到了从库；异步复制下不保证

## 追问
### [f1] 为什么会有主从延迟？
主库写入并发高、从库重放慢，或网络、大事务等原因，会让从库落后。常见缓解手段是多线程重放、拆小事务。
