## 一句话
HotSpot 里 synchronized 的锁会随竞争变激烈，从无锁到偏向锁、轻量级锁，最后变成重量级锁；一般只升不降。偏向锁在 JDK 15 起默认关闭。

## 要点
- [kp1|3] 升级路径：无锁 → 偏向锁 → 轻量级锁 → 重量级锁
- [kp2|3] 锁状态记录在对象头的 Mark Word 里
- [kp3|2] 偏向锁记录线程 ID；轻量级锁用 CAS 加自旋；重量级锁会让线程阻塞
- [kp4|2] 一般只升级不降级，竞争越激烈，锁越重
- [kp5] JDK 15 起偏向锁默认禁用，路径实际变成无锁到轻量级到重量级

## 详解
### 先搞懂：为什么锁要分档位
想象一间会议室。大多数时候只有一个人在用，他进出不用登记；偶尔有两个人错开时间用，在门口贴张便签就够；只有真有人撞上、要排队了，才需要正式找前台登记、让后来的人去休息区等。

synchronized 也是这个思路：没人竞争时用最轻的办法，竞争变激烈再换更重的办法。这样没竞争的场景不用为「重锁」付出代价。

后文用到的术语：

- **对象头**：每个 Java 对象内存里开头的一小块，存着对象自己的元信息。
- **Mark Word**：对象头里的一个字段，用来记录锁状态、哈希码等信息。
- **CAS**：比较并交换，一条原子操作，要么改成功，要么失败。
- **自旋**：拿不到锁时不睡觉，在原地循环再试几次。
- **监视器（Monitor）**：重量级锁背后的那个管理结构，由操作系统的互斥机制支撑。

### 四种状态：从轻到重
1. **无锁**：没有线程在用这个对象当锁，Mark Word 正常存放哈希码等信息。
2. **偏向锁**：第一个线程来时，把自己的线程 ID 写进 Mark Word。之后还是这个线程进来，只比较一下 ID，连 CAS 都省了。别的线程来竞争时，偏向被撤销。
3. **轻量级锁**：多个线程交替使用、基本没有同时抢的情况。线程用 CAS 把 Mark Word 换成指向自己栈上「锁记录」的指针，成功就算拿到锁。抢不到的线程先自旋几次，不直接睡。
4. **重量级锁**：自旋也拿不到，说明真有竞争。这时锁膨胀为监视器，拿不到锁的线程被阻塞，交给操作系统挂起，等持有者释放后再唤醒。阻塞和唤醒都要和操作系统打交道，开销比前几种大。

### 升级触发条件
| 状态 | 触发条件 | 拿不到锁时 | 代价 |
|---|---|---|---|
| 偏向锁 | 只有一个线程反复进入 | 偏向被撤销，转为轻量级锁 | 重入几乎没有同步开销 |
| 轻量级锁 | 多线程交替、没有同时抢 | 自旋 | 一次 CAS，不阻塞 |
| 重量级锁 | 自旋仍失败，或调用了 `wait()` | 线程阻塞 | 要操作系统参与 |

结论：先看有没有竞争再选锁，竞争越激烈升得越高；一般用 synchronized 不用手动选择档位，JVM 自动决定。

### 为什么一般不降级
一把锁升到重量级，说明它这一阵竞争很激烈，马上降回去很可能又要升，来回切换反而浪费。所以通常认为锁只升不降。需要补充的是，偏向锁是可以被撤销的：撤销后若持有者已不在同步块里，对象可以回到无锁状态，或被重新偏向给别的线程，不一定走向轻量级锁。重量级锁的监视器在某些情况下也会被 JVM 回收，所以「不可逆」说的是正常使用中的趋势，不是绝对规则。

### 进阶：版本差异（基础薄弱可先跳过）
- JDK 15 起偏向锁默认禁用（JEP 374），后续版本继续清理这部分实现，所以新版本里不要再背「四级升级」当成现状。
- 锁的具体实现细节随 JDK 版本演进，面试答升级思路和触发条件就够了，不必追位的具体布局。
- 调用 `Object.wait()` 会让锁直接膨胀成重量级锁，因为等待队列在监视器里。

## 易错点
- 以为锁升级是 Java 语言规定的；其实这是 HotSpot 虚拟机的优化，不同虚拟机、不同版本实现不同
- 以为所有锁都经过偏向这一档；JDK 15 起默认没有偏向锁
- 以为偏向锁一被别的线程碰就必然升级；持有者已退出同步块时，可以撤销后重新偏向
- 以为轻量级锁一定比重量级锁快；竞争激烈时自旋空转浪费 CPU，反而不划算

## 追问
### [f1] 偏向锁和轻量级锁有什么区别？
偏向锁适合始终只有一个线程用，之后连 CAS 都省了；轻量级锁适合多个线程交替用，每次加锁要做一次 CAS。

### [f2] 为什么重量级锁慢？
拿不到锁的线程要被操作系统挂起，等到锁释放再唤醒，切换要进入内核，开销比用户态的 CAS 和自旋大得多。

### [f3] 自旋是怎么回事，会一直转吗？
不会。自旋有上限，HotSpot 还会根据历史结果自适应调整；转几次还拿不到，就放弃自旋，升级为重量级锁。
