## 一句话
IO 多路复用是让一个线程同时监视很多个连接，只处理有事件发生的那些，这样就不用给每个连接单独分配一个线程。

## 要点
- [kp1|3] 一个线程通过 select、poll 或 epoll 同时监视多个 socket
- [kp2|3] 只有出现可读、可写等事件的连接才会被处理
- [kp3|2] 为每个连接分配进程或线程，连接多了系统会扛不住
- [kp4|2] select 和 poll 要遍历全部连接；epoll 只返回就绪的连接
- [kp5] select 的监视数量有上限，poll 去掉了这个固定上限

## 详解
### 先搞懂：一个前台管很多房间
酒店如果每个房间都配一个专人守着，人手根本不够。更好的办法是一个前台，哪个房间按了铃，就去处理哪一间。

服务器处理连接同理：每个连接雇一个线程，连接很多时，线程占内存、切换也耗时。多路复用就是那个前台。

后文会用到几个词：

- **socket**：网络连接在程序里的句柄。
- **就绪**：这个连接上有数据可读，或者可以写数据了。
- **事件**：就绪这件事的通知。

### 传统方式的问题
如果每个客户端都要一个进程或线程，连接成千上万时，内存占用和上下文切换的成本都会很高。而且大部分连接多数时间是空闲的，这些线程大多在白白等待。

### 多路复用怎么做
让一个线程把关心的 socket 交给内核，然后问内核：这里面谁有事件？内核返回有事件的那些，线程只处理它们，其他的不管。

### 三种实现
- **select**：把所有连接放进一个集合，整个拷贝给内核。内核遍历检查后标记就绪的，再整个拷回用户态，用户态还要再遍历一遍找哪些就绪。监视数量有上限，一般是 1024。
- **poll**：改用动态数组存连接，突破了固定数量上限。但本质和 select 相同，仍要遍历全部连接。
- **epoll**：连接用 `epoll_ctl` 一次性登记到内核，之后只需要等待，内核只返回就绪的那部分，不需要每次传入全部连接。

### 方案对比：三种机制
| 维度 | select | poll | epoll |
|---|---|---|---|
| 连接存储 | 固定大小集合 | 动态数组 | 内核里的红黑树 |
| 每次调用 | 传入全部连接 | 传入全部连接 | 不用重复传入 |
| 找就绪连接 | 遍历 | 遍历 | 直接返回就绪列表 |
| 连接数量限制 | 有固定上限 | 受系统限制 | 受系统限制 |

结论：连接数量大且活跃连接比例低时，epoll 更合适；连接很少时，三者差别不大。

## 易错点
- 以为多路复用让数据读写变快；它减少的是线程数量和无效等待
- 以为 select 和 poll 本质不同；二者都需要遍历所有连接
- 以为 epoll 在任何场景都更好；连接少且都活跃时优势不明显

## 追问
### [f1] epoll 为什么适合大量连接？
连接只登记一次，不用每次传入全部连接；内核直接返回就绪的，用户态不需要遍历全部。
