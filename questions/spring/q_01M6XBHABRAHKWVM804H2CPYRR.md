## 一句话
服务启动时把自己的地址登记到注册中心，调用方要调用时再去注册中心查当前可用的实例列表，地址不用写死在代码里。

## 要点
- [kp1|3] 服务启动时向注册中心登记自己的名字、IP 和端口
- [kp2|3] 调用方按服务名向注册中心查实例列表，再从中挑一个调用
- [kp3|2] 服务定期发心跳，注册中心据此判断实例是否还活着
- [kp4] 常见实现有 Nacos、Eureka、Consul

## 详解
### 先搞懂：为什么不能把地址写死
订单服务要调用库存服务。最简单的做法是在配置里写死 `http://192.168.1.10:8080`。一旦库存服务扩容成三台、其中一台宕机，或者换了机器、换了端口，订单服务就得改配置、重新发布。

可以把注册中心想成一本公共通讯录：每个服务上线时把自己的名字和电话写进去，下线时划掉。谁要找库存服务，不用记号码，翻通讯录就行。

后文用到的术语：
- **服务提供者**：被调用的服务，比如库存服务。
- **服务消费者**：发起调用的服务，比如订单服务。
- **注册中心**：保存“服务名到实例地址列表”的独立服务，如 Nacos。
- **实例**：同一个服务启动出来的每一个进程，每个实例有自己的 IP 和端口。

### 服务注册：启动时登记，运行中报平安
提供者启动完成后，会把服务名、IP、端口等信息发给注册中心，这一步叫**注册**。

之后它会每隔一小段时间发一次**心跳**，意思是“我还活着”。如果注册中心很久收不到某个实例的心跳，就认为它出了问题，把它从列表里摘掉。正常关闭时，实例也会主动注销。

### 服务发现：调用前先查列表
消费者调用前，向注册中心按服务名查询，拿到该服务当前所有健康实例的地址。通常消费者会把列表缓存在本地，注册中心有变化时再更新，这样即使短暂查不到注册中心，也不影响调用。

列表里有多个实例时，消费者再用负载均衡策略（如轮询）挑一个发请求。所以扩容只需要多启动几个实例，调用方自动就能用上。

### 带来的好处
- 地址不写死，扩容、迁移、故障摘除都不用改调用方的代码。
- 调用方只关心服务名，不关心具体机器。

## 示例
```yaml
# 提供者：把自己注册到 Nacos（Spring Cloud Alibaba）
spring:
  application:
    name: stock-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
```

## 易错点
- 以为注册中心会帮忙转发请求；它只提供地址列表，请求是消费者直接发给提供者的
- 以为注册中心挂了服务就全都不能调用；消费者本地有缓存列表时，通常还能继续调用

## 追问
### [f1] 实例宕机了，注册中心怎么知道？
靠心跳或健康检查：一段时间收不到心跳，或检查不通过，注册中心就把该实例标记为不健康或直接剔除，消费者之后就查不到它了。

### [f2] 常见的注册中心有哪些？
Nacos、Eureka、Consul、ZooKeeper 都能做注册中心。Spring Cloud 项目里常用 Nacos。
