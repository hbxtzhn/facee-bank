## 一句话
联合索引的列顺序要先满足最左前缀：把经常用等值查询、区分度高的列放前面，范围条件的列放在等值列之后，并兼顾排序。

## 要点
- [kp1|3] 联合索引按列顺序依次排序，查询必须从最左边的列开始用起
- [kp2|3] 等值条件的列放前面，范围条件的列放后面
- [kp3|2] 在满足前面两条的前提下，区分度高的列放前面
- [kp4|2] 排序需求要和索引列顺序一致，才能省掉额外排序
- [kp5] 高频查询所需的列，决定了顺序，不是单纯看区分度

## 详解
### 先搞懂：像电话簿先按姓、再按名排序
电话簿先按姓排序，姓相同的再按名排序。要找「姓张名三」，先翻到张姓，再在里面找「三」，很快。但如果只知道名叫「三」，不知道姓，电话簿就帮不上忙，因为「三」分散在每个姓里。

联合索引就是这样一本电话簿。后文用到的术语：

- **联合索引**：由多列按顺序组成的一个索引。
- **最左前缀**：查询必须从联合索引最左边的列开始、连续地用。
- **区分度**：列里不同值的占比，越高越能快速缩小范围。

### 规则一：先满足最左前缀
对索引 `(a, b, c)`：

- 条件里有 `a`，或有 `a, b`，或有 `a, b, c`，可以用上索引；
- 只有 `b` 或只有 `c`，用不上这个索引来定位；
- 有 `a` 和 `c` 但没有 `b`，只有 `a` 能用来定位。

所以查询里最常出现的列，要放在最前面。

### 规则二：等值在前，范围在后
遇到范围条件（如 `>`、`<`、`BETWEEN`）时，这一列之后的列就没法继续用来缩小范围了。因此：

- 等值条件的列放前面；
- 范围条件的列放在等值列后面。

例如查询是 `WHERE status = 1 AND create_time > '2026-01-01'`，索引应该是 `(status, create_time)`，而不是反过来。

### 规则三：区分度高的放前面
在其他条件相当的情况下，区分度高的列放前面，一开始就能把范围缩得更小。但这条的优先级低于前两条：如果高区分度的列只是偶尔用到，而另一列几乎每个查询都用，就应该让常用的在前。

### 规则四：兼顾排序
如果查询要 `ORDER BY`，让索引顺序与排序顺序匹配，就可能省掉额外排序。例如 `WHERE user_id = 10 ORDER BY create_time`，用 `(user_id, create_time)`：定位到某个用户后，里面的数据已经按时间排好了。

### 实际取舍
列顺序没有放之四海皆准的答案，要对照业务里最频繁、最重要的几条查询来定。一个索引服务不了所有查询时，可以建多个，但索引越多，写入越慢、占用空间越大。

## 示例
```sql
-- 常见查询：某用户在某个时间之后的订单，并按时间排序
SELECT id, amount FROM orders
WHERE user_id = 10 AND create_time > '2026-11-01'
ORDER BY create_time;

-- 合适的联合索引：等值列在前，范围兼排序列在后
CREATE INDEX idx_user_time ON orders (user_id, create_time);
```

## 易错点
- 只按区分度排序；把偶尔用到的高区分度列放在最前，常用查询反而用不上
- 把范围条件的列放在等值列前面；后面的列就没法继续缩小范围
- 以为查询里列的书写顺序要和索引一致；优化器会自行调整，关键是列有没有从最左开始

## 追问
### [f1] 查询只用了联合索引的后面几列会怎样？
通常没法用索引来定位，因为后面的列在索引里并不是整体有序的。有时优化器会扫描整个索引来代替全表，但这比直接定位慢得多。
