## 一句话
AOF 把每条写命令追加到文件末尾，重启时按顺序重新执行这些命令来恢复数据；它比 RDB 更实时，是目前主流的持久化方式。

## 要点
- [kp1|3] AOF 记录的是写命令，不是数据本身，只追加不修改
- [kp2|3] 重启时按顺序重放文件里的命令，就能重建数据
- [kp3|2] 通过同步策略控制落盘频率，丢数据的窗口比 RDB 小
- [kp4] AOF 默认不开启，需要配置 `appendonly yes`
- [kp5] 文件会越来越大，需要重写来压缩

## 详解
### 先搞懂：记账本和存折
RDB 像月底拍一张账户余额的照片，AOF 像每笔收支都记在流水账上。账本丢了一页，只丢那一笔；照片则是只有拍照那一刻的信息。想恢复余额，把流水从头算一遍就行。

后文用到的词：
- **写命令**：会修改数据的命令，如 `SET`、`LPUSH`、`DEL`。读命令不会记录。
- **重放**：把文件里的命令按顺序再执行一遍。

### 怎么记录
1. 客户端发来写命令，Redis 执行它；
2. Redis 把这条命令按协议格式追加到内存中的 AOF 缓冲区；
3. 按同步策略把缓冲区写入 AOF 文件并刷到磁盘。

只追加、不修改的写法，磁盘顺序写，速度比较友好，文件也不容易被写坏。

### 怎么恢复
重启时，Redis 读取 AOF 文件，从头到尾把命令执行一遍，内存数据就回到宕机前的样子。Redis 在内部用一个不连接网络的伪客户端来执行这些命令。

### 和 RDB 比的特点
- **更实时**：可以做到每秒甚至每条命令都落盘，丢数据更少；
- **文件更大**：记录的是命令，同一个 key 改一万次就有一万条；
- **恢复更慢**：要重放全部命令，而 RDB 是直接加载数据。

### 文件越来越大怎么办
Redis 提供 AOF 重写，用最少的命令重新生成一份等效的 AOF，缩小文件。这在下一题讲。

## 示例
```conf
appendonly yes
appendfsync everysec
```

## 易错点
- 以为 AOF 默认是开着的；默认关闭，要手动开启
- 以为 AOF 记录所有命令；只记录会修改数据的写命令
- 以为开了 AOF 就一条数据都不会丢；还要看同步策略，默认每秒同步一次

## 追问
### [f1] AOF 文件被写坏了怎么办？
可以用 `redis-check-aof` 工具检查并修复，一般是截掉末尾不完整的那部分命令。修复前先备份文件。
