## 一句话
各个服务把日志、监控、用户行为等数据实时或分批写进消息队列，再由下游把它们导入大数据引擎统一处理。

## 要点
- [kp1|3] 各服务把日志、监控、行为数据作为消息写入队列
- [kp2|3] 队列先承接海量数据，下游按自己的速度消费
- [kp3|2] 数据可以实时写入，也可以攒一批再批量写入
- [kp4|2] 消费端把数据导入大数据处理引擎做分析和计算
- [kp5] 这类场景丢少量数据可以接受，更看重吞吐

## 详解
### 先搞懂：自来水管道里的蓄水池
一个平台有几十个服务，每个服务每秒都在产生日志，用户点击、浏览也会产生行为数据。如果每个服务直接把数据写进分析系统，分析系统一旦慢了或挂了，业务服务也会被拖累。

好比很多住户的水直接接到一个小处理厂，水一多就冲垮。中间加一个蓄水池，住户把水放进池子就行，处理厂按自己的能力慢慢抽。消息队列就是这个蓄水池。

后文术语：
- **数据流**：源源不断产生的数据，像流水一样。
- **生产者**：写入数据的一方，这里是各个业务服务。
- **消费者**：读取数据的一方，这里是大数据处理程序。
- **批量**：攒一批数据一起处理。

### 数据怎么流动
1. **采集**：每个服务把日志、监控指标、用户行为作为消息发给队列，或者由采集程序读取日志文件后再发进去；
2. **缓冲**：队列把数据存起来，业务服务发完就走，不受下游快慢影响；
3. **消费**：下游程序从队列读取数据；
4. **入库与计算**：把数据写入大数据引擎，做离线分析、实时计算或报表。

### 实时与批量
- **实时**：每产生一条就发送，下游能很快看到，适合实时监控和告警。
- **批量**：攒够一批或等一段时间再发送，网络和磁盘开销更小，吞吐更高，适合对延迟不敏感的分析。

很多场景两种混着用：生产端按批次发送，消费端实时读取。

### 为什么选择消息队列
- **削峰**：流量高峰时数据先堆在队列里；
- **解耦**：新增一个分析系统，只需要再多订阅一份，不用改业务；
- **可回放**：数据在队列里保留一段时间，分析程序出错后可以重新读。

这类场景一般更看重吞吐，所以常选吞吐高的 MQ，比如 Kafka。

## 示例
```bash
# 用命令行向主题写入一条日志消息（Kafka 自带脚本）
echo "user=1001 action=click page=home" | \
  kafka-console-producer.sh --bootstrap-server localhost:9092 --topic user-behavior
```

## 易错点
- 以为日志数据也要像订单那样保证绝对不丢；多数日志场景可以容忍少量丢失，换取吞吐
- 以为消息队列自己能分析数据；它只负责传输和暂存，分析要靠下游引擎
- 每条日志都同步等确认才发下一条，吞吐被拖低

## 追问
### [f1] 数据量很大时队列怎么扩展？
把主题拆成更多分区，让生产者和消费者并行读写，同时增加 Broker 机器分担存储和流量。
