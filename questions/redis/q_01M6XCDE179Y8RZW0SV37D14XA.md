## 一句话
Redis 事务把多条命令打包按顺序一次执行：MULTI 开始，命令入队，EXEC 执行，DISCARD 取消，WATCH 监视 key 被改动就打断事务。

## 要点
- [kp1|3] `MULTI` 开启事务，之后的命令只入队，不立刻执行
- [kp2|3] `EXEC` 一次性按顺序执行队列中的所有命令，期间不会被其他客户端插队
- [kp3|2] `DISCARD` 放弃事务，清空队列
- [kp4|2] `WATCH` 监视 key，执行前被别人改过，EXEC 就返回失败

## 详解
### 先搞懂：为什么要把命令打包
下单扣库存时，你要连续做两步：库存减一，订单数加一。如果两步之间别的客户端插进来改了数据，就可能算错。

可以想成银行柜台办业务：你把几件事写在一张单子上，交给柜员一次办完，中间不会被别人打断。

后文用到几个词：

- **事务**：一组命令打包，按顺序执行。
- **入队**：命令先排进队列，不马上执行。
- **乐观锁**：不加锁，提交时检查数据有没有被别人改过。

### 四个命令怎么配合
- **`MULTI`**：标记事务开始。此后输入的命令，Redis 只回复 `QUEUED`，放进队列。
- **`EXEC`**：执行队列里的所有命令，按入队顺序，一次执行完。执行过程中不会处理别的客户端命令。
- **`DISCARD`**：取消事务，丢弃队列，不执行任何命令。
- **`WATCH`**：在 `MULTI` 之前监视一个或多个 key。如果到 `EXEC` 时，这些 key 被别的客户端改过，整个事务不执行，`EXEC` 返回空。

### 用 WATCH 实现乐观锁
`WATCH` 的典型用法：先监视 key，读出值，在应用里算好新值，再用事务写回。如果期间 key 被别人改了，`EXEC` 失败，应用重新读、重新算，再试一次。

### 和数据库事务的区别
Redis 事务和数据库事务不完全一样：

- **没有回滚**：命令在入队时语法错误，整个事务会被拒绝。但执行时某条命令出错，比如对字符串做 `INCR`，其他命令照常执行，已经完成的不会撤销。
- **不隔离读**：事务里的命令在入队阶段不返回结果，只在 `EXEC` 后才拿到所有结果。

所以“要么全部成功，要么全部失败”的说法并不严谨。

## 示例
```bash
WATCH stock:1001
MULTI
DECR stock:1001
INCR order:count
EXEC
```

## 易错点
- 以为 Redis 事务出错会回滚；执行阶段的错误不会撤销其他命令
- 以为 MULTI 之后命令会立即执行；它们只是入队
- 以为 WATCH 要写在 MULTI 之后；应该在 MULTI 之前

## 追问
### [f1] Redis 事务和 Lua 脚本有什么区别？
Lua 脚本在服务端一次执行，可以在脚本里读值、做判断、再写入，逻辑更灵活。事务只能把命令排好队，里面无法根据前一条命令的结果做判断。
