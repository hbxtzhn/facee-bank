## 一句话
公平锁按先来后到把锁交给等得最久的线程，非公平锁允许新来的线程直接抢；ReentrantLock 默认非公平，构造时传 true 才是公平锁。

## 要点
- [kp1|3] 公平锁：严格按请求顺序，先等的线程先拿到锁
- [kp2|3] 非公平锁：新来的线程可以不排队，直接尝试抢锁
- [kp3|2] ReentrantLock 默认非公平，new ReentrantLock(true) 创建公平锁
- [kp4|2] 非公平锁吞吐量通常更高，但可能让某些线程等很久
- [kp5] synchronized 是非公平锁

## 详解
### 先搞懂：排队买奶茶，能不能插队
奶茶店门口排了一队人，老板刚做好一杯，正好有人在门口走过来。

- **公平**：这杯必须给队伍最前面等得最久的人，路过的人不准抢。
- **非公平**：谁先伸手谁拿，路过的人如果正好赶上，就可以直接拿走，不用排队。

锁也是一样：线程拿不到锁就排队，一旦锁被释放，下一个该是谁？

后文用到的术语：

- **公平锁**：按请求顺序授予锁。
- **非公平锁**：不保证顺序，新来的线程可能先拿到锁。
- **饥饿**：某个线程一直拿不到锁，长时间得不到执行。

### 公平锁：不插队
线程要锁的时候，如果发现已经有别的线程在排队，自己就老老实实排到队尾。好处是每个线程等待时间有保障，不会一直被插队，不容易出现饥饿。缺点是每次释放锁都要唤醒队首线程，线程切换更频繁。

### 非公平锁：先抢一下
线程要锁的时候，不管有没有人排队，先直接抢一下。锁刚好空着就抢到了；抢不到再去排队。

好处是：刚释放锁时，如果有个线程恰好来了，可以直接拿到，省掉唤醒排队线程的切换开销，吞吐量通常更高（JDK 文档也有这样的说明）。缺点是排在队里的线程可能一直被插队，等待时间不可预测。

### 对比
| 对比项 | 公平锁 | 非公平锁 |
|---|---|---|
| 获取顺序 | 先来先得 | 新来的可以抢 |
| 是否可能饥饿 | 基本不会 | 可能 |
| 吞吐量 | 通常较低（切换多） | 通常较高 |
| 创建方式 | `new ReentrantLock(true)` | `new ReentrantLock()`（默认） |

结论：没有特殊要求就用默认的非公平锁；确实需要保证顺序、避免线程饿死时才用公平锁。

### 补充说明
- `synchronized` 也是非公平的，并且没有办法改成公平。
- 即使是公平锁，也不等于线程执行的顺序绝对公平，因为线程调度本身由操作系统决定，公平只是锁的授予顺序。
- ReentrantLock 的无参 `tryLock()` 方法即使在公平锁下也会直接尝试抢锁，不遵守排队顺序。

## 示例
```java
ReentrantLock nonFair = new ReentrantLock();     // 默认：非公平
ReentrantLock fair    = new ReentrantLock(true); // 公平锁
```

## 易错点
- 以为公平锁一定比非公平锁好；公平带来的是顺序保证，代价是吞吐
- 以为非公平锁一定会让线程饿死；只是有可能，多数情况下问题不明显
- 以为 synchronized 可以配置成公平
- 以为公平锁保证线程执行顺序；它只保证锁的获取顺序

## 追问
### [f1] 为什么非公平锁吞吐量通常更高？
锁刚释放时，如果恰好有新线程来，它可以立刻拿到，省去了唤醒排队线程再切换的开销。

### [f2] 什么情况下该用公平锁？
对等待时间有顺序要求、不能容忍线程长时间拿不到锁的场景。
