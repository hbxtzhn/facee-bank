## 一句话
读写锁把锁拆成读锁和写锁：读锁可以多人同时持有，写锁同一时刻只能一个人持有，并且写的时候不允许别人读。

## 要点
- [kp1|3] 读锁是共享锁，多个线程可以同时持有读锁
- [kp2|3] 写锁是排他锁，持有时其他线程不能读也不能写
- [kp3|2] 读读不互斥，读写互斥，写写互斥
- [kp4|2] 适合读多写少的场景，比如缓存数据
- [kp5] Redisson 提供了基于 Redis 的分布式读写锁

## 详解
### 先搞懂：图书馆的阅览规则
图书馆里一本书，很多人可以同时翻看，互不影响。但管理员要修订这本书时，就得把书拿走，期间谁也不能看，也不能有第二个人同时修订。

读写锁就是这套规则：看书是读，修订是写。多人读不冲突，只要有人写，就要和所有人互斥。

后文用到的术语：

- **共享锁**：多个线程可以同时持有，对应读。
- **排他锁**：同一时刻只能一个线程持有，对应写。
- **互斥**：一方持有时，另一方必须等待。

### 三种组合怎么处理
| 情况 | 能否同时进行 | 原因 |
|---|---|---|
| 读和读 | 可以 | 只读取，不改数据，互不影响 |
| 读和写 | 不可以 | 读到一半数据被改，会读到不完整的结果 |
| 写和写 | 不可以 | 同时修改会互相覆盖 |

### 为什么不用普通互斥锁
普通互斥锁不分读写，哪怕只是读也要排队。缓存数据通常读多写少，如果读也互斥，大部分时间都在白白排队。读写锁让读操作并发进行，只在写的时候才互斥，读多时吞吐更好。

### 在缓存一致性中的用法
修改数据时加写锁，读数据时加读锁。这样写的过程中没有人能读到旧值，写完释放后，再读到的就是新数据。这种方式一致性高，但写时所有读请求都要等，性能有损失。

### 用 Redisson 实现分布式读写锁
单机 Java 有 `ReentrantReadWriteLock`，只能在一个 JVM 内生效。多个服务实例要共用一把锁，可以用 Redisson 的 `RReadWriteLock`，锁的状态保存在 Redis 中。

## 示例
```java
RReadWriteLock rwLock = redisson.getReadWriteLock("lock:item:1");

// 读
RLock readLock = rwLock.readLock();
readLock.lock();
try {
    // 读缓存、读数据库
} finally {
    readLock.unlock();
}

// 写
RLock writeLock = rwLock.writeLock();
writeLock.lock();
try {
    // 改数据库、删缓存
} finally {
    writeLock.unlock();
}
```

## 易错点
- 以为读写锁里读也互斥；读锁之间可以并发
- 以为读写锁在写多的场景也更快；写多时反而会频繁互斥
- 忘记在 `finally` 里释放锁；异常时锁会一直占着

## 追问
### [f1] 读写锁有什么缺点？
写锁持有期间所有读请求都要等待，如果写操作慢或频繁，读性能会明显下降。读多写少才划算。
