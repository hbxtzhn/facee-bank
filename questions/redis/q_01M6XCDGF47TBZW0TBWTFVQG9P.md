## 一句话
Redisson 用 hash 存锁：field 是线程标识，value 是重入次数；同一线程再次加锁，次数加一，解锁时减一，减到 0 才真正释放。

## 要点
- [kp1|3] 锁的 key 是 hash，field 为客户端加线程标识，value 为重入次数
- [kp2|3] 同一线程再次加锁，判断标识一致，次数加一
- [kp3|2] 解锁每次次数减一，减到 0 才删除 key
- [kp4|2] 标识里带客户端 ID，防止不同机器上同编号的线程冲突
- [kp5] 加锁和解锁都用 Lua 脚本，保证原子

## 详解
### 先搞懂：自己进自己锁的门
一个业务方法 A 加了锁，里面又调用了方法 B，B 也要加同一把锁。如果锁不可重入，B 会等 A 释放，而 A 在等 B 返回，两边互相等，就死锁了。

可重入的意思是：已经拿到锁的人，再次要这把锁时直接放行。类比：你有一张门禁卡，进了大楼之后再进里面的办公室，不需要再申请，只是记一笔“又进了一次”。

后文用到的词：

- **可重入**：同一个线程可以多次获取同一把锁。
- **重入次数**：同一线程已经获取了几次，需要释放几次。

### 用 hash 记两样信息
一个普通字符串只能存一个值。可重入要同时记“谁持有”和“持有了几次”，所以 Redisson 用 hash：

- key：锁的名字；
- field：客户端 ID 加线程 ID，用来标识“谁”；
- value：重入次数。

标识里带上客户端 ID，是因为不同机器上的线程 ID 可能相同，只用线程 ID 会混淆。

### 加锁过程
Lua 脚本里按顺序判断：

1. 锁不存在：创建 hash，field 为当前标识，次数为 1，设置过期时间；
2. 锁存在，且 field 就是当前标识：说明是自己重入，次数加一，刷新过期时间；
3. 否则：别人持有，加锁失败。

### 解锁过程
1. 检查 field 是不是自己，不是就不能解；
2. 次数减一；
3. 减完大于 0：只刷新过期时间，锁依然被持有；
4. 减到 0：删除这个 key，通知等待的线程。

所以加锁几次，就要解锁几次，成对出现，不然锁不会释放。

### 为什么不用 ReentrantLock 那样的方式
`ReentrantLock` 的重入次数存在 JVM 内存里（AQS 的状态变量里）。分布式锁的状态必须放在 Redis，所有节点才看得到。思路一样，存放的位置不同。

## 示例
```java
RLock lock = redisson.getLock("lock:order:1001");
lock.lock();        // 重入次数 1
try {
    lock.lock();    // 同线程再次加锁，重入次数 2
    try {
        doBusiness();
    } finally {
        lock.unlock(); // 次数 1，锁仍被持有
    }
} finally {
    lock.unlock();     // 次数 0，真正释放
}
```

## 易错点
- 以为可重入只靠线程 ID；还要带客户端 ID，避免不同机器冲突
- 加锁两次只解锁一次；次数没归零，锁不会释放，直到过期
- 以为重入时过期时间不变；脚本在重入时会刷新过期时间

## 追问
### [f1] 可重入锁和不可重入锁的区别？
不可重入锁中，持有者再次加锁也会被挡住，容易自己等自己造成死锁。可重入锁识别出是同一线程后直接放行，并记录次数。
