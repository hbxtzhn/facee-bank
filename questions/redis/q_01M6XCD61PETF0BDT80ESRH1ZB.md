## 一句话
先查缓存，命中直接返回；没命中就查数据库，把结果写回缓存并设置过期时间，下一次同样的请求就能直接命中。

## 要点
- [kp1|3] 读流程第一步总是先查缓存，命中就直接返回
- [kp2|3] 未命中才查数据库，再把结果写入缓存
- [kp3|2] 写入缓存时要设置过期时间，避免旧数据永远留着
- [kp4] 数据库里也没有时，要处理空结果，避免反复查库

## 详解
### 先搞懂：先翻小抄，翻不到再查书
做题时，常用的公式记在小抄上，要用先看小抄，有就直接用；小抄上没有，才翻厚厚的教材，找到后顺手抄在小抄上，下次就快了。

缓存读写就是这样。Redis 是小抄，数据库是教材。这种做法一般叫**旁路缓存**：应用自己负责查缓存、查库、回填，缓存不会自动从数据库加载。

后文用到的术语：

- **命中**：在缓存里找到了数据。
- **未命中**：缓存里没有。
- **回填**：从数据库查到后，写回缓存。
- **TTL**：缓存数据的存活时间。

### 读流程：四步
1. 根据 key 查 Redis。
2. 命中，直接返回，不碰数据库。
3. 未命中，查数据库。
4. 把查到的数据写入 Redis，设置过期时间，再返回给调用方。

### 为什么要设过期时间
即使有更新缓存的逻辑，也可能漏掉某些情况，或者更新失败。给缓存设 TTL，相当于给旧数据一个保险：就算一时不一致，过期后也会重新从数据库加载。

TTL 也不要设得对所有 key 都一样，以免同时过期，可以加一个随机值。

### 数据库也查不到怎么办
如果数据库里也没有这条数据，直接返回空，下一个请求还会再查库。恶意请求不断查不存在的 ID，就会打到数据库，这叫缓存穿透。常见做法是把空结果也缓存一小段时间，或在前面加布隆过滤器。

## 示例
```java
String get(String key) {
    String json = redis.opsForValue().get(key);
    if (json != null) {
        return json;                                  // 命中
    }
    json = loadFromDb(key);                           // 未命中，查库
    if (json != null) {
        redis.opsForValue().set(key, json, 30, TimeUnit.MINUTES); // 回填并设过期时间
    }
    return json;
}
```

## 易错点
- 回填缓存时不设过期时间；数据一旦变化，旧值会一直留在缓存里
- 把「缓存自动加载数据库」当成 Redis 的功能；这一步需要应用代码完成
- 忽略数据库查不到的情况；会让缓存形同虚设

## 追问
### [f1] 并发时同一个 key 会被重复回填吗？
会。多个线程同时未命中，各自查库再写缓存。热点 key 可以用互斥锁，让只有一个线程回填。
