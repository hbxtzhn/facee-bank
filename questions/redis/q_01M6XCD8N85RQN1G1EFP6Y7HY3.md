## 一句话
全量同步时，主节点用 bgsave 生成 RDB 快照发给从节点，从节点清空旧数据后加载，快照期间新写入的命令先存进缓冲区，再补发给从节点。

## 要点
- [kp1|3] 从节点首次发 psync，没有主节点 ID 和偏移量，主节点回复 FULLRESYNC
- [kp2|3] 主节点执行 bgsave 生成 RDB，发给从节点
- [kp3|2] 从节点收到 RDB 后清空本地数据，再加载快照
- [kp4|2] 生成 RDB 期间的新写命令，记在复制缓冲区里，之后补发
- [kp5] 全量同步成本高，生成和传输 RDB 都耗时耗资源

## 详解
### 先搞懂：新同学要抄整本笔记
新同学第一天来，课已经上了一半，他什么笔记也没有。老师不能从头再讲，就把自己的完整笔记复印一份给他，让他先照着看。复印的时候老师还在继续讲课，新内容也要记下来，等复印件给完，再补给他。

全量同步就是这个过程。

后文用到的术语：

- **psync**：从节点发起同步的命令，会带上主节点 ID 和复制偏移量。
- **replid / 运行 ID**：标识主节点的一个 ID。
- **offset（偏移量）**：从节点已经复制到的数据位置。
- **bgsave**：在后台生成 RDB 快照，不阻塞主线程。
- **复制缓冲区**：保存生成快照期间新写命令的区域。

### 流程
1. **发送 psync**：从节点是第一次复制，没有主节点 ID，也没有偏移量，所以发送「psync ? -1」，表示请求全量。
2. **主节点判断**：主节点看出这是全量复制，回复 `+FULLRESYNC`，同时带上自己的运行 ID 和当前偏移量。
3. **从节点保存**：从节点收到回复，保存主节点的运行 ID 和偏移量。
4. **生成 RDB**：主节点执行 bgsave，把当前数据保存成 RDB 文件。
5. **记录新写入**：在 bgsave 执行期间，主节点收到的写命令，不会丢，暂存在复制缓冲区里。
6. **发送 RDB**：RDB 生成完成，主节点把文件发给从节点。
7. **加载 RDB**：从节点先清空本地旧数据，再加载 RDB。
8. **补发缓冲命令**：主节点把缓冲区里的写命令发给从节点，从节点执行，追平主节点。

### 为什么全量同步比较重
- 主节点要执行 bgsave，需要 fork 子进程并占用磁盘和 CPU。
- RDB 文件通过网络传输，数据量大时耗时久。
- 从节点要清空数据，加载文件期间无法提供服务。

所以应该尽量避免频繁触发全量同步，比如把缓冲区设大一点，减少断线后被迫全量的情况。

## 示例
```bash
# 在从节点上查看复制状态，确认是否完成同步
redis-cli INFO replication
# 关注 master_link_status 是否为 up
```

## 易错点
- 以为全量同步直接发命令；实际先发 RDB 快照，再补发命令
- 以为 bgsave 期间新写入会丢失；它们会进缓冲区，之后补发
- 以为每次重连都是全量同步；断线重连通常优先增量

## 追问
### [f1] 什么时候会触发全量同步？
从节点第一次连接主节点时，或从节点保存的偏移量已经不在主节点的缓冲区里时，就会触发全量同步。主节点 ID 变化（比如换了新主）通常也需要全量。
