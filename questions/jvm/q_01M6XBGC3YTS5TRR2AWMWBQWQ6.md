## 一句话
Stop-The-World 是垃圾回收时 JVM 把所有业务线程暂停下来的现象；我们说的 GC 停顿时间，就是业务线程被暂停的这段时间。

## 要点
- [kp1|3] STW 期间，除 GC 线程外的所有 Java 业务线程都被暂停
- [kp2|3] 暂停是为了让对象引用关系在回收时保持不变，避免漏标或误回收
- [kp3|2] GC 停顿时间就是业务线程被暂停的时长，用户感受就是接口卡了一下
- [kp4] 所有收集器都有 STW，区别只是停顿的阶段多少、时间长短

## 详解
### 先搞懂：为什么回收垃圾时要让大家都停下来
想象超市在盘点货架：店员一边清点，顾客一边往货架上拿东西、放东西，账怎么也对不上。最稳妥的办法是盘点时先让顾客停一会儿。

JVM 里也是这样。业务线程在不停地创建对象、修改对象之间的引用关系；GC 要判断哪些对象还有用、哪些是垃圾，如果引用关系在判断过程中一直在变，就可能把还在用的对象当成垃圾回收掉，程序就会出错。所以 GC 在关键阶段会让业务线程暂停。

后文会用到的术语：
- **STW（Stop-The-World）**：GC 暂停所有业务线程的现象。
- **停顿时间**：一次 STW 从开始到结束的时长。
- **业务线程**：执行你写的代码的线程，和 GC 自己的线程相对。

### STW：暂停的是谁，什么时候暂停
暂停的是所有执行 Java 代码的业务线程，GC 线程继续干活。业务线程不是被立刻"拍停"的：JVM 会等每个线程跑到一个安全的位置（叫**安全点**），线程在那里停下来，GC 才开始动手。

GC 做完这一阶段的工作后，业务线程恢复运行。对用户来说，就是这段时间内请求没有响应，表现为接口突然变慢、偶尔超时。

### 不同收集器怎么对付 STW
STW 没法完全消除，只能尽量缩短。思路有两种：

- **多线程并行回收**：暂停期间用多个 GC 线程一起干，早点干完（如并行收集器）。
- **让大部分工作和业务线程并发**：只在必须的几个短阶段暂停，其他时间 GC 和业务线程一起跑（如 CMS、G1、ZGC）。

早期的串行收集器就是最直接的做法：一个 GC 线程回收，期间所有业务线程停着，简单但停顿最明显。

### 停顿多了有什么影响
- 接口响应时间出现毛刺，对延迟敏感的服务（交易、网关）受影响大。
- 停顿太长，调用方可能超时重试，甚至被注册中心认为节点失联。
- 排查时看 GC 日志里每次停顿的时长，可以判断是否是 GC 造成了卡顿。

## 易错点
- 以为只有 Full GC 才会 STW；Young GC 同样会暂停业务线程，只是通常更短
- 以为并发收集器完全没有停顿；它们仍有短暂的 STW 阶段，只是比整个回收过程短得多
- 以为 STW 是线程"卡死"或程序出错；它是 JVM 的正常行为

## 追问
### [f1] 怎么减少 STW 带来的影响？
选用停顿更短的收集器（如 G1、ZGC），避免频繁创建大量短命大对象，合理设置堆大小，并通过 GC 日志观察停顿时长再调整。
