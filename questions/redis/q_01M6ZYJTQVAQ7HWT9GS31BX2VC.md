## 一句话
数据库和缓存是两份独立的数据，更新它们是两个动作，不是一个原子操作，中间失败或被别的请求插进来，缓存就会留下旧值。

## 要点
- [kp1|3] 数据库和 Redis 是两个系统，没法放进同一个事务
- [kp2|3] 先后两次写之间，第二步会失败，其他线程也会插进来
- [kp3|2] 并发读写时，读线程会把旧数据重新写回缓存
- [kp4|2] 不一致的根源是顺序和并发，不管先改哪个都有风险
- [kp5] 业务通常根据一致性要求，选择不同方案

## 详解
### 先搞懂：同一件事记在两个本子上
想象你把家里的开销同时记在手机和纸质账本上。改一笔账，要改两个地方。如果改了手机，还没来得及改纸质本就被叫走了，两边就对不上。又或者你正在改，家人此时来看，看到的是改了一半的状态。

数据库和缓存就是这两个本子。我们期望它们一致，但没有一个机制能让两次更新同时成功。

后文用到的术语：

- **双写一致性**：修改数据库的同时，缓存里的数据也要保持一致。
- **脏数据**：和数据库不一致的缓存数据。
- **原子性**：一组操作要么全成功，要么全不执行。

### 原因一：两步操作中间可能出事
不管先写哪个：

- 先改数据库、再更新缓存：数据库改成功，缓存更新失败（网络抖动、服务重启），缓存里是旧值。
- 先更新缓存、再改数据库：缓存改了，数据库失败回滚，缓存里反而是错的值。

两个系统没有共同的事务，一个成功另一个失败时，没法自动回滚。

### 原因二：并发读写交叉
即使每一步都成功，多个线程交叉也会出问题。典型过程：

1. 线程 A 读缓存没有，去数据库读到旧值。
2. 线程 B 修改数据库，并删除缓存。
3. 线程 A 把刚才读到的旧值写回缓存。

这时数据库是新值，缓存却是旧值，而且会一直保持到缓存过期。

### 原因三：数据库主从延迟
如果读库是从库，删除缓存后马上有请求读从库，此时从库还没同步到新数据，读到旧值又写进了缓存。

### 怎么办
没有一种办法能让两者绝对强一致且性能不受影响，只能按业务选择：

- 允许短暂不一致：给缓存设 TTL，或先改库再删缓存。
- 一致性要求高：用读写锁，让读写互斥。
- 想要最终一致：用消息队列或 canal 异步更新。

具体做法在后续题目展开。

## 易错点
- 以为 Redis 和 MySQL 可以放进一个事务；它们是两个独立系统
- 以为每一步都成功就不会不一致；并发交叉同样会产生旧值
- 以为设了 TTL 就不会不一致；TTL 只能限制旧值存在的时间

## 追问
### [f1] 更新数据时，是更新缓存还是删除缓存？
通常选删除缓存，下次读时再加载新值。更新缓存要在每次写入时计算新值，并发写入时还可能顺序错乱，删除更简单。
