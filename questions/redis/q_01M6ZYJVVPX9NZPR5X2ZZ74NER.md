## 一句话
Redis 分片集群把数据分到 16384 个哈希槽里，每个节点负责一部分槽；读写时先算 key 属于哪个槽，再找到负责它的节点。

## 要点
- [kp1|3] 对 key 做 CRC16 计算，再对 16384 取余，得到槽位编号
- [kp2|3] 每个主节点负责一段槽，槽位决定数据存在哪个节点
- [kp3|2] 请求发错节点，该节点返回 MOVED，告诉客户端正确地址
- [kp4|2] 槽迁移过程中，读写可能收到 ASK 重定向
- [kp5] key 里用 `{}` 包住的部分作为哈希标签，同标签的 key 落在同一槽

## 详解
### 先搞懂：小区快递柜按楼栋分格
快递员送件时，不会在整个小区里挨家找，而是先看地址属于哪一栋楼，把包裹放进那栋楼的快递柜。每个柜子管几栋楼，查包裹也是先算楼栋，再去对应的柜子。

Redis 集群的槽就像“楼栋编号”，节点就像“快递柜”。后文用到的词：

- **哈希槽**：集群把数据分成固定的 16384 份，每份叫一个槽。
- **重定向**：节点告诉客户端“这个数据不归我，请去另一个节点”。

### 存储：先算槽，再落到节点
写入一个 key 的过程：

1. 对 key 算 CRC16 校验值；
2. 对 16384 取余，得到 0 到 16383 之间的槽号；
3. 集群里记录了每个槽归哪个节点；
4. 数据存到那个节点。

例如三个主节点，可以大致这样分：

- 节点 A 管 0 到 5460；
- 节点 B 管 5461 到 10922；
- 节点 C 管 10923 到 16383。

### 读取：同样的计算
读取时客户端用同一套公式算出槽号，找到节点，直接向它发请求。

常用的客户端会在本地缓存“槽到节点”的对应表，所以多数请求一次就能找到正确节点。

### 请求发错了怎么办
如果客户端的缓存过期，把请求发给了不负责这个槽的节点：

- 节点返回 `MOVED 槽号 地址`，表示这个槽已经归别人了，客户端更新缓存后再去请求。
- 如果槽正在迁移途中，节点可能返回 `ASK`，表示这次请去新节点问一下，但不更新缓存。

### 多 key 命令的限制
`MGET`、事务、Lua 这类涉及多个 key 的操作，要求这些 key 在同一个槽里。

可以用哈希标签：`{user:1001}:cart` 和 `{user:1001}:order`。只对大括号里的内容算槽，两个 key 就落在同一个槽。

### 进阶：MOVED 与 ASK 的区别（基础薄弱可先跳过）
- MOVED 表示槽的归属已经确定变了，客户端应更新本地的槽映射。
- ASK 表示迁移进行中，只有这一次请求去新节点，下次仍然先问旧节点。

## 示例
```bash
# -c 表示集群模式，遇到 MOVED 自动跟随跳转
redis-cli -c -p 7000
127.0.0.1:7000> SET user:1001 tom
-> Redirected to slot [xxxx] located at 127.0.0.1:7001
OK
127.0.0.1:7001> CLUSTER KEYSLOT user:1001
```

## 易错点
- 以为每个 key 都单独记录在哪个节点；集群只记录槽归哪个节点
- 以为客户端每次都要先问集群；通常缓存槽映射，只在 MOVED 时刷新
- 在集群里随意用多 key 命令；key 不在同一个槽会报错
- 把 MOVED 和 ASK 混为一谈；前者是归属已变，后者是迁移中的临时指引

## 追问
### [f1] 为什么槽数量是固定的 16384？
槽数固定后，key 到槽的映射永远不变，扩缩容只需要把槽整体迁移，而不用重新计算所有 key。至于为什么取这个数，是集群心跳消息大小与节点规模的折中。
