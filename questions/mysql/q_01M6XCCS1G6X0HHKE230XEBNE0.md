## 一句话
死锁就是两个或多个事务各自拿着对方需要的锁，又都在等对方释放，谁也走不下去。最常见的原因是加锁顺序相反。

## 要点
- [kp1|3] 死锁：事务之间互相等待对方持有的锁，形成环
- [kp2|3] 常见成因：两个事务以相反的顺序修改同样的几行
- [kp3|2] InnoDB 会检测到死锁，回滚其中一个事务
- [kp4] 被回滚的事务会收到死锁错误，应用要重试
- [kp5] 预防办法：统一加锁顺序、缩短事务、让查询走索引

## 详解
### 先搞懂：两个人在窄路上互相让不了
两个人在窄过道里迎面走来，都不肯后退，谁也过不去，这就是死锁。

数据库里的例子：账户 1 和账户 2 之间互相转账。

- 事务 A：先改账户 1，再改账户 2；
- 事务 B：先改账户 2，再改账户 1。

A 拿到账户 1 的锁，B 拿到账户 2 的锁。A 接下来要账户 2 的锁，被 B 挡住；B 要账户 1 的锁，被 A 挡住。两个事务互相等待，形成一个环。

后文会用到这几个词：

- **等待环**：事务 A 等 B，B 又等 A，没有人能先动。
- **死锁检测**：InnoDB 主动发现等待环的机制。
- **牺牲者**：被 InnoDB 选中回滚的那个事务。

### InnoDB 怎么处理
InnoDB 默认开启死锁检测。一旦发现等待环，会选择一个事务回滚，让另一个事务继续。被回滚的事务会收到错误，错误信息里写着发生了死锁，应用需要重新执行这个事务。

### 常见成因
- **加锁顺序不一致**：就是上面转账的例子。
- **间隙锁相互等待**：可重复读下，两个事务先加间隙锁，再往里插入，互相等待。
- **锁的范围太大**：没走索引导致锁住很多行，更容易碰撞。
- **事务太长**：持锁时间久，冲突概率变大。

### 怎么减少死锁
1. 多个事务按**同样的顺序**访问表和行，比如总是先改 id 小的；
2. 事务尽量**短**，拿到锁后尽快提交；
3. 查询**走索引**，缩小锁的范围；
4. 应用端对死锁错误**捕获并重试**。

## 示例
```sql
-- 事务 A                               -- 事务 B
START TRANSACTION;                      START TRANSACTION;
UPDATE account SET bal=bal-10           UPDATE account SET bal=bal-10
 WHERE id = 1;                           WHERE id = 2;
UPDATE account SET bal=bal+10           UPDATE account SET bal=bal+10
 WHERE id = 2;  -- 等待 B                WHERE id = 1;  -- 等待 A，死锁
```

## 易错点
- 把长时间的锁等待当成死锁；等待可能自己结束，死锁需要有一方被回滚
- 以为出现死锁说明数据库有 bug；多数是业务加锁顺序的问题
- 遇到死锁错误不重试，直接给用户报错

## 追问
### [f1] 死锁和普通的锁等待有什么区别？
锁等待是一方等另一方，对方提交后就能继续。死锁是互相等待，不处理就永远不会结束，必须由 InnoDB 回滚其中一个事务。
