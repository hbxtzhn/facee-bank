## 一句话
CAS 是「比较并交换」：只有变量当前值等于我预期的值，才把它改成新值，否则不改，由调用方重试；整个过程是原子的，不需要加锁。

## 要点
- [kp1|3] CAS 有三个值：变量当前值 V、预期值 E、新值 N
- [kp2|3] V 等于 E 才改成 N，否则什么都不做并告诉调用方失败
- [kp3|2] 比较和交换由 CPU 一条原子指令完成，不需要加锁
- [kp4|2] 失败后通常循环重试（自旋），这是乐观锁的做法
- [kp5] Java 中 AtomicInteger 等原子类就是基于 CAS 实现的

## 详解
### 先搞懂：改共享文档前先确认没人动过
想象几个人同时编辑一份共享文档的某个数字。你读到数字是 10，想改成 11。为了避免覆盖别人的修改，你在提交时说：「如果现在还是 10，就改成 11；不是 10 了，说明有人改过，我重新看看再试。」

这就是 CAS：不先锁住文档，而是提交时检查「有没有变过」。

后文用到的术语：

- **原子操作**：要么完整做完，要么没做，中途不会被别的线程打断。
- **乐观锁**：假设冲突很少，先干活，发现冲突再重试。
- **自旋**：失败后在循环里不断重试。

### CAS 的三个值和判断
CAS 涉及三个值：

- **V**：要修改的变量（内存里现在的值）。
- **E**：预期值，也就是你以为它现在是多少。
- **N**：想改成的新值。

执行时：如果 V 等于 E，就把 V 改成 N，返回成功；如果 V 不等于 E，说明被别人改过，什么也不改，返回失败。

关键是：「比较」和「修改」这两步合在一起是原子的，中间不会被别的线程插进来。这靠的是 CPU 提供的原子指令，Java 通过底层接口调用它。

### 失败了怎么办：循环重试
CAS 失败不是错误，只是告诉你「刚才有人改了」。典型写法是一个循环：重新读最新值、算出新值、再 CAS，直到成功。

比如 `AtomicInteger.incrementAndGet()` 就是这样：读当前值，加 1，CAS 写回，失败就重来。

### 对比：CAS 与加锁
| 对比项 | CAS | 加锁（synchronized 等） |
|---|---|---|
| 思路 | 乐观：先做，冲突了重试 | 悲观：先锁住，再做 |
| 线程会阻塞吗 | 不会 | 会 |
| 适合 | 冲突少、操作简单 | 冲突多、逻辑复杂 |

结论：简单的计数、状态切换用 CAS 很合适；操作复杂或竞争很激烈时，用锁更稳妥。

### CAS 的三个已知问题
CAS 不是万能的，后面的题会详细讲：

- ABA 问题：值从 A 变 B 又变回 A，CAS 发现不了；
- 自旋开销：一直失败会空转消耗 CPU；
- 只能保证一个变量的原子操作。

## 示例
```java
AtomicInteger count = new AtomicInteger(0);

// 手写一个自增：典型的 CAS 重试循环
int old;
do {
    old = count.get();                          // 读当前值
} while (!count.compareAndSet(old, old + 1));   // 失败就重试
```

## 易错点
- 以为 CAS 不会失败；它会失败，需要调用方处理，通常是循环重试
- 以为不加锁就没有开销；冲突激烈时反复重试同样消耗 CPU
- 以为 CAS 是 Java 语言层面的实现；它依赖 CPU 的原子指令
- 把「比较」和「交换」当成两步分别做，这样就不是原子的了

## 追问
### [f1] AtomicInteger 的自增是怎么实现的？
循环读取当前值，计算新值，用 CAS 写回，失败就重新读取并重试，直到成功。

### [f2] CAS 为什么说是乐观锁？
它假设不会有冲突，不先加锁就操作，提交时才检查，冲突了就重试，而不是一开始就阻止别人。
