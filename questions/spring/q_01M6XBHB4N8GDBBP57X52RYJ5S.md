## 一句话
单体把所有功能打成一个应用整体部署，简单但牵一发动全身；微服务把功能拆成多个独立部署的服务，灵活、隔离好，但分布式带来的运维和调用复杂度也更高。

## 要点
- [kp1|3] 单体是一个进程整体构建和发布；微服务每个服务单独构建、发布、回滚
- [kp2|3] 单体一处故障可能拖垮整个应用；微服务可以把故障限制在单个服务
- [kp3|2] 微服务允许不同服务用不同技术栈，服务间通过接口（如 HTTP、RPC）通信
- [kp4|2] 微服务要额外处理注册发现、分布式事务、监控等问题，运维成本更高

## 详解
### 先搞懂：一家大饭店和一排小摊位
单体像一家大饭店：前台、厨房、仓库都在同一栋楼里，统一管理，开起来简单。但想把厨房扩大，整栋楼都得停业装修；仓库起火，整家店都受影响。

微服务像美食街的一排小摊位：每个摊位独立经营，谁想升级自己装修，不影响别人。代价是摊位之间要协调，管理街区的事情变多了。

后文用到的术语：
- **单体架构**：所有功能模块放在同一个工程、同一个进程里运行。
- **微服务**：按业务拆成多个小服务，每个独立运行、独立发布。
- **服务间通信**：服务之间通过网络调用接口，例如 HTTP 或 RPC。

### 方案对比：单体和微服务
| 维度 | 单体架构 | 微服务架构 |
|---|---|---|
| 部署 | 整体打包，改一行也要全量发布 | 每个服务单独发布和回滚 |
| 技术选型 | 通常统一技术栈和依赖版本 | 不同服务可以用不同语言和框架 |
| 团队协作 | 多人改同一份代码，容易冲突 | 按服务划分团队，各自负责 |
| 故障隔离 | 一个模块出问题可能拖垮整个进程 | 故障可以限制在单个服务 |
| 运维复杂度 | 低，只有一个应用要管 | 高，要管理很多服务和它们之间的调用 |
| 开发调试 | 本地一个进程就能跑 | 要启动多个服务或依赖环境 |

结论：项目规模小、团队小时先用单体，开发和运维都省事；业务和团队变大、需要独立发布和扩缩容时，再考虑拆微服务。

### 微服务带来的新问题
拆开之后，原来的方法调用变成了网络调用，会遇到这些问题：
- 服务地址怎么找：需要注册中心。
- 调用失败或超时怎么办：需要重试、熔断、降级。
- 一次业务跨多个服务，数据一致性怎么保证：需要分布式事务或最终一致性方案。
- 出问题怎么定位：需要日志收集、链路追踪。

所以微服务不是“更先进就更好”，而是用更高的复杂度换更好的灵活性。

## 易错点
- 以为微服务一定比单体好；业务简单时拆微服务只会增加成本
- 以为拆成多个工程就是微服务；如果还是必须一起发布、共用一个数据库，就没有得到独立部署的好处

## 追问
### [f1] 什么情况下该拆微服务？
业务复杂、团队变大，不同模块的发布节奏或访问压力差异很大，需要独立部署和独立扩容时，拆分才有价值。

### [f2] 单体能不能做好模块化？
可以。单体内部也能按业务划分模块、约束依赖方向，这样将来要拆服务时会容易很多。
