## 一句话
惰性删除是访问 key 时才检查它是否过期，过期就删掉；它对 CPU 友好，但过期后没人访问的 key 会一直占着内存。

## 要点
- [kp1|3] 惰性删除只在访问 key 时才检查是否过期
- [kp2|3] 发现 key 已过期就当场删除，并当作 key 不存在返回
- [kp3|2] 优点：只在用到时花 CPU，不需要额外扫描
- [kp4|2] 缺点：过期后再也没人访问的 key 不会被删，内存浪费

## 详解
### 先搞懂：过期的酸奶什么时候扔
冰箱里的酸奶过期了。有两种扔法：一种是每天专门检查一遍；另一种是等你要喝的时候，看一眼日期，过期了才扔。后一种就是惰性删除，也叫懒汉式。

Redis 的 key 过期时，不会精确地在那个时刻被删掉，而是靠几种机制配合清理。惰性删除是其中一种。

后文用到几个词：

- **过期**：key 设置的存活时间到了，之后不应该再被读到。
- **惰性**：不主动做，等到需要时再做。

### 惰性删除：用到时再检查
过程很简单：

1. 客户端访问某个 key，比如 `GET user:1`。
2. Redis 在真正读取之前，先检查这个 key 有没有设置过期时间，过期时间是否已过。
3. 已经过期，就把 key 删掉，并返回“key 不存在”。
4. 没有过期，正常返回。

对客户端来说，过期的 key 永远读不到，行为是正确的。

### 优点和缺点
| 方面 | 表现 |
|---|---|
| CPU | 只在访问时检查一次，成本极小 |
| 额外扫描 | 不需要 |
| 内存 | 过期后没人再访问的 key 会一直留着 |

结论：惰性删除省 CPU，但不能单独使用。如果大量 key 过期后再也没被访问，内存就被白白占用，所以 Redis 还要配合定期删除。

### 进阶：删除操作也可以异步（基础薄弱可先跳过）
删除一个很大的 key 会阻塞主线程。Redis 4.0 起可以配置 `lazyfree-lazy-expire yes`，让过期删除改为在后台线程释放内存。

## 易错点
- 以为 key 一过期就立刻被删除；过期和被删除之间可能有时间差
- 以为过期但未删除的 key 还能读到；访问时会被检查，读不到
- 以为只靠惰性删除就够了；冷数据会一直残留，需要定期删除补充

## 追问
### [f1] 从节点访问过期 key 时会自己删吗？
通常不会。从节点不自己决定删除，而是等主节点同步来 `DEL` 命令。不过从节点读到过期 key 时，会按不存在处理。
