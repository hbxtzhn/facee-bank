## 一句话
大 key 是 value 很大，或集合类型里元素特别多的 key；它会让客户端超时、占满带宽和 CPU、造成数据倾斜，删除时还会阻塞 Redis。

## 要点
- [kp1|3] 大 key 有两种：单个 value 很大，或集合里元素特别多
- [kp2|3] 常见参考标准：字符串超过约 10KB，集合元素达到万级
- [kp3|2] 危害：读写耗时变长、占用带宽和 CPU、集群里数据倾斜
- [kp4|2] 删除大 key 可能长时间阻塞主线程，影响其他请求

## 详解
### 先搞懂：一个大箱子堵住了传送带
快递分拣线上，大部分包裹都很小，传送带转得很快。某天来了一个巨大的箱子，要好几个人搬，传送带只能停下来等，后面所有包裹都被卡住。

Redis 处理命令基本是单线程的，一个大 key 的操作耗时很长，其他命令只能等着。

后文用到几个词：

- **大 key**：占用空间很大，或包含元素很多的 key。
- **数据倾斜**：集群里某个节点存的数据明显比别的多。

### 什么算大 key
没有官方统一的标准，常见的经验判断是：

- 字符串类型：value 超过约 10KB。
- Hash、Set、ZSet、List：元素个数达到上万。

具体阈值要结合业务和实例规模，这些数字只是经验值。

### 大 key 的危害
- **客户端耗时增加，甚至超时**：读写一个很大的 value，要传输和处理很多数据。
- **占用带宽和 CPU**：反复读取大 key 时，网络带宽和 Redis 的 CPU 都被占用。
- **数据倾斜**：在集群里，大 key 所在节点的内存明显比别的节点多，容易先撑满。
- **删除阻塞**：直接用 `DEL` 删除大 key，要一次性释放大量内存，可能阻塞主线程。过期自动删除和被动淘汰同样可能触发这种阻塞。

### 它是怎么产生的
- 把整个列表、整张表缓存在一个 key 里。
- 没有清理机制，集合不断变大，比如一直往一个 List 里添加元素。
- 把大对象序列化后直接存成一个字符串。

### 怎么应对
发现和处理方法见后面两道题：“怎么找出大 key”和“怎么处理大 key”。

## 易错点
- 以为只有字符串会是大 key；集合元素太多同样是
- 以为大 key 只是占内存；它还会引起阻塞和超时
- 以为用 DEL 删除是安全的；删大 key 可能卡住 Redis

## 追问
### [f1] 为什么大 key 会造成集群数据倾斜？
集群按 key 的哈希值分配槽位，一个 key 只能放在一个节点上。大 key 把那个节点的内存撑得比别的节点高，但迁移槽位时也很难把它拆开。
