# 答案生成规范

输入一道题的**标题**（可附分类、题型），输出一份可直接通过 `bank-spec validate` 的 v2 题目文件。
用于 AI 批量生成，也用于人工复核时对照。

## 第一优先级：通俗好懂

读者大多只做过项目、基础薄弱。取舍顺序：

1. **正确**是底线：错了的内容不能发布，查证规则一条不能省。
2. 在正确的前提下，**通俗好懂排第一**。
3. 完整、严谨的限定条件排在后面。

两者冲突时这样处理：

- **主结论用最直白的话说**，例外和限定条件挪到后面的段落、易错点或追问里，不和主结论挤在同一句。
- **先举例子，再讲规则**：先让读者看到 `WHERE a = 1 AND c = 3` 能用上索引的哪一部分，再总结成「最左前缀」。
- **每节第一句就是这一节的结论**，后面再解释为什么。
- **宁可少讲一个边角细节**，也不让主线变难；边角内容放进「进阶」或「追问」。
- **代码以看得懂为先**：10 行能说明的不写 30 行；不用 `set -e`、`trap`、heredoc、层层嵌套的函数这类工程写法，除非不用就跑不通。

判断标准：把详解读给一个只写过增删改查的同事听，每一段他都能用自己的话复述出来。

## 输入

```yaml
title: Redis 过期 key 的删除策略有哪些？   # 必填
category: redis                           # 必填，取自 bank.yaml categories
tags: [expiration]                        # 必填，清单给定，取自 bank.yaml tags
difficulty: medium                        # 清单给的初值；按内容判断不合适可以改，在汇报里说明
importance: 2                             # 清单统一评定，原样使用
type: concept                             # 可选；不填由生成者判断
note: 惰性删除加定期删除，两者都漏掉时由淘汰兜底   # 可选：清单给的范围说明
```

文件骨架由 `bank-spec new --bank . --category <id> --tags <a,b> --title <标题>` 生成，生成者只填内容，不手写 id。

完成后跑 `node scripts/check.mjs <新文件>`：它检查 validate 管不到的规则（先搞懂节、`|3` 数量、对比表结论、口号），并真的运行 Java 小实验、比对输出注释。

## 流程

0. **读样题**：动笔前至少读一道难度相近的样题，把它当作质量和语气的标杆：
   - easy：`prompts/examples/basic-redis-set-expire.md`、`prompts/examples/basic-why-thread-pool.md`
   - medium：`prompts/examples/interview-redis-expire-delete.md`、`prompts/examples/interview-thread-pool-create.md`
   - 样题不在题库里，只作参照；它们 front matter 里的 id、`related`、`prerequisites` 不要照抄。
1. **定题**：这道题面试官想确认什么？列出 3–5 个必须答到的考点，作为「要点」的草稿。
   - 按**面试口径**列：面试官通常期望听到的维度都要覆盖（例如对比类题目常问「实现层面」「释放方式」「功能差异」「怎么选」）。官方 API 文档里没写的维度，去规范、源码、JEP 里找来源，找不到才省略。
   - 题目太大（如「讲讲 Redis」）→ 拆成多题，只答其中一道。
   - 标题有歧义 → 改写标题，让它只有一个答法。
2. **建立关联**：先用 `grep -rH "^title:" questions/` 列出题库已有标题（见「难度与前置关系」）。
   - 读懂本题之前必须先懂的题 → 填进本题 `prerequisites`。
   - 以本题为前置的已有题 → 在对方的 `prerequisites` 里加上本题。
   - 话题相近、但没有先后依赖的题 → 双方 `related` 互相加上。
   - 需要的前置题题库里还没有 → **不在本次任务里写**，在交付汇报的「缺少的前置题」里给出建议标题。
   - 改已有题目时只动 `related` / `prerequisites` 这两行。
3. **查证**：八股题的结论大多早已稳定，通用概念（什么是线程池、TCP 为什么三次握手）不用逐条查。只把答案里的**数字、默认值、版本行为**列成事实清单，逐条找一手来源：
   - 优先级：官方文档 > 官方源码 / 配置文件 > RFC / 规范 > 作者本人的论文或博客。
   - 不用：二手面经、博客转述、AI 回答。
   - 事实清单里的来源要实际打开核对（`curl` 或网页抓取工具），确认原文支持你的说法；不能凭记忆填 `references`。
   - 找不到一手来源的事实**不写**，或改成不含具体数字的定性描述。
   - 与版本相关的行为写明版本边界，并填 `appliesTo`。
4. **写作**：按下面的分段规则填写。
5. **跑实验**（极少数写了小实验的题）：代码块原样复制出来运行，把真实输出写回注释。
6. **自检**：逐条过一遍「自检清单」。
7. **校验**：`bank-spec fix-ids` 补号；`bank-spec validate` 和 `node scripts/check.mjs <新文件>` 都要零错误、零警告；提示（info）不用处理，在汇报里列出即可。
8. **汇报**：完成后按「交付汇报」的格式回复。

## 分段规则

### front matter

| 字段 | 规则 |
|---|---|
| `title` | 一个问句，只有一种答法；不写「请简述」「谈谈你的理解」 |
| `type` | concept 原理 / scenario 场景 / coding 写代码 / design 设计 / behavioral 行为 / choice 选择 |
| `difficulty` | easy 讲清是什么、怎么用、为什么需要 / medium 讲清机制 / hard 讲清取舍或源码。与题型无关；清单给了初值，按内容判断不合适可以改，并在汇报里说明理由 |
| `importance` | 3 高频必考（约 20%）/ 2 常见（约 60%）/ 1 加分（约 20%）。表示面试被问到的频率，与难度无关。清单给了就原样使用（全库统一评定，单题看不到整体分布） |
| `tags` | 1–3 个，第一个是主要考点。标签表达知识点、不带领域前缀，必须已在 `bank.yaml` 声明。批量生成时用清单给定的标签，**不改 `bank.yaml`**；觉得缺标签，在汇报里提出 |
| `appliesTo` | 答案依赖版本时必填，如 `["Redis >= 6.0"]`、`["Java >= 21"]` |
| `references` | 事实清单里每个来源都列上；标题写清是哪份文档 |
| `source` | 原创写 `{ name: FaceE, license: CC-BY-4.0 }`；改编写原作者与许可 |
| `reviewedAt` | 完成查证的日期 |
| `estimatedMinutes` | 面试中口头答完需要的分钟数 |

### 一句话（必填，≤ 80 字，1–2 句）

面试官问完，开口第一句就说它。必须是**结论**，不是铺垫。

- ✅ Redis 用惰性删除加定期删除两种方式清理过期 key，剩下的由内存淘汰策略兜底。
- ❌ Redis 的过期删除是一个很重要的知识点，主要涉及多种策略。（没有结论）
- ❌ 联合索引通常按从左到右连续的列来定位数据；中间缺列或遇到范围条件会限制后续列用于确定扫描范围，但不代表后续列完全无用。（限定语堆满一句，听不出主结论；例外放到要点和详解里）

### 要点（必填，3–5 条，每条 ≤ 40 字）

答案的评分标准：用户自评时逐条勾选「我答到了吗」。

- 每条只写**一个可自查的具体事实**，不写话题。
- `|3` 核心要点每题最多 2 条；`|2` 重要；不标为加分项（权重 1）。
- ✅ `[|3] 定期删除每批抽查 20 个，过期比例超过 10% 就继续`
- ❌ `[|3] 定期删除的原理`（是话题，没法自查）
- ❌ `[|2] 惰性删除和定期删除，以及主从复制的处理`（一条塞了多件事）

### 详解（建议 ≤ 1500 字，内部用 `###` 分节）

**读者假设：基础薄弱、主要做过项目的求职者。** 一句话和要点是面试口径；详解负责让这样的读者真正看懂。按三层写：

1. **`### 先搞懂：…`**（第一节，必写）：用白话说清这东西是什么、为什么需要它、不这样会怎样。
   - 从读者做项目时见过的场景切入（扣库存、发验证码、上传文件），再给**一个**生活类比；类比只帮助理解，后文仍要给出准确说法。
   - 这一节不出现规范术语（如 happens-before、内存语义、监视器指令），它们放到机制节或进阶节。
   - 最后列出后文要用的术语，每个用一句白话解释。
2. **机制节**（若干节，节标题写「X：一句话特点」，如「惰性删除：用到时再检查」）：按发生顺序讲机制，再讲为什么这样设计。术语第一次出现时，用括号或一句话解释。
3. **`### 进阶：…（基础薄弱可先跳过）`**（最后一节，medium / hard 建议写）：源码入口、底层实现、版本差异表、调参项。基础读者跳过它，也不影响理解前面的内容。

- 前置知识不在本题展开，交给 `prerequisites` 关联的题（见流程第 2 步）。

**语气**：像一位耐心的前辈在讲解，不像 API 文档的译文。短句，一句只说一件事，主语写清楚。

- ✅ 线程 A 改完数据、释放锁之后，线程 B 再拿到同一把锁，就一定能看到 A 改过的值。
- ❌ 释放锁与另一个线程随后获取同一把锁，还能保证前者的修改对后者可见。（主语不清，翻译腔）

先搞懂节的对比：

- ✅ 「大促时两个请求同时扣库存，都读到还剩 1 件，都扣成功，结果卖出 2 件。锁就像试衣间的门锁：一个人进去锁上门，下一个人只能在外面等。」
- ❌ 「锁让使用同一把锁的线程互斥进入受保护的代码。」（对没学过的人等于没说）

### 难度与前置关系

题库不分「基础题 / 面试题」两层。每道题的深浅由 `difficulty` 表达，学习先后由 `prerequisites` 表达，学习顺序由专题路线（`collections`）表达：

| | easy | medium | hard |
|---|---|---|---|
| 例子 | Redis 怎么给 key 设置过期时间？ | Redis 过期 key 是怎么被删除的？ | Redis 定期删除为什么用游标扫描替代随机抽样？ |
| 讲清 | 是什么、怎么用、为什么需要 | 怎么实现、为什么这样设计、有什么坑 | 取舍、源码、版本差异 |
| 篇幅 | 短；进阶节可省略 | 可以有进阶节 | 进阶节通常要写 |

- `prerequisites` 是有方向的依赖：「不先懂 B 就看不懂 A」才写；任何难度的题都可以有前置题。
- `related` 是双向的关联：话题相近、没有先后依赖。
- 有前置题时，「先搞懂」只用一两段做铺垫，完整背景交给前置题；追问可以直接引出后续题（「详见相关题『…』」）。

**写作规则**

- 每节解决一个问题。
- 出现数字就要有来源；写源码函数名、配置项名用行内代码。
- 源码函数名、内部常量只放在「进阶」节；机制节用它们做了什么来描述。
- 不写「面试加分项」「一定要记住」「灾难」「秒杀」等口号；不写空泛总结段。
- 不确定的不写；有争议的写清楚在什么条件下成立。
- 性能结论最容易写错：「两者性能相当」「吞吐远高于」这类比较，没有官方文档或可复现的基准就不写，改写成「性能差异取决于 JDK 版本和竞争程度，需要实测」。

#### 方案对比（有替代方案时必写）

题目涉及「有几种做法」「新旧版本」「为什么选 A 不选 B」时，详解中必须有一张对比表：

- 放在标题含「对比」的小节里，如 `### 方案对比：…`、`### 三种删除策略对比`；
- 第一列是方案，其余 3–5 列选最能区分方案的维度（如原理、开销、优点、缺点、适合场景），每格一句短语；
- 表后紧跟一句以「结论：」开头的话：默认选哪个、什么条件下换成另一个；
- 表里的每条事实同样要有出处；没有可比方案的题不硬凑。

### 示例（可选）

只放能说明问题的最小代码或命令。代码块必须标语言，单块 ≤ 40 行。

#### 小实验（默认不写）

**绝大多数题不写实验。** 八股题的答案早已稳定，读者需要的是讲清楚，不是自己跑一遍。`## 示例` 只放一段最小用法代码（如怎么创建线程池、一条 `SET … EX` 命令），没有合适的代码就整节省略。

只有同时满足下面三条才写实验，整个题库预计只有很少几道：

1. 结论明显反直觉，很多人记错（如「过期 key 到期后不会马上从内存里消失」）；
2. 几条命令或二十行左右的代码就能复现，输出确定；
3. 正文讲完后读者仍然很难相信。

写实验时遵守：

- **验证核心结论**：实验要证明某条 `|3` / `|2` 要点或某条易错点，不验证边角行为。对比类题目最好把两种方案放进同一个实验，让读者看到差别（例如同样「提前 return 忘了解锁」，`synchronized` 和 `ReentrantLock` 各自的结果）。
- **复制即可运行**：Java 写成带 `main` 的完整类；Redis 等中间件用 `docker run` 起临时实例，写成可直接粘贴的 shell 命令；不依赖项目代码。
- **Windows 也能跑**：Windows 的 Git Bash 会把以 `/` 开头的参数改写成 Windows 路径，`docker exec lab cat /tmp/x` 会失败。容器里的路径要写进 `sh -c '…'` 的引号里，如 `docker exec lab sh -c 'cat /tmp/x'`。
- **输出写在代码里**：Java 的输出原样放在类后面的 `//` 注释里，一行注释对应一行输出，不加「输出：」之类的前缀；命令输出写在行尾 `# →` 之后；关键行用 `←` 标出说明。
- **注释里是原样输出，不是摘要**：输出太长时，在命令里用 `cut`、`awk` 或只查需要的列把它截短，让命令本身打印出注释里的内容；不要运行完再手工改写成「key: idx_abc, key_len: 12」这样的摘要。
- **输出必须确定**：靠 `sleep` 等时间差才能得到的结果不可靠，用 `CountDownLatch`、`join` 等手段保证顺序。等容器里的服务启动，用一行循环探测，不用固定的 `sleep 20`，例如：`until docker exec lab mysql -uroot -plab -e "SELECT 1" >/dev/null 2>&1; do sleep 1; done`。
- **输出要和正文一致**：逐行对照正文和要点。某行输出看起来和正文结论矛盾（例如正文说「范围条件后的列不再参与定位」，输出的 `key_len` 却显示用到了后面的列），要么在正文里解释原因，要么换掉这一行；不能留给读者自己发现矛盾。
- **必须实际运行过**：作者在写入前真实运行，并在代码块前注明环境，如「JDK 21 实测」「Redis 7.2 / 8.0 实测」。输出不确定的（线程名、耗时、随机数）不写进注释，或改写实验让输出确定。
- 需要调试开关的（如 `DEBUG` 命令），注明「仅限实验」，并把对应文档加入 `references`。
- 不放截图。

### 易错点（可选，无序列表）

写**真实存在的误解**，每条一句话说清错在哪。

- ✅ 以为 key 到期的那一刻一定会被删除
- ❌ 不要忘记复习这个知识点（不是误解）

### 追问（可选，2–4 条，答案 ≤ 150 字）

面试官顺着这道题最可能问的下一句。答案直接给结论加一句理由；需要长篇展开的，升级为独立题并互相 `related`。

## 交付汇报

完成后用下面的格式回复（不写进题目文件）：

```markdown
新增文件：questions/<category>/q_xxx.md
关联：prerequisites / related 改了哪些文件
缺少的前置题：建议标题 + 一句话说明它讲什么（没有写「无」）
难度调整：改了清单给的难度时，写原难度 → 新难度和理由（没有写「无」）

事实清单：
| 事实 | 来源 URL | 原文摘录（一句） |
|---|---|---|

实验：运行命令 + 实际输出（原样粘贴）；没写实验时说明理由
校验：bank-spec validate 的最后一行输出
```

## 自检清单

- [ ] 只做过项目、没系统学过这块的人，读完「先搞懂」和机制节能复述出要点
- [ ] 先搞懂从项目场景切入，没有规范术语；全文是短句白话，不是 API 文档译文
- [ ] 主结论说得直白，「通常」「可能」这类限定语没有堆在同一句里；每节第一句就是结论
- [ ] 代码和实验对新手也看得懂，没有不必要的工程写法
- [ ] 前置题已关联（本题 `prerequisites`、对方 `prerequisites` 或双方 `related`）；缺少的已在汇报里列出
- [ ] 机制节里每个术语第一次出现都有白话解释；源码名只出现在「进阶」节
- [ ] 一句话是结论，单独说出来也能得分
- [ ] 要点 3–5 条，每条是一个能勾选的具体事实，`|3` 不超过 2 条
- [ ] 每个数字、默认值、版本行为都能在 `references` 里找到出处
- [ ] 与版本相关的内容写了 `appliesTo` 和版本边界
- [ ] 没有无出处的效果数据（如「召回率提升 18%」）、没有绝对化结论（如「唯一」「一定」）
- [ ] 有替代方案的题有对比表，表后有选型结论
- [ ] 没有为了写而写实验；极少数写了实验的，满足三条条件，代码块按原样运行过，注释中的输出与实际一致
- [ ] 没有引用不存在的图片（「如下图」）
- [ ] 易错点是真实的误解，追问答案 ≤ 150 字
- [ ] `bank-spec validate` 零错误、零警告
