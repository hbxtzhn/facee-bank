## 一句话
分布式锁是让多台服务器之间互斥执行同一段逻辑的锁，锁放在大家都能访问的地方，并且必须带超时时间。

## 要点
- [kp1|3] 多个进程在不同机器上，单机的 synchronized 管不到它们
- [kp2|3] 锁存放在所有节点都能访问的地方，如 Redis、ZooKeeper
- [kp3|2] 典型场景：集群里的定时任务、抢单、防重复提交
- [kp4|2] 锁必须设超时时间，否则持有者宕机后锁永远释放不了

## 详解
### 先搞懂：单机锁为什么不够用
假设订单系统部署了三台服务器，每台都有一个定时任务，每天零点给用户发优惠券。三台同时跑，用户就会收到三张券。

`synchronized` 和 `ReentrantLock` 只在一个 JVM 里有效，三台服务器是三个独立的进程，互相看不到对方的锁。

生活类比：三个人都想用同一间会议室，每个人手里各有一份自己的预约本，谁也看不到别人的。要想不冲突，就得有一块挂在门口、所有人都看得见的预约牌。分布式锁就是这块牌。

后文用到的词：

- **互斥**：同一时刻只有一个人能拿到锁。
- **超时时间**：锁自动失效的时间，到点自动释放。

### 分布式锁解决什么问题
只要多个进程要抢同一份资源，就需要它：

- **定时任务**：集群里每台机器都有任务，只想让一台执行。
- **抢单**：多个服务同时处理同一个订单，只能一个成功。
- **幂等**：同一个请求重复到达，只处理一次。

### 为什么锁一定要有超时时间
想象某台服务器拿到锁以后突然断电，没来得及释放。如果锁没有超时时间，这把锁就永远留在那里，别的服务器再也拿不到。

加上超时时间，锁到点自动消失，别人就能接着干。代价是：如果业务执行得比超时时间长，锁会在业务做完之前失效，这个问题要用续期等办法处理。

### 常见的实现方式
- **Redis**：用 `SET key value NX EX` 加锁，简单、快，实际项目里最常见。
- **Redisson**：封装好的 Redis 客户端，带可重入、自动续期，底层用 Lua 脚本。
- **ZooKeeper**：用临时节点做锁，一致性更强。

## 示例
```bash
# 抢到返回 OK，没抢到返回 (nil)；30 秒后自动失效
SET lock:coupon-job 1 NX EX 30
```

## 易错点
- 以为 synchronized 在集群里也能用；它只对同一个 JVM 里的线程有效
- 以为加了锁就万无一失；没有超时时间，宕机会造成永久占用
- 以为超时时间设得越长越安全；时间过长会让故障后的恢复变慢

## 追问
### [f1] 业务执行时间超过锁的超时时间会怎样？
锁会提前失效，别的线程能拿到锁，两个线程就同时在执行了。常见处理是给锁续期，比如 Redisson 的看门狗。
