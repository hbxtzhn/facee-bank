## 一句话
JOIN 的表越多，可选的连接顺序和中间结果越多，优化器更容易选错，结果集也容易膨胀。可以拆成几个简单查询，在应用层组合。

## 要点
- [kp1|3] 表越多，可选的连接顺序越多，优化器越容易选错
- [kp2|3] 一对多关系连续相乘，结果行数会急剧膨胀
- [kp3|2] 拆成多个简单查询，在应用层按 id 组装
- [kp4] 简单查询更容易走索引、命中缓存，也更好排查慢查询
- [kp5] 多表 JOIN 不是禁止，关键是每一步都有索引、结果集可控

## 详解
### 先搞懂：一次拼太多，越拼越乱
假设要做一个订单详情页：订单、用户、商品、优惠券、物流、地址，共六张表。如果写成一条 SQL 把它们全部 JOIN 起来，会出现两个问题。

类比：开会要同时对齐六个部门的数据。让六个人坐在一张桌子上一起对，比两两对完再汇总要乱得多：谁先谁后、中间对出了多少结果，都很难控制。

后文会用到这几个词：

- **连接顺序**：多张表连接时，先连哪两张、再连哪一张。
- **中间结果**：前几张表连完之后、还没连后面表时的那批行。
- **结果集**：一条查询最终返回的全部行。

### 问题一：连接顺序变多，执行计划容易出问题
N 张表有很多种连接顺序。优化器要根据统计信息估算成本，选出一个顺序。表越多，估算越容易偏差，选出来的顺序可能很慢。

另外，每多一张表，就要多一次内层查找。任何一张表缺了索引，整条查询都会被拖慢。

### 问题二：结果集会膨胀
一对多的关系会让行数相乘。一个订单有 5 个商品、3 张优惠券，两者同时 JOIN，同一个订单会变成 15 行，订单里的字段被重复返回 15 遍。

这样会带来几个后果：

- 网络传输的数据变多，应用层内存占用变大；
- 应用层还要把重复行重新合并成对象，代码更复杂；
- 加上排序或分页之后，数据库要处理的行数更多。

### 拆分：多个简单查询再组合
常见的拆法是：

1. 先查主表，拿到一批主键；
2. 用 `IN` 一次性查出各个关联表里对应的行；
3. 在应用层按 id 建立映射，把结果拼起来。

这样做的好处：

- 每条 SQL 简单，容易走索引；
- 部分关联数据（如商品信息）可以放缓存；
- 出了慢查询，能一眼看出是哪张表的问题；
- 表分了库之后，本来也没法跨库 JOIN。

代价是多了几次网络往返，应用层代码要多写一些。

### 并不是 JOIN 越少越好
两三张表、都有索引、结果行数可控的 JOIN，数据库做得又快又好。判断标准不是「几张表」，而是每一步的连接列有没有索引，中间结果是不是可控。

## 示例
```sql
-- 第一步：先查订单
SELECT id, user_id FROM orders WHERE id IN (1001, 1002, 1003);

-- 第二步：再一次性查关联表，应用层按 id 拼装
SELECT id, nickname FROM users WHERE id IN (7, 8);
SELECT order_id, sku_name FROM order_items WHERE order_id IN (1001, 1002, 1003);
```

## 易错点
- 把「不建议 JOIN 太多表」理解成「不允许用 JOIN」，常见的两三表连接完全正常
- 拆成多个查询后，在应用层循环里一条条查，变成 N+1 查询，比 JOIN 更慢
- 多个一对多关系同时 JOIN，没发现行数在相乘

## 追问
### [f1] 什么是 N+1 查询问题？
先查出 N 条主记录，再对每条记录单独发一条查询取关联数据，总共发出 N+1 条 SQL。解决办法是把第二步改成 `IN` 批量查询，或者改用 JOIN。

### [f2] 分库分表之后还能 JOIN 吗？
跨库的表通常没法直接 JOIN，只能在应用层组合，或者提前做冗余。所以多表 JOIN 拆成简单查询，也是为后续拆分做准备。
