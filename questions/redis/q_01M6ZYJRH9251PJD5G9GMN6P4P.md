## 一句话
write 只是把数据交给操作系统的缓存，真正写到磁盘要靠 fsync；刷盘时机晚，宕机时缓存里没落盘的数据就会丢。

## 要点
- [kp1|3] write 成功只代表数据进了操作系统缓存，不代表已经在磁盘上
- [kp2|3] fsync 才会要求操作系统把缓存数据真正写到磁盘
- [kp3|2] 操作系统会定期自己刷盘，但时机不受程序控制
- [kp4] 进程崩溃缓存还在，机器断电或内核崩溃缓存才会丢

## 详解
### 先搞懂：寄快递先放前台，不等于已发出
你把快递交给小区前台，前台说“收到了”。但包裹还在前台，要等快递员来取才算真正发出。如果前台这时候停电，包裹可能丢了。程序调用 write，就像交给前台：操作系统说“收到”，数据其实还在内存缓存里。

后文用到的词：
- **页缓存**：操作系统在内存里缓存文件数据的区域，读写文件都先经过它。
- **刷盘**：把缓存里的数据真正写到磁盘。
- **fsync**：程序主动要求立即刷盘的系统调用。

### 为什么操作系统要缓存
磁盘慢，内存快。如果每次写文件都等磁盘写完，程序会非常慢。操作系统的做法是：数据先写进页缓存，立刻返回，之后在合适的时候批量写到磁盘。这对性能很好，代价是数据在缓存里时还不安全。

### 什么情况会丢数据
- 只是程序崩溃（进程被杀）：页缓存归操作系统管，数据还在，通常不会丢；
- 机器断电、系统内核崩溃：页缓存里还没刷盘的数据直接丢失。

所以“write 成功”不等于“数据安全”，要看有没有 fsync 过。

### fsync 解决什么，代价是什么
fsync 会等数据真正到磁盘才返回，数据更安全。但磁盘慢，每次都 fsync，吞吐会明显下降。

所以 Redis 的 AOF 让你选择多久 fsync 一次。每条命令都 fsync 最安全。每秒一次是折中。完全不主动 fsync，则交给操作系统。

### 进阶：磁盘自己也有缓存（基础薄弱可先跳过）
有的磁盘或磁盘控制器自带缓存，fsync 返回后数据是否一定落到介质上，还取决于硬件。企业级设备通常有掉电保护，这里不展开。

## 示例
```java
try (FileOutputStream out = new FileOutputStream("data.log", true)) {
    out.write("hello\n".getBytes());   // 数据进入操作系统缓存
    out.getFD().sync();                // 要求操作系统刷盘，对应 fsync
}
```

## 易错点
- 以为 write 返回就代表数据落盘；它通常只写入了缓存
- 以为进程被杀一定会丢缓存数据；缓存由操作系统管理，进程退出后通常仍会被写出
- 以为 fsync 没有代价；它会明显降低写入速度

## 追问
### [f1] Redis 的 everysec 为什么最多丢约 1 秒？
每秒调用一次 fsync，宕机时两次 fsync 之间的数据还在缓存里，所以最多丢大约这一秒的写入。
