## 一句话
在网关或 Nginx 限制进入系统的请求量，超出阈值的请求直接降级，返回兜底数据或友好提示，让数据库不被压垮。

## 要点
- [kp1|3] 限流：控制单位时间放进来的请求数，超出的直接拒绝
- [kp2|3] 降级：系统扛不住时返回兜底结果，放弃部分功能保核心
- [kp3|2] 限流通常设在网关或 Nginx，在请求到达业务之前拦截
- [kp4|2] 它是系统保底策略，对穿透、击穿同样适用
- [kp5] 兜底数据可以是默认值、静态页或旧缓存

## 详解
### 先搞懂：餐厅爆满时的做法
饭点餐厅门口排起长队，厨房出不了那么多菜。老板有两招：一是门口控制进店人数，满了请后面的人等一等，这是**限流**；二是只做几道简单的菜，复杂菜品先不卖，这是**降级**。目的是保证厨房不垮，已经进店的客人能吃上饭。

雪崩发生时，缓存挡不住请求，数据库面对的流量远超平时。我们没法让数据库瞬间变强，只能让流量变小。

后文用到的术语：

- **限流**：限制单位时间内通过的请求数量。
- **降级**：主动关闭或简化部分功能，返回兜底结果。
- **兜底数据**：事先准备好的默认值、静态内容或旧数据。
- **阈值**：触发限流的临界值，比如每秒多少个请求。

### 限流：在入口把住量
限流规则一般设在最外层，比如 Nginx 或 API 网关，因为越早拦截越省资源。常见做法有按 IP、用户或接口限制每秒请求数，超出的直接返回「系统繁忙，请稍后重试」。

也可以在服务内部对访问数据库的操作单独限流，保护数据库这个最脆弱的环节。

### 降级：宁可少一点功能，也不能整个挂掉
被限流的请求或数据库已经不稳时，不要硬扛，而是返回事先准备好的结果：

- 返回默认值，如热门推荐列表。
- 返回静态页面或提示信息。
- 关闭非核心功能，比如评论、推荐，把资源留给下单、支付等核心流程。

用户体验会差一点，但系统整体可用。

### 它的位置：最后一道保底
限流降级不能让缓存命中率回升，它只是保护数据库。所以要和随机 TTL、集群、多级缓存配合：前面这些是预防，限流降级是兜底。同样的办法也能用在缓存穿透和击穿的场景。

## 易错点
- 以为限流能解决雪崩的根因；它只是保护数据库，根因要靠预防手段
- 阈值随便设；设得太低会误伤正常流量，要结合压测和监控确定
- 降级时没有准备兜底数据；返回空白或报错同样影响体验

## 追问
### [f1] 限流有哪些常见算法？
常见的有固定窗口、滑动窗口、漏桶和令牌桶。固定窗口实现简单，但窗口边界可能出现突发；滑动窗口更平滑；令牌桶允许一定程度的突发流量。

### [f2] 限流和降级怎么配合？
限流负责把进入系统的量控制住，被拒绝或处理失败的请求走降级逻辑，返回兜底结果。两者都是为了在压力下保住核心功能。
