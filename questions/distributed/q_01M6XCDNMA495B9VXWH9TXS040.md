## 一句话
给业务加上显式的状态字段，用“处理中、成功、失败”记录异步进度，最终结果通过通知告知用户，失败的任务重试或补偿。

## 要点
- [kp1|3] 用状态字段显式记录异步任务进度，如处理中、成功、失败
- [kp2|3] 处理结束后通过短信、邮件或站内消息通知最终结果
- [kp3|2] 用户查询时看到“处理中”，不要把未完成显示成已完成
- [kp4|2] 失败的任务要能重试或补偿，并保证重复处理也不出错
- [kp5] 发消息和写数据库要一致，避免订单有了消息却丢了

## 详解
### 先搞懂：外卖订单的状态
你点外卖，App 上会依次显示“已下单、商家接单、配送中、已送达”。你不会一下单就看到“已送达”。每一步状态都是系统记下来的，你随时可以看到进展到了哪一步。

异步处理要避免不一致，用的就是这个办法。先说几个词：

- **中间态**：任务还没做完时的状态，比如“处理中”。
- **状态流转**：状态只能按约定的路径变化，比如处理中变成功或失败。
- **幂等**：同一个操作重复做多次，结果和只做一次一样。

### 第一步：把状态存下来
异步处理之后，最怕的是调用方不知道现在到底怎么样了。解决办法是在数据库里给任务加一个状态字段：

1. 提交时，记录状态为“处理中”；
2. 消费者处理成功，改为“成功”；
3. 处理失败且重试也不行，改为“失败”。

页面和接口查询时，直接读这个状态，用户就知道是还在处理、成功还是失败。

### 第二步：主动通知最终结果
用户不会一直盯着页面。处理完成后，可以通过短信、邮件或站内消息告诉他结果。失败时也要告诉他，并提示下一步该怎么做。

### 第三步：处理失败和重复
- **失败重试**：消费失败时，让队列重新投递，次数用完后转入人工处理或补偿流程；
- **幂等处理**：重试或重复投递会让同一条消息被处理多次，消费者要靠订单号等唯一标识，保证只生效一次；
- **状态只能向前走**：比如已经是“成功”的任务，不会再被改回“处理中”。

### 进阶：发消息和写库要保持一致
如果先写数据库再发消息，两步之间进程挂了，就会出现“订单有了，消息没发”。常见办法是本地消息表：把消息和业务数据放在同一个本地事务里存下来，再由后台任务可靠地发送出去。

## 示例
```sql
-- 订单表中用状态字段记录异步进度
ALTER TABLE orders
  ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'PROCESSING';

-- 消费成功后，只允许从处理中变成成功
UPDATE orders SET status = 'SUCCESS'
WHERE order_no = 'O123' AND status = 'PROCESSING';
```

## 易错点
- 以为异步处理完就万事大吉；没有状态和通知，用户永远不知道结果
- 更新状态时不带条件，重复消息会把已经完成的任务状态覆盖掉

## 追问
### [f1] 消息一直处理失败怎么办？
重试几次后仍失败，就把消息转入死信队列，同时将业务状态改成失败并通知用户，再由人工排查或走补偿流程。
