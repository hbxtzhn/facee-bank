## 一句话
Structured Outputs 在解码的每一步，根据 schema 或语法屏蔽不合法的 token，只允许选符合结构的，所以输出天然合规，不用事后校验重试。

## 要点
- [kp1|3] 每一步生成前，先算出当前位置哪些 token 合法
- [kp2|3] 不合法的 token 概率被屏蔽，模型只能在合法的里选
- [kp3|2] 屏蔽是在生成过程中完成的，不是生成完再检查
- [kp4] 保证的是结构，字段取值是否正确仍要靠模型和校验

## 详解
### 先搞懂：像填表格时只能写进格子里
事后校验好比：让人自由写，写完再检查对不对，不对就让他重写。

解码阶段约束好比：给他一张印好格子的表，每个格子只允许填数字或选项，想写错都写不出来。结构一开始就被限定了。

后文用到的词：
- **解码**：模型逐个选出 token 的过程。
- **logits**：模型给每个候选 token 打的原始分数。
- **语法/schema**：描述合法输出长什么样的规则。
- **屏蔽**：把不合法 token 的概率设为零，使其不可能被选中。

### 生成过程怎么被约束
1. 把 schema 转换成一套语法规则，可以理解成一个状态机。
2. 模型每一步先正常算出各 token 的分数。
3. 根据已生成的内容，状态机判断下一步允许哪些 token。
4. 把不允许的 token 屏蔽。
5. 在剩下的合法 token 里按采样策略选一个。
6. 更新状态，进入下一步。

举例：schema 要求某个字段是整数，刚写完 `"age":` 之后，只有数字相关的 token 是合法的，字母之类都被屏蔽。

### 和事后校验的区别
| 方式 | 何时检查 | 失败怎么办 | 特点 |
|---|---|---|---|
| 事后校验 | 生成完再查 | 重试或报错 | 可能反复重试 |
| 解码约束 | 生成每一步 | 不会生成非法结构 | 结构一次到位 |

结论：对结构要求严格时优先用解码约束；字段取值是否合理，仍需业务校验。

### 它有什么局限
- 保证的是结构合规，不保证内容正确，值可能是错的。
- 支持的 schema 特性有限，复杂规则可能不被支持，以接口文档为准。
- 过于苛刻的约束可能影响内容质量，需要实测。

### 进阶：为什么是在 token 层面做（基础薄弱可先跳过）
因为模型本来就是逐 token 选择，在每次选择前加一道过滤，改动最小，也最容易保证结构。实现细节如状态机怎样编译，各家做法不同，这里不展开。

## 易错点
- 以为结构合规就等于答案正确
- 以为所有 schema 特性都能被强制支持
- 以为这是生成后的检查；它发生在生成过程中

## 追问
### [f1] 为什么这比重试更可靠？
重试靠碰运气，可能反复失败；解码约束让非法结构根本无法生成，结果更确定。

### [f2] 用了它还需要做什么校验？
仍要校验字段值是否合理，比如数值范围、业务含义，因为结构合规不代表内容正确。
