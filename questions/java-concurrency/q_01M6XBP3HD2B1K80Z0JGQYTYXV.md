## 一句话
可见性问题是指一个线程改了共享变量，别的线程却还在读旧值。原因是每个线程有自己的本地内存，修改不一定及时写回主内存，别人也不一定重新去读。

## 要点
- [kp1|3] 可见性：一个线程修改共享变量后，其他线程能及时看到
- [kp2|3] 原因：线程先改自己的本地内存副本，不一定马上写回主内存
- [kp3|2] 其他线程也可能一直读自己本地的旧副本，不去主内存重新读
- [kp4|2] volatile、synchronized、final 都能保证可见性

## 详解
### 先搞懂：改了没人知道
假设你在后台线程里写了一个循环，每次检查「是否要停止」的标志；主线程在界面上点了停止，把标志改成 true。结果后台线程就是停不下来，一直在跑。这就是典型的可见性问题：主线程改了，后台线程没看到。

类比：公司的通知栏换了新通知，但有个同事手里一直拿着自己抄的旧版本，从不抬头看通知栏。

后文用到的几个词：
- **可见性**：一个线程的修改，别的线程能及时读到。
- **本地内存**：线程私有的工作区，保存共享变量的副本。

### 问题是怎么发生的
按 JMM 的抽象，共享变量在主内存，每个线程有自己的本地内存副本：

1. 线程 A 修改了本地副本，但还没写回主内存；
2. 线程 B 读的是自己本地的旧副本，或者从主内存读到了还没被更新的旧值；
3. 于是 B 看不到 A 的修改。

为了效率，编译器和 CPU 都会缓存变量值，所以没有同步手段时，别的线程什么时候能看到，是不确定的。

### 怎么保证可见性
- `volatile`：写入时立即刷回主内存，读取时总是读最新值；
- `synchronized`：线程退出同步块时把修改刷回主内存，别的线程进入同步块时重新读取；
- `final`：构造完成后，final 字段对其他线程可见（前提是构造过程中没有把 this 泄漏出去）。

## 示例
```java
class Task implements Runnable {
    private volatile boolean stop = false; // 去掉 volatile，循环可能停不下来

    public void run() {
        while (!stop) { /* 干活 */ }
    }
    public void shutdown() { stop = true; }
}
```

## 易错点
- 以为不加 volatile 就一定看不到；是不保证看到，有时能看到，这让问题更难发现
- 以为 volatile 能解决所有并发问题；它只保证可见和有序，不保证 i++ 这类复合操作的原子性
- 把可见性和原子性混为一谈；可见是「能看到」，原子是「不会被打断」，是两件事

## 追问
### [f1] volatile 是怎么保证可见性的？
写 volatile 变量时，会把值立即刷回主内存；读 volatile 变量时，会让本地缓存失效，重新从主内存读取。这样其他线程总能读到最新值。
