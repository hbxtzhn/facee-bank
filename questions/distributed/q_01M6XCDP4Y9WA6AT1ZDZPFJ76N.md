## 一句话
消费速率靠消费者自己控制：设置每次拉取的批量和并发线程数，再配合限流，让积压的消息平稳消化，不压垮下游。

## 要点
- [kp1|3] 拉取批量决定每次取多少条，批量越大单次压力越大
- [kp2|3] 并发线程数决定同时处理多少条消息
- [kp3|2] 在消费逻辑里加限流，保护数据库等下游服务
- [kp4|2] 处理不过来时暂停拉取，消息安全地留在队列里
- [kp5] 速率要结合下游承受能力和压测来定

## 详解
### 先搞懂：食堂打饭的窗口
食堂打饭，窗口前排着长队。要控制出餐速度，你可以：

- 一次给每个人盛几勺（每次取多少）；
- 开几个窗口同时打（并发数）；
- 里面忙不过来时，让后面的人先别上前（暂停拉取）。

消费者控制消费速率，用的是同样的办法。先说几个词：

- **拉取批量**：消费者每次向 Broker 要多少条消息。
- **并发数**：同时有多少个线程在处理消息。
- **下游**：消费者处理消息时要调用的数据库、接口等。

### 为什么要控制速率
队列里积压了很多消息，消费者如果以最快速度全部处理，下游数据库可能被瞬间打满。消费者“能处理多少”应该由下游的承受能力决定，而不是由队列里有多少消息决定。

### 具体的控制手段
1. **控制拉取批量**：一次拉得少，处理压力小。Kafka 里有 `max.poll.records`，RocketMQ 里有 `pullBatchSize`。
2. **控制并发线程数**：线程多处理得快，对下游压力也大。RocketMQ 可以设置 `consumeThreadMin` 和 `consumeThreadMax`。
3. **在代码里限流**：处理每条消息前，先拿令牌或信号量，拿不到就等一等，把调用下游的速度压在安全范围内。
4. **处理不过来就暂停**：拉模式下，消费者不拉就不会有新消息进来，消息留在队列里，这是最安全的刹车。

### 速率怎么定
没有放之四海而皆准的数字。通常先看下游每秒能承受多少次调用，再压测，找到吞吐和稳定性都合适的批量和并发数，上线后根据积压量观察调整。

## 示例
```java
// Kafka：每次最多拉 50 条，数值仅为示例
Properties props = new Properties();
props.put("max.poll.records", 50);

// 用信号量限制同时调用下游的并发数
Semaphore permits = new Semaphore(10);
permits.acquire();
try {
    handle(message);
} finally {
    permits.release();
}
```

## 易错点
- 以为线程开得越多消费越快；超过下游承受能力，只会让下游更慢甚至崩溃
- 批量设得过大，处理时间超过超时时间，消息会被判为失败并重复投递

## 追问
### [f1] 积压很多时，是不是就应该加大消费速率？
不一定。要先看消费慢的原因。如果瓶颈在下游，加大速率只会雪上加霜。应先解决下游的瓶颈，再逐步调大。
