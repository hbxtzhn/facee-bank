## 一句话
重排序分三类：编译器优化时调整语句顺序、CPU 把多条指令重叠执行时调整指令顺序、内存系统因缓存和缓冲区让读写生效顺序变乱。

## 要点
- [kp1|3] 编译器重排：编译器生成指令时重新安排语句顺序
- [kp2|3] 指令级并行重排：CPU 让没有数据依赖的多条指令重叠执行
- [kp3|2] 内存系统重排：缓存和读写缓冲区让读写看起来乱序
- [kp4] 三类都以不改变单线程结果为底线，多线程下才会暴露

## 详解
### 先搞懂：快递从下单到送到，每一站都可能调换顺序
你同一天买了两件东西：先下单 A，后下单 B。仓库发现 B 就在手边，就先把 B 打包了；快递公司的分拣线上两个包裹同时在跑；最后还有驿站，包裹先放架子上，你取件的时间也不一定和送达顺序一致。每一站都没出错，但你看到的「先后」可能和下单顺序不一样。

代码执行也一样，从源码到数据真正落到内存，要经过三站，每一站都可能调整顺序。后文术语：

- **数据依赖**：后一条语句要用前一条的结果，这种不会被调换。
- **指令**：CPU 能直接执行的最小操作。
- **缓存、写缓冲区**：CPU 内部的小块存储，先把数据存在这里，之后再写入内存。

### 编译器重排：生成指令时调整
编译器（Java 里主要是 JIT 即时编译器）在不改变单线程语义的前提下，可以重新安排语句的先后。例如两条互不依赖的赋值，编译器为了更好地利用寄存器，可能把它们对调。

### 指令级并行重排：CPU 同时跑多条指令
现代 CPU 不是一条一条严格排队执行，而是把多条指令重叠着跑。如果两条指令没有数据依赖，CPU 可以改变它们实际执行的顺序，哪条先完成就先用哪条的结果。

### 内存系统重排：缓存和缓冲区造成的错觉
CPU 写数据时，通常先放进写缓冲区，之后才刷到内存；读数据也可能直接用缓存里的值。结果是：线程 A 先写 X 后写 Y，线程 B 可能先看到 Y 的新值，后看到 X 的新值。这一类并不是指令真的换了位置，而是读写「生效」的顺序在别的线程看来变了，所以也算重排序。

### 方案对比：三类重排序
| 类别 | 谁来调整 | 发生在 | 典型表现 |
|---|---|---|---|
| 编译器重排 | 编译器 | 生成指令阶段 | 源码顺序和指令顺序不同 |
| 指令级并行重排 | CPU | 执行指令阶段 | 无依赖指令的执行顺序改变 |
| 内存系统重排 | 缓存和读写缓冲区 | 读写内存阶段 | 别的线程看到的写入顺序错乱 |

结论：前两类改变的是执行顺序，第三类改变的是别的线程看到的顺序；Java 内存模型用 volatile、锁等规则统一约束这三类，开发者不需要分别处理。

## 示例
```java
int a = 0;
boolean flag = false;

// 线程 1
a = 1;        // 1
flag = true;  // 2

// 线程 2
if (flag) {
    int r = a; // 如果 1、2 被重排，r 可能是 0
}
```

## 易错点
- 以为只有编译器会重排；CPU 和缓存也会让顺序看起来乱
- 以为内存系统重排是指令真的被调换；它是写入生效顺序在其他线程看来不同
- 以为单线程里也要担心重排；有数据依赖的语句不会被调换，单线程结果不变

## 追问
### [f1] 怎么阻止这三类重排序？
在 Java 里用 volatile、synchronized 或 Lock，它们会让编译器不做相关重排，并让 JVM 在合适位置插入内存屏障（限制 CPU 重排的指令），最终保证 happens-before 规定的可见性和顺序。

### [f2] 重排序一定会让程序出错吗？
不会。只有多线程共享数据、又没有同步手段时，才可能看到错乱的中间状态。正确使用锁或 volatile 的程序，不需要关心具体是哪一类重排。
