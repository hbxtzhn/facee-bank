## 一句话
写缓存时，在统一的基础 TTL 上再加一个随机值，让 key 的过期时间分散开，就不会同一时刻集中失效、集中回源。

## 要点
- [kp1|3] 批量写入缓存时，TTL 设成固定值加随机偏移
- [kp2|3] 随机偏移让过期时间分散，数据库压力被摊平
- [kp3|2] 随机范围要和基础 TTL 相称，太小起不到分散作用
- [kp4] 这个办法只防同时过期，防不了单个热点 key 击穿

## 详解
### 先搞懂：大家同一时间下班会堵车
公司如果规定所有人 18:00 整下班，电梯和地铁口就会挤满人。如果规定每人下班时间在 17:30 到 18:30 之间错开，拥堵就小得多。

缓存也是这样。凑巧在同一时刻写入、又设了同样 TTL 的 key，会在同一时刻一起过期。请求同时回源，数据库就像被挤爆的电梯。解决办法就是错峰。

后文用到的术语：

- **TTL**：key 的存活时间，到点自动过期。
- **回源**：缓存没有，转去查数据库。
- **抖动**：在固定值上加一点随机变化。

### 随机 TTL：基础值加一点随机数
做法很简单：不要给所有 key 写死同一个时间，而是用「基础时间 + 随机偏移」。

比如基础时间 30 分钟，再随机加 0 到 5 分钟。这样一批 key 的过期时间就分布在一段区间里。每个时刻只有少量 key 过期，回源请求也被摊平了。

### 为什么这个办法有效
雪崩的危险在于「同一瞬间」的请求量。随机 TTL 不会减少总的回源次数，只是把它拉长到一段时间，数据库每个时刻面对的压力小得多。

### 使用时要注意
- 随机范围要足够大。如果基础 TTL 是 30 分钟，只随机几秒，大部分 key 还是扎堆过期。
- 随机范围也不能过大，否则有的数据缓存太久，更新后读到旧值的时间变长。
- 只对批量写入、过期时间可以有弹性的数据有意义。
- 它不能解决单个热点 key 的击穿，那要用互斥锁或逻辑过期。

## 示例
```java
long base = 30 * 60;                                   // 基础 30 分钟，单位秒
long jitter = ThreadLocalRandom.current().nextLong(0, 5 * 60); // 随机 0 到 5 分钟
redis.opsForValue().set(key, value, base + jitter, TimeUnit.SECONDS);
```

## 易错点
- 把随机值只加在个别 key 上；要让同一批写入的 key 都带随机偏移
- 随机范围太小，key 依然集中在很短时间内过期
- 以为随机 TTL 能防宕机；缓存整体不可用要靠集群和降级

## 追问
### [f1] 除了随机 TTL，还有什么办法避免集中失效？
可以对热点数据不设过期、改用逻辑过期，或者分批预热、错开写入时间。关键是别让一大批数据在同一时刻失效。
