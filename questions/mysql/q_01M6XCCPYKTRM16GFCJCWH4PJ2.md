## 一句话
表锁锁住整张表，开销小但并发低；行锁只锁被访问的行，并发高但开销大，还可能死锁。InnoDB 默认用行锁。

## 要点
- [kp1|3] 表锁锁整张表，加锁快、开销小，并发度最低，不会死锁
- [kp2|3] 行锁只锁具体的行，并发度高，开销大，可能死锁
- [kp3|2] InnoDB 支持行锁，MyISAM 只支持表锁
- [kp4] InnoDB 的行锁加在索引上，查询没用到索引会锁住更多行
- [kp5] 页锁介于两者之间，常见的 InnoDB 和 MyISAM 都没有页锁

## 详解
### 先搞懂：锁一整个仓库，还是只锁一个货架
想象仓库里有很多货架。你要整理其中一个货架：

- 把整个仓库的门锁上，别人谁也进不来：简单，但别人都得等；
- 只围住你要整理的那一个货架：别人可以去其他货架，但要管理很多个「围栏」，更麻烦。

前者就是表锁，后者就是行锁。后文会用到这几个词：

- **锁粒度**：一把锁锁住的范围有多大。
- **并发度**：同一时间能有多少个事务一起干活。
- **死锁**：两个事务互相等对方手里的锁，谁也走不下去。

### 表锁：锁整张表
- 一次锁住整张表，所有对这张表的冲突操作都要等。
- 加锁、解锁的动作简单，开销小。
- 冲突概率高，并发度最低。
- 因为一次只拿一把锁，不会出现死锁。
- MyISAM 只有表锁；InnoDB 也可以用 `LOCK TABLES` 手动加表锁，但一般不建议。

### 行锁：锁具体的行
- 只锁事务访问的那些行，其他行不受影响，冲突概率低，并发度高。
- 要记录每一行的锁信息，开销大、加锁慢。
- 事务会同时拿多把锁，加锁顺序不一致就可能死锁。
- InnoDB 的行锁，实际上是加在索引记录上的。如果查询条件没有用上索引，要扫描很多行，就会锁住很多行，效果接近表锁。

### 页锁：介于两者之间
页锁锁住一页数据（多条相邻记录），开销、并发度都介于表锁和行锁之间，也可能死锁。常见的 InnoDB 和 MyISAM 没有页锁。

### 方案对比：三种粒度
| 粒度 | 锁住什么 | 开销 | 并发度 | 死锁 |
|---|---|---|---|---|
| 表锁 | 整张表 | 小，加锁快 | 最低 | 不会 |
| 页锁 | 一页数据 | 居中 | 一般 | 可能 |
| 行锁 | 单条记录 | 大，加锁慢 | 最高 | 可能 |

结论：高并发的在线业务默认选支持行锁的 InnoDB；批量导入等一次性操作且不怕阻塞的场景，才考虑表锁。

## 示例
```sql
-- 只锁 id = 1 这一行（id 有索引）
SELECT * FROM account WHERE id = 1 FOR UPDATE;

-- 手动锁整张表
LOCK TABLES account WRITE;
UNLOCK TABLES;
```

## 易错点
- 以为 InnoDB 的行锁锁的是「数据行本身」，其实加在索引上，没用索引就会锁很多行
- 以为表锁不会有问题；它的问题是并发度低，大量请求会排队
- 以为行锁一定比表锁快；行锁并发更好，但单次加锁开销更大

## 追问
### [f1] 为什么 UPDATE 的 WHERE 条件没有索引会很危险？
InnoDB 要扫描全表来找符合条件的行，扫描过程中碰到的行都可能被锁住，其他事务的写操作基本都会被挡住，效果接近锁表。
