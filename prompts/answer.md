# 答案生成规范

输入一道题的**标题**（可附分类、题型），输出一份可直接通过 `bank-spec validate` 的 v2 题目文件。
用于 AI 批量生成，也用于人工复核时对照。

## 输入

```yaml
title: Redis 过期 key 的删除策略有哪些？   # 必填
category: redis                           # 必填，取自 bank.yaml categories
type: concept                             # 可选；不填由生成者判断
```

文件骨架由 `bank-spec new --bank . --category <id> --title <标题>` 生成，生成者只填内容，不手写 id。

## 流程

1. **定题**：这道题面试官想确认什么？列出 3–5 个必须答到的考点，作为「要点」的草稿。
   - 题目太大（如「讲讲 Redis」）→ 拆成多题，只答其中一道。
   - 标题有歧义 → 改写标题，让它只有一个答法。
2. **查证**：把答案里每个**数字、默认值、版本行为、API 名称**列成事实清单，逐条找一手来源：
   - 优先级：官方文档 > 官方源码 / 配置文件 > RFC / 规范 > 作者本人的论文或博客。
   - 不用：二手面经、博客转述、AI 回答。
   - 找不到一手来源的事实**不写**，或改成不含具体数字的定性描述。
   - 与版本相关的行为写明版本边界，并填 `appliesTo`。
3. **写作**：按下面的分段规则填写。
4. **自检**：逐条过一遍「自检清单」。
5. **校验**：`bank-spec fix-ids` 补号，`bank-spec validate` 通过，警告也要处理。

## 分段规则

### front matter

| 字段 | 规则 |
|---|---|
| `title` | 一个问句，只有一种答法；不写「请简述」「谈谈你的理解」 |
| `type` | concept 原理 / scenario 场景 / coding 写代码 / design 设计 / behavioral 行为 / choice 选择 |
| `difficulty` | easy 背得出就行 / medium 要讲清机制 / hard 要讲清取舍或源码 |
| `importance` | 3 高频必考（约 20%）/ 2 常见（约 60%）/ 1 加分（约 20%） |
| `tags` | 1–3 个，必须已在 `bank.yaml` 声明；缺的先加到 `bank.yaml` |
| `appliesTo` | 答案依赖版本时必填，如 `["Redis >= 6.0"]`、`["Java >= 21"]` |
| `references` | 事实清单里每个来源都列上；标题写清是哪份文档 |
| `source` | 原创写 `{ name: FaceE, license: CC-BY-4.0 }`；改编写原作者与许可 |
| `reviewedAt` | 完成查证的日期 |
| `estimatedMinutes` | 面试中口头答完需要的分钟数 |

### 一句话（必填，≤ 80 字，1–2 句）

面试官问完，开口第一句就说它。必须是**结论**，不是铺垫。

- ✅ Redis 用惰性删除加定期删除两种方式清理过期 key，剩下的由内存淘汰策略兜底。
- ❌ Redis 的过期删除是一个很重要的知识点，主要涉及多种策略。（没有结论）

### 要点（必填，3–5 条，每条 ≤ 40 字）

答案的评分标准：用户自评时逐条勾选「我答到了吗」。

- 每条只写**一个可自查的具体事实**，不写话题。
- `|3` 核心要点每题最多 2 条；`|2` 重要；不标为加分项（权重 1）。
- ✅ `[|3] 定期删除每批抽查 20 个，过期比例超过 10% 就继续`
- ❌ `[|3] 定期删除的原理`（是话题，没法自查）
- ❌ `[|2] 惰性删除和定期删除，以及主从复制的处理`（一条塞了多件事）

### 详解（建议 ≤ 1500 字，内部用 `###` 分节）

**读者假设：基础薄弱、主要做过项目的求职者。** 一句话和要点是面试口径；详解负责让这样的读者真正看懂。按三层写：

1. **`### 先搞懂：…`**（第一节，必写）：用白话说清这东西是什么、为什么需要它、不这样会怎样。可以用一个生活类比，但类比只用来帮助理解，不能代替准确说法。最后列出后文要用的术语，每个用一句白话解释。
2. **机制节**（若干节，节标题写「X：一句话特点」，如「惰性删除：用到时再检查」）：按发生顺序讲机制，再讲为什么这样设计。术语第一次出现时，用括号或一句话解释。
3. **`### 进阶：…（基础薄弱可先跳过）`**（最后一节，可选）：源码入口、版本差异表、调参项。基础读者跳过它，也不影响理解前面的内容。

- 前置知识不在本题展开：在 front matter 的 `prerequisites` 里关联基础题；题库里还没有的，记入待写清单。

### 基础题与面试题的分层

每道面试题之前，至少要有一道基础题把它的前置知识讲清楚，形成「基础题 → 面试题」的学习路径：

| | 基础题 | 面试题 |
|---|---|---|
| 例子 | Redis 怎么给 key 设置过期时间？ | Redis 过期 key 是怎么被删除的？ |
| `difficulty` | easy | medium / hard |
| 作用 | 讲清「是什么、怎么用、为什么需要」 | 讲清「怎么实现、为什么这样设计、有什么坑」 |
| 关联 | `related` 指向面试题 | `prerequisites` 指向基础题 |
| 篇幅 | 短；进阶节可省略 | 可以有进阶节 |

- 面试题的「先搞懂」只用一两段做铺垫，完整的背景交给基础题。
- 基础题的追问可以直接引出面试题（「详见相关题『…』」）。
- 每节解决一个问题。
- 出现数字就要有来源；写源码函数名、配置项名用行内代码。
- 源码函数名、内部常量只放在「进阶」节；机制节用它们做了什么来描述。
- 不写「面试加分项」「一定要记住」「灾难」「秒杀」等口号；不写空泛总结段。
- 不确定的不写；有争议的写清楚在什么条件下成立。

#### 方案对比（有替代方案时必写）

题目涉及「有几种做法」「新旧版本」「为什么选 A 不选 B」时，详解中必须有一张对比表：

- 第一列是方案，其余 3–5 列选最能区分方案的维度（如原理、开销、优点、缺点、适合场景），每格一句短语；
- 表后紧跟一句**结论**：默认选哪个、什么条件下换成另一个；
- 表里的每条事实同样要有出处；没有可比方案的题不硬凑。

### 示例（可选）

只放能说明问题的最小代码或命令。代码块必须标语言，单块 ≤ 40 行。

#### 小实验（结论反直觉、或易错点能用代码验证时必写）

让读者亲手跑一下就能看到结论，比读三段解释更可信：

- **复制即可运行**：Java 写成带 `main` 的完整类；Redis 等中间件用 `docker run` 起临时实例，写成可直接粘贴的 shell 命令；不依赖项目代码。
- **输出写在代码里**：Java 输出放在末尾的 `//` 注释中，命令输出写在行尾 `# →` 之后；关键行用 `←` 标出说明。
- **必须实际运行过**：作者在写入前真实运行，并在代码块前注明环境，如「JDK 21 实测」「Redis 7.2 / 8.0 实测」。输出不确定的（线程名、耗时、随机数）不写进注释，或改写实验让输出确定。
- 需要调试开关的（如 `DEBUG` 命令），注明「仅限实验」，并把对应文档加入 `references`。
- 不放截图。

### 易错点（可选，无序列表）

写**真实存在的误解**，每条一句话说清错在哪。

- ✅ 以为 key 到期的那一刻一定会被删除
- ❌ 不要忘记复习这个知识点（不是误解）

### 追问（可选，2–4 条，答案 ≤ 150 字）

面试官顺着这道题最可能问的下一句。答案直接给结论加一句理由；需要长篇展开的，升级为独立题并互相 `related`。

## 自检清单

- [ ] 只做过项目、没系统学过这块的人，读完「先搞懂」和机制节能复述出要点
- [ ] 机制节里每个术语第一次出现都有白话解释；源码名只出现在「进阶」节
- [ ] 一句话是结论，单独说出来也能得分
- [ ] 要点 3–5 条，每条是一个能勾选的具体事实，`|3` 不超过 2 条
- [ ] 每个数字、默认值、版本行为都能在 `references` 里找到出处
- [ ] 与版本相关的内容写了 `appliesTo` 和版本边界
- [ ] 没有无出处的效果数据（如「召回率提升 18%」）、没有绝对化结论（如「唯一」「一定」）
- [ ] 有替代方案的题有对比表，表后有选型结论
- [ ] 反直觉的结论配了小实验，代码块按原样运行过，注释中的输出与实际一致
- [ ] 没有引用不存在的图片（「如下图」）
- [ ] 易错点是真实的误解，追问答案 ≤ 150 字
- [ ] `bank-spec validate` 零错误、零警告
