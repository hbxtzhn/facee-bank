## 一句话
InnoDB 每行记录带着最近修改它的事务 ID 和一个回滚指针，指针指向 undo log 里的旧版本，旧版本再指向更旧的，串成一条版本链。

## 要点
- [kp1|3] 行记录有隐藏列：最近修改它的事务 ID，和回滚指针
- [kp2|3] 回滚指针指向 undo log 中该行的上一个版本
- [kp3|2] 每次更新都在链头新增一个版本，链越往后越旧
- [kp4|2] 读视图沿着版本链找第一个对自己可见的版本
- [kp5] 没有事务需要的旧版本，会被后台清理

## 详解
### 先搞懂：一份文档的修改历史
像在线文档的版本历史：当前版本在最上面，点一下可以回到上一个版本，再点又回到更早的版本。每个版本记着是谁、什么时候改的。

InnoDB 的版本链就是这样的一条历史记录。

后文会用到的术语：

- **事务 ID**：每个事务开始写数据时得到的递增编号。
- **回滚指针**：指向 undo log 中旧版本的地址。
- **undo log**：保存数据改动前的旧值，既用于回滚，也用于读旧版本。

### 行上的两个隐藏列
InnoDB 的每一行除了你定义的列，还有两个隐藏列：

- `DB_TRX_ID`：最近一次修改这行的事务 ID。
- `DB_ROLL_PTR`：回滚指针，指向 undo log 中这行的上一个版本。

### 版本链怎么长出来
假设某行的值是 10，由事务 100 创建：

1. 事务 200 把它改成 20。InnoDB 把旧值 10 写进 undo log，行上改成 20，事务 ID 记为 200，回滚指针指向刚写的 undo 记录。
2. 事务 300 再把它改成 30。同样，旧值 20 进入 undo log，行上变成 30，回滚指针指向这条新的 undo 记录。

最终链是：当前行（30，事务 300）指向（20，事务 200）指向（10，事务 100）。

### 读的时候怎么用
读视图从链头开始，用每个版本的事务 ID 判断能不能看。看不了，就顺着回滚指针找上一个版本，直到找到可见的为止。

### 旧版本什么时候清理
undo log 里的旧版本不会永远保留。系统判断没有任何事务还需要读它之后，后台会把它清理掉。所以一个长时间不提交的事务，会让旧版本一直不能清理，undo 空间越积越大。

### 进阶：删除和二级索引（基础薄弱可先跳过）
- 删除一行并不是立刻物理删除，而是给记录打上删除标记，等没人需要时再清理。
- 版本链挂在聚簇索引的记录上；通过二级索引读数据时，通常要回到聚簇索引上判断可见性。

## 易错点
- 以为版本链保存在表里；旧版本放在 undo log 里
- 以为所有历史版本都永久保留；不再需要时会被清理
- 以为长事务只占用自己的资源；它会拖住 undo 的清理

## 追问
### [f1] 为什么要避免长事务？
长事务的读视图可能还要读很早之前的版本，所以相关的旧版本都不能清理，undo 越积越多，还会持有锁，拖慢其他事务。
