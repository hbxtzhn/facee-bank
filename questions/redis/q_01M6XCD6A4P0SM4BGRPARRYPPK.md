## 一句话
延迟双删是先删缓存、再改数据库、等一小段时间后再删一次缓存，把期间被写回的旧值清掉；但等多久不好定，仍可能有脏数据。

## 要点
- [kp1|3] 步骤：删缓存，改数据库，延时一会再删一次缓存
- [kp2|3] 第二次删除，是为了清掉并发读线程写回的旧值
- [kp3|2] 延时要覆盖读线程回填时间，有主从时还要覆盖同步延迟
- [kp4|2] 延时长短难以确定，所以仍有出现脏数据的风险
- [kp5] 第二次删除失败也会留下旧值，可配合重试

## 详解
### 先搞懂：擦黑板，写完再擦一次
老师把黑板上的旧答案擦掉，写上新答案。可有个同学刚好抄了旧答案，又举手贴回了黑板。老师发现后，过一会儿再擦一遍，把后来贴回的旧答案擦掉。

延迟双删对应这个过程：第一次擦，是删缓存；写新答案，是改数据库；过一会再擦，是第二次删缓存。

后文用到的术语：

- **脏数据**：缓存里和数据库不一致的旧值。
- **主从同步**：从库复制主库的数据，存在延迟。
- **延时**：第二次删除前等待的时间。

### 为什么单次删除不够
无论先删缓存还是先改数据库，都可能产生脏数据。

先删缓存、后改数据库：

1. 线程 A 要更新，先删除缓存。
2. 线程 B 读缓存没有，去数据库读到旧值（A 还没改完）。
3. A 把数据库改成新值。
4. B 把旧值写回缓存。缓存是旧值，数据库是新值。

### 延迟双删怎么解决
在 A 改完数据库后，再过一小段时间，A 第二次删除缓存。B 写回的旧值被清掉，之后新请求读缓存没有，会从数据库读到新值，重新回填。

### 延时为什么难把握
延时要大于「读线程读到旧值并写回缓存」的时间。如果读数据库用的是从库，还要考虑主库到从库的同步延迟。

- 延时太短：第二次删除时，旧值还没写回，删了个空，之后旧值又被写回，脏数据依旧存在。
- 延时太长：旧值在缓存中停留更久。

这个时间随负载和网络变化，没法精确确定，所以它只能降低风险，不能彻底消除。

### 还有哪些风险
- 第二次删除失败，比如服务重启，旧值留在缓存里，需要重试或补偿机制。
- 要等待延时，一般放到异步线程去做，增加了实现复杂度。

对一致性要求极高的场景，需要用读写锁，或用 canal 订阅 binlog 删缓存。

## 示例
```java
void update(Item item) {
    redis.delete(key(item.getId()));          // 第一次删除缓存
    db.update(item);                          // 修改数据库
    executor.schedule(() -> {
        redis.delete(key(item.getId()));      // 延时后第二次删除
    }, 500, TimeUnit.MILLISECONDS);
}
```

## 易错点
- 以为延迟双删能彻底避免脏数据；延时长短靠估计，只能降低概率
- 延时设得比数据库同步更短；第二次删除仍可能早于旧值写回
- 第二次删除直接阻塞业务线程睡眠；应交给异步任务
- 忽略第二次删除失败的情况；需要重试

## 追问
### [f1] 先改数据库再删缓存，是不是比先删缓存更好？
一般更推荐先改库再删缓存，脏数据出现的条件更苛刻。但并发读线程仍可能写回旧值，只是概率低。需要更强保证时再配合延迟删除或 binlog 订阅。
